# TripWise — исправления ИИ-агента v9 (накопительное обновление)

Базовая ветка: `snapshot/tripwise-current`, коммит `c78bb2ea9dabad1614a80ac5463913c4cac0a2ca`.
Этот ZIP содержит также все исправления v1–v8; отдельно устанавливать старые архивы не нужно.
Исходные базы Москвы V7 и Шанхая, репозиторий GitHub не изменены.

## Реально внесённые изменения v9

1. **Поиск по названию с опечатками** (`ai_ds/moscow_named_poi.py`):
   осторожное сопоставление нескольких неточно написанных слов, проверка неоднозначности,
   приоритет реально существующих ID; похожая фамилия сама по себе недостаточна.
2. **Короткая реплика — это тоже команда**: отдельное сообщение «уголок дедушки дурова»
   либо «уголак дедущки дурово» обрабатывается как запрос на добавление места
   без обращения к OpenRouter.
3. **Локальные операции** (`ai_ds/moscow_local_commands.py`): добавление именованных мест,
   запрос добавления объекта по категории (музей, парк, торговый центр и др.),
   перенос и удаление посещений, изменение темпа по дням, переключение допустимых
   транспортных режимов, заполнение пауз. Для некоторых сочетаний команд поддержан
   единый набор операций. Не распознанные составные инструкции не выполняются частично.
4. **Интеграция с действующим маршрутизатором** (`backend/moscow.py`):
   выбранные POI и кандидаты нужной категории включаются в рабочий список;
   изменения рассчитывает прежний JS-движок, а не другая реализация.
5. **Перенос альтернатив**: прежде чем удалить чужое необязательное место ради
   явного именованного запроса, агент пробует перенести это место на другой день
   (не более 10 попыток), с повторной проверкой расписания, еды и бюджета.
   Обязательные места и зафиксированное питание автоматически не переносятся.
6. **Транзакционная обработка**: операция попадает лишь в предварительный маршрут;
   без явного подтверждения сохранённая поездка не меняется.
7. **Индикатор версии**: экран и API отображают `moscow-offline-v9`, чтобы отличать
   новый сервер от оставленного работающим старого.
8. **Новые тесты**: отдельный набор для опечаток, намерений и подтверждения,
   корректировка проверки версии агента.

## Что намеренно НЕ обещано

Это улучшение не устраняет квоту бесплатного OpenRouter: произвольные свободные
запросы, которые нельзя разобрать локально, по-прежнему зависят от API.
Поиск по опечаткам не гарантирует однозначный результат для любого запроса.
Сохранены согласие на изменение маршрута, явные ограничения и защита обязательных POI.
Не заявлена полная оптимальность маршрута или проверка всех 19 510 реальных POI.

# TripWise — v8: quality-aware budget optimization (cumulative update)

**Source branch:** `snapshot/tripwise-current`; base commit `c78bb2ea9dabad1614a80ac5463913c4cac0a2ca`.  
**Cumulative:** contains changes from v1–v7; do not install old ZIP archives separately.  
**Original Moscow V7 and Shanghai data are unchanged.** GitHub has not been modified.

## What changed in v8

1. **Generous budgets now improve meal quality instead of always selecting the cheapest food.** The Moscow POI shortlist selects suitable sit-down restaurants and nearby alternatives, retaining inexpensive fallback options. The shared JS engine uses restaurant type, meal suitability, known rating / review signals, price-fit and realistic walking/transit detours. A restaurant's higher price is *not* automatically proof of quality.
2. **Soft daily dining targets instead of forced spending.** Only Moscow-style RUB routes with a genuinely generous budget use target meal budgets, which depend on budget per traveler per day (not the entire group's sum). Price-fit is subordinate to type and available evidence. Other currency/city routes retain their previous policy.
3. **Preserve dinner options on the last day.** Fixed the `futureFood` reservation bug: future empty-day placeholders were incorrectly treated as fully planned days. The planner now reserves funds for upcoming meals, including a better dinner when feasible, while keeping an inexpensive option available. It does not exceed the user's total budget; the preference is soft and allows legitimate expensive mandatory visits.
4. **Fast food not misclassified as a full-service restaurant.** The normalized Moscow planning layer recognizes Burger King (English/Russian), KFC and some other quick-service signals. These are *heuristic profiles* (source_type=synthetic unless verified facts exist). No source coordinates or verified fields are overwritten.
5. **No blanket price premium for unknown venues.** Where restaurant type is unknown, a more expensive synthetic estimate is not treated as higher quality. The regression for a 65-minute dinner wait passes again.
6. **Tests:** new JS and Python targeted cases for high/low budget, appropriate dinner, multi-day fairness, ratings vs price, group/per-person budgeting and restaurant type recognition.

## Expectations and limitations

- Aim for good value and a reasonable share of the available budget, *not* arbitrary spending to exactly 100%. If no attractive paid upgrade exists or verified information is missing, keep the unused money.
- A budget of ₽30,000 for one person on three days is not the same as ₽30,000 for four travelers on five days. Per-person/day resources determine when a premium dinner is financially realistic.
- Quality scores use only available evidence plus documented cuisine/type **estimates**; there is no confirmed menu, quality inspection, live price, opening-hour verification or booking availability in the limited local dataset.
- The system is a bounded heuristic. The full Moscow V7 data, transport graph and saved user's actual route were **not** exercised in this environment. We cannot certify globally optimal or always-filled itineraries.
- The common JS engine is still shared with Shanghai; the richer experience policy is scoped to RUB-mode routes. Some older Shanghai tests fail the same way on untouched v7; details in TEST_RESULTS.md.

# TripWise Moscow Routing — v7: порядок завтрака и географическая оптимизация

**Ветка:** `snapshot/tripwise-current`. **Базовый коммит:** `c78bb2ea9dabad1614a80ac5463913c4cac0a2ca`.
**Архив накопительный**: все изменения v1–v6 включены. Оригинальные Moscow V7 и Shanghai POI не изменяются.

## Новые исправления v7

1. **Завтрак — первая остановка.** В `ai_ds/web_demo/shanghai-engine.js` первая допустимая остановка в дне с завтраком — именно завтрак, до любых музеев/парков. Если его нельзя разместить до первой остановки, планировщик отмечает пропуск вместо нелогичного «завтрака» после достопримечательностей. Существующие ограничения по часам работы, бюджету, составу группы и времени питания сохраняются.
2. **После редактирования маршрута** фиксированная последовательность проверяет правило `BREAKFAST_NOT_FIRST`. Для изменяемых дней старого маршрута порядок нормализуется, затем рассчитывается общий планировщик. Противоречащая правка не принимается как успешная.
3. **Отказ от коротких поездок на такси ради 2–5 минут.** Для пеших переходов до 18 минут (меньше для детей/пожилых) такси допускается лишь при значимой экономии полного времени. Учитываются разрешённые режимы, стоимость и профили дорожной сети. В режимах «только такси» или «только ОТ» вспомогательная ходьба ограничена короткими переходами.
4. **Дополнительная внутридневная перестановка POI (relocate).** После 2-opt оптимизатор проверяет перемещение отдельных мест по дню. Принимает результат только после полного пересчёта времени переходов, питания, открытых часов и бюджета. Сравнение дорогих неоправданных автомобильных петель добавлено в целевую функцию московских маршрутов.
5. **Новые тесты** `tests/test_moscow_breakfast_geo_v7.cjs`: 1, 3, 5 дней; пропущенный завтрак; правка старой последовательности; проверка некорректного порядка; выбор пешком вместо такси; длинная полезная поездка на такси.

### Совместимость и ограничения

- Это улучшение эвристического маршрутизатора, а не доказательство глобально оптимального маршрута. Проверка оригинальных 19 510 POI, реального дорожного графа в полном объёме и браузерный E2E не проводились: большой каталог отсутствует в загруженном архиве `TripWise_code.zip`.
- Цены такси — синтетические расчётные оценки, не реальные предложения перевозчиков.
- Обходы дорог иногда неизбежны из-за одностороннего движения и мостов. Сокращение петель не может быть гарантировано для каждой поездки; маршрут с приблизительной геометрией остаётся таким и помечен на карте.
- Изменения находятся в **реально используемом общем JS-движке**, отдельная карта или дублирующий планировщик не созданы. Основная логика также используется Шанхаем. Несколько старых тестов Шанхая остаются с прежними ошибками без данных и несовпадений ожиданий; детали в `TEST_RESULTS.md`.

# TripWise Moscow Routing — v6: длительности посещений и темп

**Исходная ветка:** `snapshot/tripwise-current`; базовый коммит: `c78bb2ea9dabad1614a80ac5463913c4cac0a2ca`.
**Тип архива:** накопительный v1–v6; распаковывать прошлые архивы отдельно не нужно.

## Новое в v6

- Исправлены неестественно короткие синтетические оценки длительности у московских музеев и торговых центров. Больше не считаем музей с исторической категорией прогулкой на 25 минут.
- `ai_ds/moscow_catalog.py`: введена детерминированная классификация `visit_type` на базе названия, категорий и OSM-тегов. Музеи (обычные/крупные), торговые центры, рынки, отдельные магазины, парки, исторические места и пр. имеют разные ориентиры времени. Примеры: обычный музей ~90–125 мин; торговый центр ~140–170 мин до учёта темпа; отдельный магазин ~35–60 мин.
- Внесены распознавание сокращений `ТЦ`, `ТРЦ`, `ТРК`, `ГУМ`, `ЦУМ`, OSM `shop=mall`, а также ряда известных названий московских ТЦ. Не все объекты однозначно классифицируются по имени — оценка остаётся синтетической.
- Шопинг в торговом центре: **120–180 минут** в зависимости от темпа. Обычный маленький магазин не получает такую длительность.
- Коэффициенты темпа применяются к базовым минутам при первичном планировании и после подтверждённого редактирования маршрута. При более спокойном темпе на музей выделяется больше времени, а дневная целевая насыщенность ниже.
- Для торговых центров без исходных часов работы применяется оценочное окно 10:00–22:00, явно помеченное как синтетическое; подтверждённые часы работы сохраняются.
- Запрошенное пользователем конкретное число минут для обязательных мест теперь передаётся в общий JS-движок как жёсткая длительность; темп **не перезаписывает** его.
- Версия планировочного слоя повышена до `moscow-planning-estimates-v3` для отличия пересчитанных оценок. Сырые московские/шанхайские базы и географические координаты не изменены.
- Движок Шанхая оставлен функционально совместимым: новый предел 120–180 минут применяется только к POI с признаком `visit_type=shopping_mall`, `duration_source=synthetic`, который передаёт московский адаптер.

## Важные ограничения

- Реальная 19 510-объектная Moscow V7, транспортные матрицы и браузерное окружение не входили в компактный `TripWise_code.zip`, поэтому скриншоты и маршрут пользователя **не воспроизведены end-to-end**.
- Если пользователь самостоятельно задал индивидуальную длительность, она сохраняется, даже если меньше типичной оценки (это осознанное пожелание, не гарантия достаточности).
- Старые сохранённые маршруты сами не перепланируются. Нужна новая поездка; после смены темпа через чат для изменённого дня возможен отдельный пересчёт.
- Полное заполнение всех часов не гарантируется при ограничениях бюджета, времени, доступности и дорожной сети; предыдущие ограничения v5 остаются.

# TripWise — Moscow named POI fix v5

Основа: `snapshot/tripwise-current` @ `c78bb2ea9dabad1614a80ac5463913c4cac0a2ca`. Накопительный пакет: содержит v4 и все предыдущие исправления. GitHub и базы данных не изменялись.

## Причина ошибки на скриншоте

- В v4 локальный парсер не распознавал фразу «дебил, я хочу в уголок дедушки дурова» (не было шаблона `хочу в`). Запрос уходил в OpenRouter; ИИ мог вернуть ложное «не нашёл в каталоге».
- В некоторых вариантах `Уголок Дурова` совпадение по двум словам из трёх не проходило порог `.67` (реальное значение `2/3` немного меньше `.67`). Порог заменён на точное целочисленное сравнение `overlap * 3 >= len(query_words) * 2`.
- Исходный **реальный V7 CSV** на GitHub подтверждает запись: `moscow-cultural-0,Уголок дедушки Дурова,55.77933,37.62121,entertainment` (blob SHA `9542f7198bb8f41000bc0bd9e17c1bfe7dccbd35`). Встроено строгое сопоставление с этим ID, **только если объект присутствует в фактически загруженном каталоге**. Нет генерации POI/изменения координат.
- Поиск распознаёт разговорные варианты «хочу в», «хочу попасть в», «хочу сходить в», «пойдём в», «давай в», «внеси» и т. д. Не трактует «не хочу» как просьбу о добавлении. Не подменяет Уголок дедушки Дурова Театриумом Терезы Дуровой или Дуровским бульваром.
- Кандидаты остаются привязаны к **точному ID**. Прежде чем менять маршрут, проверяется выполнимость времени, бюджета и транспорта. Предпросмотр и подтверждение обязательны. Простые команды работают при исчерпании лимита OpenRouter.
- В API статуса московского агента добавлено `agent_version=moscow-named-v5` и режим `local` при отсутствии ключа ИИ. На странице маршрута под чатом отображается версия обработчика. Это позволяет обнаружить не перезапущенный старый сервер.

## Как проверить у себя

1. Сделайте резервную копию TripWise. Распакуйте содержимое этого ZIP в корень репозитория, с заменой совпадающих файлов; не удаляйте `data/` и `.git/`.
2. **Полностью остановите и заново запустите FastAPI/uvicorn**, иначе интерпретатор продолжит работать со старым модулем в памяти. Если есть несколько серверов/контейнеров, обновите тот, к которому подключается сайт.
3. Жёстко обновите страницу (Ctrl+F5). Под чатом должна появиться строка `moscow-named-v5`. Если её нет — открыта старая версия сайта/сервера.
4. Отправьте фразу «Я хочу в Уголок дедушки Дурова на 22 ноября». Если маршрут позволяет, агент покажет предложение добавить конкретное место. **Нажмите «Применить изменения»** после просмотра.
5. Если место не помещается из-за ограничений, агент должен ответить о невозможности вставки, а не отрицать его существование.

## Ограничения

Полный V7 JSON (25 МБ) в пользовательском ZIP не предоставлен; наличие и ID проверены по реальному CSV-экспорту GitHub. Настоящие часы работы театра, билеты, дорога и конкретная сохранённая поездка не проверены. Интеграционный тест использует настоящий ID и название, но синтетический доступный временной граф и транспорт.

# TripWise — накопительный пакет v4: конкретные POI и офлайн-команды чата

**Исходная ветка:** `snapshot/tripwise-current`  
**Базовый HEAD:** `c78bb2ea9dabad1614a80ac5463913c4cac0a2ca`  
**Архив для распаковки в корень проекта.** Включает все изменения предыдущего v3. Репозиторий GitHub и исходные базы `data/` не менялись.

## Исправления v4 (в дополнение к v3)

1. **Запрос конкретного места по названию:** локальный обработчик `ai_ds/moscow_named_poi.py` ищет существующий ID во всём индексированном каталоге Moscow V7 (названия и известные альтернативные названия). Название «Уголок дедушки Дурова» включено в тестовые синонимы для театра зверей; результат всегда привязан к существующему ID из каталога. Не создаёт вымышленные координаты, места или цену. Если POI отсутствует или есть неоднозначные дубли — возвращает явный вопрос, не подставляет другое место.
2. **Отсутствие OpenRouter не блокирует простые команды для Москвы.** Прямые добавления именованных POI, отдельные ответы «22, замени автоматически» после явного предыдущего запроса, а также прежнее локальное заполнение длинных перерывов обходят языковую модель. Сложные запросы по-прежнему требуют OpenRouter.
3. **Разрешённая замена:** при невозможности просто вставить точный POI проверяется удаление *одного* необязательного посещения, но только когда пользователь явно разрешил заменить. Обязательные POI и ранее запланированные приёмы пищи защищены. Полная повторная проверка маршрута выполняется тем же JS-планировщиком.
4. **Обязательное подтверждение:** в ответе явно сказано, что построенное предложение ещё не сохранено. Успешным добавление считается только тогда, когда точный запрошенный ID действительно присутствует в проверенном предложении, а окончательное изменение требует «Применить изменения». При неподходящем бюджете/окнах/транспорте остаётся прежний маршрут и возвращается конкретная ошибка.
5. **Понятная ошибка лимита ИИ:** `LLM_RATE_LIMITED` отображается как ответ HTTP 429 внешнего OpenRouter, а не как «ИИ закончился». Локальные команды доступны даже при этой ошибке.
6. **Устранена ненужная зависимость Москвы от файлов Шанхая:** `ShanghaiAssistantService` больше не читает шанхайские `pois.json`/`transport.json` при переданном извне каталоге. Обычные шанхайские сеансы по-прежнему сверяют оба файла по SHA256.
7. **Защита сложных запросов:** локальный парсер не проглатывает другие команды в составном запросе, не пытается интерпретировать общие категории («добавь недорогой парк») как имя собственного места и не повторяет уже посещённый POI.

## Ограничения v4

- **Нельзя утверждать, что конкретный «Уголок дедушки Дурова» есть в реальной Moscow V7:** большой каталог не был включён в присланный пользователем ZIP, поэтому тестировалась только синтетическая фикстура с таким названием, алиасом и проверяемым ID. Если в конкретном каталоге нет этой записи, приложение прямо сообщит, что не может выбрать точку.
- Реальные цены билетов, часы работы и транспортные переходы для названного POI не подтверждены в этом пакете.
- Нельзя гарантировать успешную вставку места: бюджет, режим транспорта, рабочие часы, состояние группы и другие ограничения имеют приоритет. Когда попытка невозможна, маршрут не меняется.
- `openrouter/free` остаётся внешним сервисом с лимитами; **обход лимита касается только распознанных локальных команд**. Не используйте нелегальные обходы API или платные fallback без согласия.
- **Полный E2E** на базе Moscow V7 и фактической поездке пользователя со скриншота по-прежнему NOT RUN. Нет крупных `data/` и полного набора примеров.
- Из v3 сохраняются известные ограничения в тестах Шанхая, описанные ниже.

## Применение

1. Создайте резервную копию текущей папки TripWise.
2. Проверьте, что основа — `c78bb2ea9dabad1614a80ac5463913c4cac0a2ca`; если после неё были самостоятельные изменения тех же файлов, не перезаписывайте их вслепую — сравните diff.
3. Распакуйте ZIP непосредственно в корень TripWise с сохранением относительных путей и заменой совпадающих файлов. Не удаляйте `data/` и `artifacts/`.
4. Перезапустите сервер. Создайте новую поездку или откройте ранее сохранённую; **изменения ассистента требуют нового сообщения и подтверждения**, старые маршруты автоматически не пересчитываются.
5. Пример локальной команды: **«Добавь Уголок дедушки Дурова на 22 ноября. Если не помещается, замени одно необязательное посещение».** В появившемся предложении проверьте требуемый POI и нажмите «Применить изменения».

## Новое в v3

1. **ИИ-помощник: длинные перерывы.** В Москве распознаётся точный запрос вида «в 2, 3, 4 день длинные перерывы, любые места и категории». Он преобразуется в проверяемую операцию `fill_gaps` на указанные даты, **не требует ответа OpenRouter для этого явного запроса**. Понимает порядковые номера, диапазон и все дни; неоднозначные и комплексные запросы оставляет общему интерпретатору.
2. **OpenRouter.** На ошибку `LLM_INCOMPLETE_RESPONSE` сделана **одна** повторная попытка с меньшим каталогом и историей. Другие ошибки (например лимит) не скрываются.
3. **Реальный маршрут через чат.** Для `fill_gaps` подключён `MoscowGapIndex` по V7, поиск кандидатов из всех разрешённых категорий, пересчёт направленных транспортных матриц, расписания, цен и питания общим JS-планировщиком. Поиск ограничен, распределён поровну между выбранными днями. Применение возможно только после предпросмотра и подтверждения; исходная версия до подтверждения неизменна.
4. **Исправлено падение чата после удачного добавления.** Новые места, найденные вне исходного shortlist, теперь имеют названия в ответе агента; раньше могла возникать ошибка `KeyError`.
5. **Длинный хвост дня.** Общий планировщик для **Москвы** (условия `RUB` + `compact_waits`) пробует ограниченное количество реальных выполнимых поздних вставок в день, со строгими проверками бюджета, транспорта, часов работы и обязательных мест. Попытки распределяются между днями, а не уходят только на первый.
6. **Резерв бюджета.** Для дешёвых московских поездок улучшен подбор реального доступного питания: более дешёвые завтраки/обеды не должны вытесняться резервом на ужин дороже дневного лимита. Фиктивное питание **не создаётся**: если на него нет денег, проверка `meals` остаётся `failed`.
7. **Сообщения об ограничениях.** Агент отличает отсутствие решения в **проверенном конечном поиске** от отсутствия подходящих мест во всей Москве. При неудачной вставке сообщает условия и сохраняет прежний план.

## Сохранено из предыдущих исправлений (v1–v2)

- Индивидуальные временные окна первого, промежуточных и последнего дней; настройка полного дня и совместимость со старыми анкетами.
- Улучшенный ценовой/питательный планировочный слой Moscow V7 без изменения исходной базы; отдельная оценочная модель тарифов и стоимости маршрута.
- Улучшения выбора транспорта на участке, дешёвых POI, доступного питания, поиска вдоль маршрута и календарного распределения.
- Исправленные цвета маркеров/линий основной карты, легенда, разбивка расходов по дням.

## Важные ограничения

- Это **не доказательство идеальной маршрутизации на всей Москве**. В переданном `TripWise_code.zip` отсутствуют `data/demo/moscow/v7/`, шанхайские базы и полный набор примеров, поэтому живой маршрут по скриншотам, все 19 510 POI и браузерный E2E не проверены.
- Полное заполнение **всех часов каждого дня** невозможно гарантировать при настоящих ограничениях времени, денег, доступности и транспортной сети. Если нет доступных ресторанов на требуемые 3 приёма пищи, план честно помечается частичным.
- Исправления v3 последнего участка дня специально включены для Москвы: Шанхай использует тот же файл JS, но ветка активируется только для московского `RUB` + `compact_waits` сценария.
- Некоторые прежние шанхайские тесты требуют отсутствующий `data/` каталог; один тест `test_shanghai_v4_meals.cjs` не проходит с ошибкой `5 !== 30` на старом и новом движке. Это **не исправлено** данным пакетом.
