# Дополнение Routing к контракту 0.1

Однодневный локальный прототип согласован владельцем AI/DS в чате. Это отдельное дополнение к [исходному контракту](contracts-v0.1.md), который не изменяется. UserPreferences, POI и Recommendation сохраняют свои структуры. Многодневность, адаптивный темп F06, реальная навигация и полный MVP не считаются реализованными.

## Вход

`build_route(preferences, pois, recommendation, travel_times, routing_context)` принимает полный проверенный POI-набор, не только top-K. Кандидаты — объединение ID Recommendation.items и required_poi_ids. Максимум восемь уникальных ID; превышение — CANDIDATE_LIMIT_EXCEEDED без усечения. UserPreferences.date_start должен равняться date_end.

Сценарий CLI содержит routing_context и travel_times. Полный пример: [day.synthetic.json](../../examples/routing/day.synthetic.json).

```json
{
  "routing_context": {
    "day_start": "2026-11-17T09:00:00+03:00",
    "day_end": "2026-11-17T12:00:00+03:00",
    "endpoint_policy": "first_last_poi",
    "declared_pace": "balanced",
    "max_active_seconds": 9000,
    "rest_after_visit_seconds": 900
  },
  "travel_times": {
    "mode": "walking",
    "basis": "test_matrix",
    "source_id": "synthetic_route_fixture",
    "pairs": []
  }
}
```

Все показанные ключи обязательны. Числа 9000/900 — явные тестовые входы, не defaults. declared_pace равен preferences.pace для любого из трёх разрешённых темпов. Автоматический вывод лимитов из pace не выполняется.

- day_start/day_end — ISO 8601 с часовым смещением, тот же местный день, что в профиле. Смещение должно соответствовать preferences.timezone в этот момент. Начало раньше окончания по абсолютному времени.
- endpoint_policy — только first_last_poi: начало в первом POI, конец в последнем. Гостиница, подход и возвращение не включены.
- max_active_seconds — конечное положительное число; предел суммы посещений и переходов.
- rest_after_visit_seconds — конечное неотрицательное число; отдых после каждого посещения, кроме последнего. Отдых занимает дневное окно, но не активный лимит. Это не планирование обеда.
- Секунды во всём Routing имеют точность не мельче одной микросекунды. Boolean, NaN, Infinity и более мелкая точность отклоняются; числовые строки не принимаются. Арифметика расписания целочисленная, без округления за границу окна. Огромные целые не преобразуются в float.

## Направленные переходы

travel_times.mode равен preferences.transport. basis: test_matrix / routing_provider / geometric_estimate; source_id — непустая строка. pairs — массив направленных записей, без дублирующихся пар и переходов в себя. Все ID должны существовать в полном POI-наборе. Пара A→B не задаёт B→A.

Каждая запись имеет from_poi_id, to_poi_id, status, duration_seconds, distance_meters:

| status | duration_seconds | distance_meters |
|---|---|---|
| known | Конечное неотрицательное число | Конечное неотрицательное число либо null с предупреждением |
| unknown | null | null |
| unreachable | null | null |

unknown означает, что источник не знает; unreachable — подтверждённую недостижимость для данного mode. Отсутствующая запись означает missing. Missing и unknown не заменяются нулём и не означают unreachable. Для рассчитанного перехода нужна known-запись с известным временем.

## Снимок Recommendation

Профиль и весь POI-набор повторно проверяются публичным recommend. Для снимка проверяются schema/model версии, обязательные ID, исключённые POI и статусы проверок. Items должны иметь допустимые уникальные ID, последовательные целые rank (boolean запрещён), score = null, непустые reasons с разрешёнными кодами и ожидаемое количество элементов. Проверяется структура warnings.

Для PRIMARY_INTEREST_MATCH и SECONDARY_INTEREST_MATCH поле categories обязательно: непустой массив уникальных строк, точно соответствующий пересечению категорий POI с соответствующими интересами профиля. Объяснение не может приписывать объекту несуществующие совпадения.

Снимок ранжирования является входом Routing: его порядок не пересчитывается для сравнения с текущим временем. Динамические предупреждения о свежести не должны делать снимок невалидным. Routing не утверждает, что снимок является самым свежим ранжированием. Изменение исходных данных требует формирования нового снимка у вызывающей стороны.

## Выход и статусы

Базовый TripRoute сохраняется. Добавлены model_version = day-enumeration-v0.1 и массив breaks в каждом дне. Break имеет start_at/end_at в том же формате, что посещение. В legs сохранены источник, basis и null геометрия/навигация, если они не предоставлены. Время перехода учитывается между отдыхом после предыдущего POI и началом следующего посещения.

Warnings — отсортированный массив кодов. Бюджет not_checked, часы работы unknown. Непроверенные координаты, доступность, неизвестное расстояние и тестовая матрица маркируются явно.

- Найденное расписание: time = passed, required_places = passed, общий status = unknown. Даже routing_provider не подтверждает неизвестные часы работы и весь маршрут.
- Нет полного расписания, но неизвестные длительности/пары потенциально могут позволить его построить: unknown, time = unknown, обязательные места перечислены в unplaced_required_poi_ids.
- Нет расписания, и полный перебор с известными данными/нижними границами доказывает невозможность ограниченной задачи: infeasible, time = failed. Это не доказательство невозможности поездки за пределами выбранных кандидатов и лимитов.
- Пустой набор: unknown с NO_CANDIDATES, без заявления о выполнимости.

Если есть допустимое расписание по известным данным, но другие последовательности зависят от неизвестного, добавляется UNRESOLVED_CANDIDATE_DATA: оптимальность по полным реальным данным не подтверждена.

Ошибки структуры/контекста/матрицы возвращаются как ROUTING_VALIDATION_ERROR с details/path/code. Ошибки профиля/POI от публичного Recommendation сохраняют VALIDATION_ERROR. CLI возвращает 0 при результате любого статуса, 1 при ошибке валидации, 2 при ошибке чтения/JSON. Оба потока явно UTF-8.
