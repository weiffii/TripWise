# Предложение завершения Routing и Route Assistant

17 ноября 2026. Routing Agent. **Предложение для согласования; новой реализации нет.** Применён `route-validation` как контрольный список ограничений и будущей приёмки. Прочитаны правила проекта, основные документы, действующие контракты, `routing-baseline.md`, код `ai_ds/routing.py` и [Data-аудит](data-readiness-2026-11-17.md). Действующие `day-enumeration-v0.1`, `lexicographic-v0.1`, контракты 0.1 и исходные данные не менялись. Сетевых вызовов и новых тестовых прогонов в этой документальной задаче нет.

## Что именно требуется закончить

F05 требует распределение по дням, расписание, обязательные места, бюджет и отдых; F06 — три темпа; F07/F08 — соответствующие транспорту реальные переходы; F10 — LLM-интерпретацию с проверяемым пересчётом и подтверждением; F12 — честные неопределённость и конфликты. Сейчас есть однодневный точный перебор не более восьми кандидатов, явные активный лимит и отдых. Многодневность отклоняется, бюджет не проверяется, часы неизвестны, geometry/navigation_url теряются при построении leg (возвращаются null).

Все 2058 актуальных реальных POI имеют неизвестные длительности, стоимость и часы; реальной матрицы переходов нет. Это **блокер рассчитанного реального расписания**, который нельзя решить выбором более сложного алгоритма. Даже после внедрения предложенного планировщика такие входы должны давать `unknown`, а не искусственные времена. Для демонстрации механики допустим явно синтетический сценарий; для реального сценария нужны отдельно утверждённые оценки/сведения и реальные переходы.

## Сравнение многодневных вариантов

Обозначения: D — число календарных дней; N — число уникальных кандидатов `Recommendation.items ∪ required_poi_ids`; n_d — число посещений дня. Начало/конец — первый/последний POI, как в baseline; подход от гостиницы и возвращение не включены и отмечаются предупреждением.

| Вариант | Что даёт | Ограничения и сложность |
|---|---|---|
| Точный общий перебор/DP по маскам | Перечислить допустимые дневные последовательности, затем выбрать непересекающиеся маски дней с required; точность для ограниченного набора и известных данных | Перечисление порядка порядка N!, распределение масок до O(D·3^N); нынешние ≤8 — только область контрольного oracle, не решение для большого пула |
| Географические кластеры, затем отдельный день | Быстро группирует близкие места; простая визуальная логика | Кластеры по координатам не знают directed travel time и required/time windows; могут отрезать допустимое решение, требуют нового правила числа/баланса кластеров |
| **Детерминированная вставка во все дни, required сначала** | Работает с произвольным конечным D/N, повторно проверяет все ограничения каждой вставки; без новых весов Recommendation и библиотек | Эвристика, не гарантирует глобальную оптимальность или нахождение существующего решения; полный пересчёт допустимых вставок всех оставшихся required с линейной валидацией даёт консервативную верхнюю оценку O(D·N⁴), optional-фаза O(D·N³), матрица O(N²) |

**Рекомендация:** третий вариант как отдельная `multiday-insertion-v0.2`, сохранив 0.1 для совместимости и малых контрольных сравнений. Сценарии 1–3 дня обязательны для приёмки; это не новый предел длительности поездки. Числовые пределы API/размера матрицы/времени исполнения определяются эксплуатационными измерениями и согласуются с Fullstack, а не скрытым усечением required или выбранных дат.

## Точный предлагаемый алгоритм

1. Валидировать профиль, весь POI-набор, снимок Recommendation, один дневной контекст на каждую дату включительного диапазона и directed travel_times с тем же transport. Явно определить пул: это items + required; недостаток top_k означает ограниченность выбора, не отсутствие других POI в городе. Число кандидатов и пределы пула возвращаются в диагностике. Увеличение candidate pool — явный запрос Recommendation с согласованным top_k, не изменение формулы ранжирования Routing.
2. Создать пустой маршрут каждого дня. Все ID используются не более одного раза во всей поездке. Никаких междневных переходов между последним POI одного дня и первым следующего: endpoint_policy не включает ночёвку; это ограничение показано пользователю.
3. Разместить required. Для каждого ещё не размещённого required вычислить все допустимые вставки во все позиции всех дней, каждый раз полностью перепроверяя порядок, directed legs, окно, активный лимит, отдых/обед, известные часы и нижнюю границу бюджета. Выбрать required с наименьшим числом допустимых вставок, при равенстве — ID по возрастанию. Для него выбрать вставку с минимальным **приращением времени переходов**, затем временем окончания дня, затем датой и индексом позиции. Приращение может быть отрицательным; это допустимо при нетреугольной/направленной матрице, обе старые/новые последовательности проверяются полностью.
4. После required по очереди рассмотреть optional в возрастающем Recommendation.rank. Принять лучшую допустимую вставку по тем же tie-breaks, если она не нарушает ранее размещённые required/optional. Весов не вводить, rank не приравнивать к количественной полезности. Не заменять уже выбранный более высокий rank ради суммы низких; это последовательная эвристика, а не доказанная глобальная лексикографическая оптимизация.
5. Если для required нет допустимой вставки: **не удалять его молча и не добавлять optional до решения проблемы**. Вернуть черновик, `unplaced_required_poi_ids`, причины отказа и `required_places=unknown` либо `failed` только при доказанном конфликте. Предлагать увеличить окно/изменить ограничения/дать недостающие данные, требуя нового подтверждения; пользовательский required-set самостоятельно не менять. Эвристический тупик при известных данных не доказывает невозможности всех перестановок: общий `status=unknown`, код `SEARCH_NOT_PROVEN`.
6. Для optional с неизвестной длительностью/переходом сохранить ID и причины в `unresolved_candidate_ids`; не выдавать время посещения. Если остаётся известная проверенная часть, она может быть показана как часть черновика, но не как полный выполненный запрос. Неизвестный required не превращается в посещение нулевой длительности.
7. Полный повторный валидатор результата независимо от процесса выбора проверяет ID/no-duplicate, required, даты, интервалы, суммарные ограничения, directed legs и ограничения источников. Одни и те же функции используются после генерации и после AI-правки. Сохранение маршрута не является обязанностью математического планировщика.

Правило выбора — **required → порядок Recommendation → минимальное приращение переходов → стабильные tie-breaks**. Не обещает минимум километров, максимальную сумму ratings или объективную туристическую полезность. Для малых полностью известных fixtures сравнить с точным oracle и измерить долю найденных решений/разницу выбранных rank; заранее не объявлять качество эвристики достаточным.

### Проверка последовательности и расписание

Для дня d окно W_d = day_end − day_start по абсолютному времени. Посещения идут подряд с учётом перерывов/переходов и ожидания известных открытий. Активность A_d = сумма visit_duration + сумма duration_seconds соседних legs. Отдых, ожидание и обед занимают окно, но не A_d. Должны выполняться A_d ≤ active_limit_d и последнее end_at ≤ day_end. При неоднозначности DST используется aware timestamp, который должен соответствовать timezone профиля; отрицательные/несуществующие интервалы отклоняются. Секунды остаются с точностью до микросекунды без float-округления, как в baseline.

Порядок между посещениями сохраняется из 0.1: отдых после посещения, затем переход, затем ожидание открытия следующего POI при необходимости. Отдыха после последнего POI нет. При фиксированном обеде его интервал нельзя перекрыть посещением/переходом; если следующая активность пересекает обед, целиком переносится после него и день пересчитывается. Нет предположения, что посетитель может закончить половину перехода до обеда.

## Предлагаемые параметры темпа — гипотеза для утверждения

Предлагается versioned `pace-policy-v0.2`. Числа ниже — продуктовые стартовые параметры для тестов, **не медицински/эмпирически доказанные нормы**. Реальных пользовательских данных для их калибровки нет.

| pace | Доля доступного окна α | Отдых после каждого посещения, кроме последнего | Окно 09:00–18:00 с обедом 45 мин: active limit |
|---|---:|---:|---:|
| relaxed | 0.55 | 20 мин | 272.25 мин |
| balanced | 0.70 | 15 мин | 346.5 мин |
| intensive | 0.85 | 10 мин | 420.75 мин |

Формула: active_limit_d = floor_microseconds(α_p · (W_d − meal_seconds_d − blocked_seconds_d)). Доля задаётся рационально 55/100, 70/100, 85/100. Подставляются реальные длительности/переходы, а не фиксированное число мест. Если explicit active cap задан, применяется min(явный cap, лимит темпа); cap должен быть >0. Дополнительные паузы задаются явными blocked intervals; blocked_seconds — сумма их длительностей. Meal и blocked intervals должны целиком находиться внутри дневного окна и не пересекаться друг с другом; пересечения отклоняются как INVALID_BLOCKED_INTERVALS, поэтому каждая секунда вычитается ровно один раз. Отдых после посещений уже проверяется в расписании и отдельно из W в формуле не вычитается. Требуется положительное доступное окно. Различие темпов может не изменить набор мест, если кандидатов мало/день короток; это допустимо, если вычисленные нагрузка и правила отдыха корректны.

Обед **не выбирается из воздуха**: у каждого дня `meal_break` — null либо явный интервал с местными aware start/end и `kind=meal`. Если null, `MEAL_BREAK_NOT_CONFIGURED`, а не утверждение «питание учтено». Для нового сценария предлагается запрашивать у пользователя/Fullstack явный обед 13:00–13:45 как редактируемую настройку; не считать этот пример обязательным фактом поездки. Кафе — POI/приём пищи только при явном решении, нет двойного учёта одного обеда и посещения кафе.

## Политика неизвестных данных и бюджет

**Рекомендуемый default `unknown_duration_policy=strict`:** null остаётся null, timestamp не вычисляется через ноль/среднее. Неизвестные необходимые длительности или directed legs дают `time=unknown`; известная часть может служить нижней границей для доказуемого отказа. Строгая политика работает уже на уровне идеи существующего baseline; ни один из нынешних реальных наборов не даст полного расписания без новых сведений.

Альтернатива после отдельного одобрения: sidecar `duration_overrides` на ID с `minutes`, `basis=expert_estimate`, `method_version`, `author`, `recorded_at`, `evidence_url` nullable. Он не перезаписывает raw/snapshot и не меняет verified_at источника. Data/Routing готовят и человек утверждает каждую методику/набор оценок; LLM не назначает duration. В результате явно сохраняются расчёт по оценкам и `ESTIMATED_VISIT_DURATION`; это ориентировочный план, не проверенный факт. Автоматических категорийных значений «музей 60 минут» этим proposal не утверждается.

Для бюджета используется существующий scope trip_food_and_entertainment, вся поездка и один человек. Предлагаемый sidecar `cost_context` содержит только явно известные затраты по ID/обедам и валюте профиля, с basis/evidence. Неизвестное не равно нулю. Известная сумма — нижняя граница: если уже превышает amount, выбранный вариант отвергается; если не превышает, но остаются неизвестные расходы, `budget=unknown`. `budget=passed` возможен только при полном покрытии согласованного состава расходов известными суммами в одной валюте. Если budget=null, `not_checked`; при несовпадении валют — `unknown` с `CURRENCY_MISMATCH`, конвертации нет. Одинаковая стоимость билета не означает включённый обед. Граница того, что считается расходом питания/развлечений, должна быть явно подтверждена человеком; без данных никаких обещаний «уложились».

Часы 0.1 только null. Предлагается отдельный слой `opening_intervals` на конкретную дату, timezone и ID (см. diff ниже), заранее нормализованный Data из разрешённых проверенных источников. Известный закрытый день — `[]`, неизвестный — null; различие обязательно. Интервал посещения целиком должен помещаться в один открытый интервал, иначе эта вставка не подходит. Weekly/holiday парсер и внешние источники не утверждаются данным алгоритмом: Data сначала фиксирует источник/условия/семантику. Наличие простого поля `availability=available` не подтверждает открытость в нужный час.

`infeasible` допускается для доказанных ограничений: например обязательный объект закрыт во все выбранные дни; минимальная собственная длительность обязательных посещений превышает сумму активных лимитов всех дней; или заданные фиксированные положения явно пересекаются. Жадная вставка может вернуть `unknown` даже на полностью известных данных. Нельзя показывать `infeasible` только потому, что эвристика не нашла решение.

## Минимальный отдельный контракт 0.2 — не изменение 0.1 на месте

1. Новый opt-in Routing request/result `schema_version=0.2`, `model_version=multiday-insertion-v0.2`; UserPreferences/POI/Recommendation 0.1 передаются как вложенные существующие структуры. Старый `build_route`/CLI и данные 0.1 продолжают работать; новый интерфейс выбирается явно. Совместимость и фактическое имя новой функции утверждаются с Architect, нельзя молча принять 0.2 старым валидатором.
2. `routing_context.days[]`: ровно одна запись на каждую дату диапазона, `date`, aware `day_start/day_end`, `meal_break` (null либо interval), `blocked_intervals[]`, `max_active_seconds` (nullable explicit cap). На уровне context: `endpoint_policy=first_last_poi`, `pace_policy_version=pace-policy-v0.2`, `unknown_duration_policy=strict`, `duration_overrides[]` (по умолчанию пустой), `cost_context`, `opening_intervals[]`. `pace` остаётся в preferences, две расходящиеся копии pace не вводятся.
3. `travel_times` сохраняет mode/basis/source_id/pairs; добавляются `retrieved_at`, `valid_for` (nullable интервал применимости) и в directed pair `geometry` (null либо GeoJSON LineString WGS84 [longitude,latitude]) и `navigation_url` (null либо проверенный абсолютный HTTPS URL). Право хранения/показа геометрии определяется источником. Если длительности зависят от даты/времени отправления, матрица должна быть помечена соответствующим valid_for; вне него — unknown, не вечная константа. Дубликаты/self-pair и неправильные координаты отклоняются.
4. `opening_intervals[]`: `{poi_id,date,timezone,intervals,source_id,source_url,retrieved_at,verified_at}`, intervals — null (unknown) или массив aware start/end интервалов; [] подтверждает закрытый день только при наличии provenance. Один день без записи означает unknown. POI.opening_hours остаётся null в 0.1, перенос не требует разрушать старые snapshots.
5. `cost_context`: `{currency,visit_costs:[{poi_id,amount,basis,source_url,recorded_at}],meal_costs:[{date,amount,basis,source_url,recorded_at}],coverage_complete:boolean}`. amount null допустим как unknown; coverage_complete не позволяет обойти валидацию: для `passed` нужны все включённые затраты и утверждённый состав scope. Записи другой валюты не конвертируются; evidence не подменяется verified_at POI. Источник на уровне поля/sidecar согласуется явно: исходное правило «один источник на набор 0.1» сохраняется.
6. В `TripRoute` сохраняются days/visits/legs/breaks; добавляются `route_id` и `version` (назначает Backend, у локального draft null), `planning_metadata` с candidate_count/selected_count/pool_scope/algorithm/search_complete=false и `unresolved_candidate_ids`, причины неразмещения, сведения об использованных estimate. Для breaks добавляется kind: rest/meal/blocked/waiting. На каждом дне и поездке — constraint_checks. Не вычисленные start/end — null, без скрытой подстановки.
7. Расширяются причины/diagnostics без обещания HTTP-статусов: UNKNOWN_DURATION, MISSING_TRAVEL_TIME, SEARCH_NOT_PROVEN, REQUIRED_CLOSED, CURRENCY_MISMATCH, ESTIMATED_VISIT_DURATION, MEAL_BREAK_NOT_CONFIGURED, MATRIX_NOT_VALID_FOR_TIME. Architect фиксирует точную схему ошибок и отображение в API отдельно с Fullstack.

Общий `status=feasible` возможен только при всех применимых checks=passed и реальных необходимых данных. При оценках/неизвестных часах/стоимости/транспортных данных остаётся `unknown` с отдельными понятными checks. `time=passed` может означать только рассчитанность по переданным оценкам; рядом обязателен basis, чтобы пользователь не принял его за проверенный факт.

### Транспорт и реальные legs

Для walking приёмка требует реальную поездку минимум с тремя POI: каждый из двух соседних legs имеет реальные duration/distance, basis=routing_provider, source и доступную geometry или navigation_url; source/units не меняются между расчётом и UI. Missing/unknown не равны unreachable и не заменяются прямой линией. Наличие known duration без distance/geometry/link позволяет ограниченный временной расчёт, но не закрывает F08.

Для car — только соответствующий mode и дорожные данные; парковка/подход не проверены без отдельного входа, предупреждение обязательно. Для public_transit — только данные реального провайдера в пределах даты/времени; нет провайдера — режим возвращает явное ограничение/unknown, без придуманных остановок/пересадок. Выбор car/PT в анкете сам по себе не доказывает поддержку рассчитанного режима. Подключение Routing API и отображение карты — Fullstack; Routing использует их проверенный результат.

## Route Assistant: конкретная схема для согласования

LLM делает только интерпретацию. Планировщик и валидатор выполняют действия; Backend владеет хранением и подтверждением. Сервис и API-ключ LLM пока не выбраны. Схема ниже независима от поставщика и не означает разрешения платного вызова.

Вход preview: `{schema_version:"0.2",route_id,base_version,poi_snapshot_id,text}`. Внутренние аргументы preferences и route_snapshot Backend загружает сам по авторизованному route_id и base_version; клиентский snapshot не является источником истины. Backend сам читает route_snapshot по авторизованному route_id, не доверяет присланному клиентом владельцу/пути. LLM получает минимальные маршрут/категории/разрешённые ID и запрос, без ключей и лишних персональных данных.

Разрешённые операции v1:

| op | Поля и проверка | Поведение |
|---|---|---|
| replace_poi | day, target_poi_id, desired_category | target должен присутствовать; replacement выбирает код через Recommendation из доступного каталога, не LLM по вымышленному имени |
| add_poi | day (nullable), poi_id из каталога | Код вставляет и перепроверяет; неизвестный ID отклоняется |
| remove_poi | poi_id | Удаление required запрещено; required-set этой операцией не меняется |
| set_day_pace | day, pace из трёх enum | Пересчитывается конкретный день с теми же required и глобальным бюджетом |
| set_meal_break | day, start_at, end_at | Явный положительный интервал в окне дня; всё затронутое расписание пересчитывается |

Слова «убери дорогие развлечения» при неизвестных ценах приводят к needs_clarification/UNKNOWN_COST, а не выбору цен LLM. «Сделай спокойнее» при нескольких днях без указания дня — уточнение, если нет явного разрешённого правила «вся поездка». Нельзя менять destination/dates/required/budget/transport произвольным patch. Для них отдельный явный пользовательский сценарий и повторная генерация; операции v1 не предоставляют свободный JSON Patch, SQL, Python или URL fetch.

LLM-ответ: `{action:"propose"|"needs_clarification"|"unsupported",operations:[],clarification:null|string}`. Неизвестные op/поля, неверные enum, лишние команды, неразрешённые IDs отклоняются до выполнения. В первой версии один запрос обрабатывается как одна атомарная транзакция всех операций: если какая-либо невалидна, proposal не применяется частично. Количественные лимиты входа/операций/token/time должны быть согласованы с выбранным API/Fullstack; не произвольные скрытые усечения.

Поток:

1. Снять авторизованный `base_version`; валидировать запрос, вызвать только согласованный LLM API с timeout.
2. Проверить структурированный ответ и все preconditions. Не выполнять instructions из названий POI/LLM/пользовательского текста как код.
3. Создать копию маршрута, вызвать разрешённые функции, пересчитать затронутые дни; перепроверить required/no-duplicates/время/дневные ограничения и **глобальный** бюджет поездки.
4. Вернуть `{proposal_id,route_id,base_version,operations,diff,candidate_route,checks,warnings,validation_status,explanation,expires_at}`. validation_status: ready_for_confirmation / needs_clarification / rejected. explanation строится по фактическому diff/checks, не по недоказанной версии LLM. Original route неизменён. Proposal с candidate_route.status=unknown допустим для подтверждения только как явно маркированный draft с показанными причинами; это не обещание выполнимости и не статус feasible. Предложение с failed обязательным ограничением не ready.
5. Confirm принимает только `{proposal_id,base_version,decision:"confirm"|"reject"}`. Backend перепроверяет владельца/версию/срок proposal и актуальность catalog/matrix, запускает повторную валидацию. Затем atomically compare-and-swap version и сохраняет candidate; stale version → VERSION_CONFLICT, никакой перезаписи новых правок. Если данные изменились — новый preview, а не скрытый пересчёт в момент подтверждения. Повторное confirm должно быть идемпотентным по proposal_id; reject ничего не меняет.

Недоступность/timeout LLM, ошибочный JSON, injection, неизвестный ID, невозможная операция и отсутствие данных возвращают отказ/уточнение и оставляют исходную поездку неизменной. Mock используется для тестов схемы, но A16/F10 закрывается только настоящим разрешённым вызовом API с проверенным результатом, без секретов в логах.

## Контрольные примеры и будущая приёмка

Все числа/ID в примерах ниже **тестовые**, не туристические факты. Эти сценарии ещё не реализованы и не прогонялись этой задачей.

| Сценарий | Вход / ожидаемое свойство |
|---|---|
| Два дня/no duplicate | Два окна 09–12, A/B по 120 мин, A→B/B→A 30 мин, balanced: active cap 126 мин в день. Required A/B размещаются в разных днях, ни один не повторяется |
| Темп влияет на нагрузку | Окно 09–15 без обеда; A/B/C по 60 мин, все переходы 10 мин. relaxed: cap 198 мин и отдых 20, intensive: 306 мин и отдых 10. Три посещения требуют 200 активных мин: relaxed не включает все, intensive может; дело не в фиксированном N |
| Граница | elapsed/active точно равны лимиту — допустимо; +1 микросекунда — отказ вставки; Fraction/int не округляются |
| Обед | Окно 09–18, fixed meal 13–13:45. Посещение 12:30–13:30 не остаётся поверх обеда, переносится целиком и день перепроверяется |
| Unknown duration | Обязательный A с null: unplaced_required содержит A, time/required unknown; нет вычисленного end_at и ложного infeasible |
| Known impossible | Required A=240 мин, единственное окно 180 мин: известная нижняя граница доказывает конфликт независимо от перестановок |
| Heuristic dead end | На малом fixture точный oracle находит решение, insertion не находит: статус unknown/SEARCH_NOT_PROVEN, а не infeasible; фиксируется limitation |
| Directed legs | A→B known 600 сек, B→A unknown: обратный leg не наследует 600; unreachable отдельно запрещает вставку |
| Часы | [] — закрыто; null — неизвестно; известные 10–12 и 14–16 не позволяют посещение 11:30–12:30 |
| Бюджет | Лимит 1000 RUB, known visits 900 и known meal 200 → сумма 1100 отвергается; meal null → unknown; 10 USD + 900 RUB не суммируются как 910 RUB |
| Реальные walking legs | Три настоящих POI, два соседних legs с провайдерскими время/расстояние/geometry-or-link/source и применимостью по времени; без этого F08 открыт |

| Assistant required | Попытка убрать required A → rejected/REQUIRED_PLACE_PROTECTED; частичной правки нет |
| Assistant conflict/error | Смена base_version, повторный confirm, reject, timeout, invalid JSON/op/ID, injection → контролируемая ошибка/идемпотентность, исходник не потерян |
| 1–3 дня, все темпы/режимы | Таблица позитивных/негативных случаев, local timezone/DST, пустой каталог, unknown legs/cost/hours, недостаточный top_k; no hidden mode conversion |

После реализации — route-validation и независимая QA-приёмка; до интеграции сравнить на малых известных наборах insertion с oracle ≤8, проверить сохранность old 0.1 suite. Внешние вызовы и их стоимость проверяются только после отдельного разрешения доступа.

## Пакет решений на одно последующее согласование

Рекомендуется утвердить **внутренний пакет R1–R5** совместно; внешние доступы E1–E3 остаются отдельными фактическими вопросами:

| Решение | Рекомендуемый ответ |
|---|---|
| R1: алгоритм | Отдельный opt-in multiday-insertion-v0.2 с required-first/rank insertion, без новой границы «не более 3 дней/8 POI всего»; heuristic failure → unknown; 0.1 сохраняется |
| R2: темп/паузы | pace-policy-v0.2: α 0.55/0.70/0.85 и rest 20/15/10 мин, active cap по доступному окну, fixed meal/blocked intervals только явные; числа — экспериментальная гипотеза, проверяемая пользовательскими тестами |
| R3: неизвестные/оценки | strict default, не заполнять текущие 2058 длительностей; отдельно разрешать только проверяемый expert_estimate overlay с basis/автором/методикой; недостающие цены/часы дают unknown |
| R4: контракт | Новый opt-in Routing 0.2 с days/context, transport geometry/link/time validity, отдельными opening/cost/duration sidecars и provenance; старые 0.1 payload не менять; точная интеграционная схема согласуется с Architect/Fullstack |
| R5: Assistant | Только пять описанных операций, атомарный preview, повторная валидация и confirm с base_version/CAS; required защищены; неизвестные данные → уточнение/предупреждения, LLM не пишет БД |
| E1: реальная навигация | Fullstack подтверждает провайдера, режимы, доступ/права, формат и применимость направленных duration/distance/geometry-or-link |
| E2: LLM | Владелец выбирает доступный API, предел расходов, секрет/политику данных; затем один реальный разрешённый вызов, не mock |
| E3: реальные сведения | Data + владелец утверждают источник/методику длительностей, стоимости и часов; правила mixed-source sidecars и конкретный реальный демонстрационный набор |

Это предложение не закрывает A10–A19. После утверждения — согласовать файлы реализации/контракта с Architect, затем Routing реализует модель и операции, Fullstack подключает источники/хранение/UI, QA независимо проверяет результат. Статусы `TASKS.md` не менялись.
