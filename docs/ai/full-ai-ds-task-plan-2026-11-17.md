### Конкретный рекомендуемый внутренний пакет R1–R5

Это готовое предложение для одного последующего решения владельца. Оно согласовано между документами агентов, но **ещё не утверждено пользователем и не реализовано**. Полные формулы/схемы/контрольные примеры — [Routing](routing-completion-proposal-2026-11-17.md), совместимость и транспорт — [Architect](integration-decision-pack-2026-11-17.md).

| Решение | Что предлагается утвердить |
|---|---|
| R1 — дни | Отдельная `multiday-insertion-v0.2`: required сначала (наиболее ограниченный по допустимым вставкам, затем ID), вставка во все дни/позиции по приращению времени переходов; optional затем по rank. ID не повторяются. Неудача эвристики = unknown/SEARCH_NOT_PROVEN, infeasible только доказанный конфликт. Нет нового бизнес-лимита 3 дня/8 POI; прежний exact ≤8 остаётся контрольным oracle |
| R2 — темп | `pace-policy-v0.2`: relaxed/balanced/intensive = доля доступного окна 0.55/0.70/0.85 и отдых между посещениями 20/15/10 минут. Активный лимит = доля × (дневное окно − явно заданные обед/blocked intervals), без float-округления и двойного вычитания пауз; явный меньший cap имеет силу. Это экспериментальные коэффициенты, подлежащие проверке, а не научно доказанные нормы |
| R3 — неизвестное | `unknown_duration_policy=strict`: существующие null не заполнять, не выдавать timestamps. При отдельном одобрении методики допустим версионированный duration sidecar с basis=expert_estimate, автором/датой/доказательством, без изменения raw; показывать приблизительность. Неизвестные часы/затраты сохраняют unknown. Одновалютная известная сумма — нижняя граница бюджета, не подтверждение полного соблюдения |
| R4 — контракт | Явный opt-in Routing 0.2 при сохранении 0.1: days на каждую дату, policy versions, duration/cost/opening sidecars с provenance, directed matrix с применимостью/geometry/HTTPS navigation_url, сохранение полей legs, diagnostics и snapshot ID. Не менять старые POI/schema_version без адаптера/валидации. Часы 0.1 остаются null; нормализованные интервалы дат обрабатывает только новая согласованная схема |
| R5 — Assistant | Allowlist `replace_poi`, `add_poi`, `remove_poi`, `set_day_pace`, `set_meal_break`. Только атомарный propose→пересчёт/валидация→preview→confirm по base_version, required защищены. Вход route_id/base_version/poi_snapshot_id/text; backend читает авторизованный snapshot. candidate_route.status отделён от validation_status предложения. Повторный confirm идемпотентен, stale version/невалидный LLM/ошибка не меняют исходник; unknown допускается только явно как draft |

Внешние факты отдельны от R1–R5: реальный backend-стек и payload напарника; провайдер/доступ/права настоящих переходов; доступный LLM API и разрешённый бюджет/секрет/данные; допустимые источники реальных рейтингов/цен/часов/длительностей и разметка unusual. Согласование алгоритма не создаёт эти данные и доступы. Для полного F04 останется A03/A09 даже после утверждения R1–R5.

3. Fullstack: подтвердить стек/входы анкеты/способ вызова AI/DS и поставку реальной направленной матрицы с геометрией/ссылкой. Нет ответа — нет заявления об интеграции.
