# TripWise — источники туристических данных

Зафиксировано по решению владельца AI/DS 17 ноября 2026 года. Документ определяет источники для глобального развития платформы и правила работы с данными. Перечисление источника не означает, что он уже подключён, проверен для каждого города или предоставляет все поля для каждого объекта. Подключение API этим документом не выполняется.

## 1. Основные источники

| Источник | Назначение в TripWise | Ссылка |
|---|---|---|
| OpenStreetMap (OSM) | Координаты, названия, адреса, категории; при наличии — часы работы и сайты объектов | [openstreetmap.org](https://www.openstreetmap.org/) |
| Geoapify Places API | Поиск туристических объектов и заведений по всему миру, географические данные и категории | [geoapify.com](https://www.geoapify.com/) |
| OpenTripMap API | Достопримечательности, описания, категории и туристическая значимость объектов | [dev.opentripmap.org](https://dev.opentripmap.org/) |
| Foursquare OS Places | Дополнительная глобальная база кафе, ресторанов, магазинов и других заведений | [Foursquare OS Places](https://opensource.foursquare.com/os-places/) |
| Wikidata | Структурированные сведения, культурные и исторические факты для карточек достопримечательностей и Premium AI-гида | [wikidata.org](https://www.wikidata.org/) |
| Wikipedia | История, описания, культурные и исторические факты для карточек достопримечательностей и Premium AI-гида | [wikipedia.org](https://www.wikipedia.org/) |

Foursquare OS Places и коммерческий Foursquare Places API — разные источники и условия доступа. Доступность данных одного продукта не подтверждает доступность тех же полей в другом.

Wikidata и Wikipedia также рассматриваются отдельно при проверке лицензий, атрибуции и способов повторного использования. Тексты и факты для AI-гида проверяются по исходным материалам; наличие генерации не подтверждает достоверность содержания.

## 2. Пользовательские рейтинги и внутренние показатели

- Не выдумывать пользовательские оценки и число отзывов.
- Если достоверного пользовательского рейтинга нет, сохранять `rating = null`. Не подменять неизвестную оценку нулём.
- Различать пользовательский рейтинг, туристическую значимость OpenTripMap и внутренний TripWise Score. Туристическая значимость и внутренняя оценка не записываются как пользовательский рейтинг.
- TripWise Score — обозначение внутренней оценки/приоритета рекомендаций, а не утверждённая этим документом новая формула. Текущая модель и её выходной `score` остаются в рамках согласованного контракта.
- Google Places API и коммерческий Foursquare Places API рассматривать как дополнительные источники пользовательских рейтингов на будущее. До использования проверить стоимость, доступность нужных полей, лицензии, атрибуцию, правила хранения и показа.
- Не считать количество отзывов, посещаемость и рейтинг одним показателем. Семантику и сопоставимость признаков фиксировать до использования в модели.

## 3. Глобальная работа и совместимость

1. Целевая архитектура не привязывается к конкретной стране. Москва и Санкт-Петербург могут использоваться как демонстрационные города, но не задают границы платформы.
2. Данные каждого источника приводятся к единому формату POI по [контракту 0.1](contracts-v0.1.md). Учитываются различия названий, языков, категорий, валют и часовых поясов.
3. Источниковые форматы обрабатываются отдельными адаптерами загрузки и нормализации. Добавление источника не должно требовать переписывания Recommendation и Routing, если выход соответствует утверждённому контракту.
4. Сохраняются источник, идентификатор объекта в источнике, ссылка на исходную запись при наличии, время получения и сведения о проверке. Время загрузки не приравнивается к проверке фактов; неизвестное время проверки остаётся `null`.
5. Реальные, синтетические и приблизительные данные явно различаются. Демонстрационный fixture не считается реальным набором.
6. Если источник не предоставляет сведения, сохраняются предусмотренные контрактом `null` и предупреждения. Не угадывать категории, координаты, цены, длительности и часы работы.
7. Наличие данных в источнике не разрешает молча расширять контракт. Например, в версии 0.1 `opening_hours` допускает только `null`; полученные исходные часы можно сохранять в raw в пределах условий источника до согласования их обработки.

Текущий контракт 0.1 предполагает один источник на набор. Этот документ не отменяет это ограничение. Сопоставление и обогащение POI из нескольких баз, включая отдельный источник рейтинга, требуют предварительного согласования происхождения данных на уровне полей или отдельного слоя обогащения.

## 4. Проверка источника перед подключением

Для каждого API или набора данных Data Agent фиксирует:

- официальную документацию и дату проверки;
- покрытие нужных стран и городов, доступность требуемых полей;
- условия доступа, необходимость ключа, бесплатные лимиты, тарифы и ограничения запросов;
- лицензию, обязательную атрибуцию, правила хранения, кэширования, изменения, публикации и объединения данных;
- правила обновления, происхождение и ограничения актуальности;
- mapping категорий и полей в контракт, пропуски и ограничения пригодности для рекомендаций и маршрутизации.

Не предполагать, что публичный API, бесплатный лимит или открытый доступ разрешают произвольное постоянное хранение и публикацию. Выбор новых сервисов, расходов, зависимостей и изменения интерфейсов согласовываются по AGENTS.md.

## 5. Качество, дубликаты и передача компонентам

- Применять `data-poi-pipeline` при загрузке/нормализации и `data-poi-quality-check` перед передачей набора алгоритмам.
- Проверять структуру, типы, идентификаторы, координаты, категории, пропуски и происхождение данных.
- Идентификаторы разных источников хранить с явным пространством имён. Одинаковое название не доказывает, что записи описывают одно место или один филиал.
- Выявлять подтверждённые и возможные дубликаты отдельно. Не удалять исходные записи и не объединять спорные совпадения автоматически.
- Хранить причины отклонений и предупреждения в отчёте качества. Пригодность для рекомендаций не означает пригодность для маршрутизации.
- Передавать Recommendation и Routing данные в согласованном формате, не скрывая неизвестные сведения и ограничения источника.

## 6. Границы решения

Существующий код, математические модели, сроки и другие требования проекта не изменяются. Реальная загрузка и интеграция перечисленных API выполняются отдельными задачами после соответствующих проверок и согласований. Premium AI-гид для 3–5 мест остаётся дополнительной задачей после стабилизации основного MVP.
