# Подключение AI/DS к backend TripWise

Состояние проверено 17 ноября 2026 года по коду. Документ описывает готовые Python-интерфейсы и предложения по их подключению. Он не утверждает новые HTTP-эндпоинты и не изменяет [контракт 0.1](contracts-v0.1.md) или [дополнение Routing](routing-contract-v0.1.md).

## 1. Что существует

В этой копии репозитория есть локальные Python-модули Data, Recommendation и Routing, JSON-примеры, CLI и автоматические тесты. Код backend, frontend, БД, HTTP-сервера и карты не обнаружен. Его состояние у напарника нужно подтвердить отдельно. Наличие работающего локального алгоритма не означает готовность веб-интеграции.

Среда: Python 3.11+, стандартная библиотека, доступная база часовых поясов `zoneinfo`. Уже установленный и использованный в проекте интерпретатор: `C:/msys64/ucrt64/bin/python.exe`. Его абсолютный путь относится только к текущему компьютеру, а не к deployment-контракту.

## 2. Готовые интерфейсы

| Интерфейс | Вход | Результат и ошибки |
|---|---|---|
| `ai_ds.data.load_pois(path)` | Путь к UTF-8 JSON | Декодированный JSON; имя функции не ограничивает содержимое массивом. Возможны `OSError`/`ValueError`, в том числе повреждённый JSON и NaN/Infinity |
| `ai_ds.data.validate_poi(poi)` | Одна запись | Массив ошибок полей; `[]` означает структурное соответствие, не проверку фактов |
| `ai_ds.data.process_pois(records)` | Массив POI | `(accepted, report)`. Некорректные записи отделяются с причинами. Ошибка формата набора/смешивание источников — `ValueError` |
| `ai_ds.recommendation.validate_preferences(profile)` | UserPreferences | Массив ошибок профиля; не делает ранжирование |
| `ai_ds.recommendation.recommend(preferences, pois, *, evaluated_at=None)` | Профиль и полный POI-набор | Recommendation `schema_version=0.1`, `model_version=lexicographic-v0.1`; ошибки профиля/POI — `RecommendationError` с `.response()` |
| `ai_ds.routing.build_route(preferences, pois, recommendation, travel_times, routing_context)` | Профиль, полный набор, снимок ранжирования, направленная матрица и контекст дня | TripRoute `model_version=day-enumeration-v0.1`; ошибки Routing — `RoutingError` с `.response()`, ошибки профиля/POI — `RecommendationError` |

Набор передаётся из серверного источника данных, а не считается достоверным только потому, что пришёл с клиента. Все ID профиля, рекомендации и матрицы относятся к одному набору. Исходные записи не меняются функциями рекомендаций и маршрутизации.

`process_pois` может вернуть частично принятый массив: вызывающая сторона должна явно обработать отклонения. `recommend` повторно валидирует весь свой вход и не выдаёт частичную рекомендацию при структурных ошибках. Не следует незаметно потерять обязательный ID при очистке.

## 3. Последовательность вызовов

1. Data отдельно загружает/нормализует источник и готовит проверенный набор с отчётом. Синтетические и реальные наборы не смешиваются; в 0.1 используется один источник на набор.
2. Backend выбирает набор по стране/городу, получает профиль из анкеты и передаёт `preferences, pois` в `recommend`.
3. Backend/Fullstack предоставляет направленные `travel_times` с явным источником и типом расчёта. Каталог POI сам по себе не предоставляет времена перемещений.
4. Вызывается `build_route` с **полным** набором, а не только top-K: обязательное место может отсутствовать в выдаче рекомендаций.
5. Backend возвращает структурированный результат и предупреждения интерфейсу, не преобразуя `unknown` в успешную проверку ограничений.
6. Fullstack отвечает за карту и сохранение/повторное открытие. Эти функции пока не реализованы в AI/DS-модулях.

Минимальный пример вызова готовых функций, без нового HTTP API:

```python
from ai_ds.data import load_pois, process_pois
from ai_ds.recommendation import recommend
from ai_ds.routing import build_route

pois, quality = process_pois(load_pois(poi_path))
# Отклонённые записи и обязательные ID должны быть рассмотрены вызывающим кодом.
recommendation = recommend(preferences, pois)
route = build_route(preferences, pois, recommendation,
                    scenario['travel_times'], scenario['routing_context'])
```

`poi_path`, `preferences` и `scenario` в примере — данные адаптера, не новые глобальные настройки проекта. Пример не заменяет обработку ошибок.

## 4. Форматы и ограничения на границе

- Профиль использует восемь согласованных кодов категорий, 1–2 основных интереса, дополнительные без пересечения. Поля и правила `null` заданы исходным контрактом.
- Recommendation содержит упорядоченные `items`, причины выбора, `required_poi_ids`, `excluded`, предупреждения и `constraint_checks`. Порядок выдачи — не порядок посещения.
- Routing принимает один день; объединение top-K и обязательных ID — не более восьми кандидатов. Превышение возвращает ошибку, не скрытое усечение.
- `routing_context`: начало/конец дня с часовым смещением, `endpoint_policy=first_last_poi`, объявленный темп, явные активный лимит и отдых. Смещение проверяется относительно `preferences.timezone`.
- Матрица направленная: A→B не задаёт B→A. `known`, `unknown`, `unreachable` и отсутствующая пара различаются. Неизвестное время не заменяется нулём.
- Снимок Recommendation валидируется по устойчивым полям и структуре. Динамические предупреждения не сравниваются с заново полученными. Вызывающая сторона должна формировать новый снимок при изменении исходных данных.
- TripRoute содержит дни, посещения, переходы, перерывы, невключённые обязательные ID и результаты проверок. Геометрия/навигационная ссылка сейчас `null`: существующий Routing не переносит их из провайдерского ответа.
- Общий `status=unknown` у рассчитанного маршрута не равен ошибке сервера. Временная проверка может быть `passed`, пока часы работы `unknown`, а бюджет `not_checked`.
- `infeasible` означает доказанный конфликт только в пределах заданных кандидатов и лимитов. Он не доказывает невозможность любой поездки по городу.

## 5. Ошибки и локальный CLI

| Команда | Успех | Ошибки |
|---|---|---|
| `python -m ai_ds.data --input ... --output ... --report ...` | Код 0; массив и отчёт в файлах, сводка в stdout | Код 1 — обработано с отклонениями; код 2 — ошибка чтения/формата/записи. stderr сейчас текстовый, не общий JSON-конверт |
| `python -m ai_ds.demo --pois ... --preferences ...` | Код 0, JSON Recommendation в stdout | Код 1 и JSON `VALIDATION_ERROR`; код 2 и JSON `INPUT_ERROR` в stderr |
| `python -m ai_ds.routing --pois ... --preferences ... --scenario ...` | Код 0, JSON TripRoute в stdout, в том числе при `unknown`/`infeasible` | Код 1 и JSON `ROUTING_VALIDATION_ERROR` либо `VALIDATION_ERROR`; код 2 и JSON `INPUT_ERROR` в stderr |

Recommendation и Routing CLI явно выводят UTF-8 в stdout/stderr. Ошибки аргументов `argparse` возвращаются отдельно как usage и код 2, а не JSON. Data CLI — инструмент подготовки наборов, не готовый транспортный интерфейс backend. Его пара output/report не записывается транзакционно.

Преобразование доменных ошибок в HTTP-статусы, лимиты времени/размера запроса и формат внешнего error response должен утвердить Fullstack вместе с AI/DS. Сейчас ни один HTTP endpoint не объявлен существующим или согласованным.

## 6. Варианты подключения — для решения команды

| Вариант | Когда применять | Особенности |
|---|---|---|
| Импорт Python-функций | Backend уже на совместимом Python | Минимум инфраструктуры, проще передавать объекты и доменные ошибки |
| Python subprocess через существующие CLI | Backend на другом языке, нужен быстрый прототип | Передавать аргументы массивом, не через shell; использовать серверные пути/временный каталог, timeout и UTF-8, разбирать exit code и оба потока |
| Отдельный HTTP-сервис | Позже, если deployment действительно требует отдельного процесса/масштабирования | Потребует нового API, жизненного цикла и, вероятно, зависимости; сейчас не выбран и не реализован |

Рекомендация: сначала узнать стек напарника. Для Python backend — прямой импорт; для другого стека на ближайшее демо — согласовать тонкий subprocess-адаптер. Не вводить отдельный сервис до подтверждения необходимости.

При subprocess нельзя принимать произвольные пути, имена модулей или исполняемые команды из пользовательского запроса. Ключи провайдеров принадлежат серверному окружению и не попадают в JSON-ответ, Git или сообщения об ошибках. Хранение raw/провайдерских payload зависит от условий источника; право на кэш не предполагается автоматически.

## 7. Воспроизводимое демо существующего кода

Из корня репозитория на настроенном Python:

```powershell
python -B -m ai_ds.demo --pois data/processed/pois.synthetic.validated.json --preferences examples/preferences/history.json
python -B -m ai_ds.demo --pois data/processed/pois.synthetic.validated.json --preferences examples/preferences/nature.json
python -B -m ai_ds.routing --pois data/processed/pois.synthetic.validated.json --preferences examples/preferences/history.json --scenario examples/routing/day.synthetic.json
python -B -m unittest discover -s tests -v
```

На этом компьютере вместо `python` можно явно использовать `& 'C:/msys64/ucrt64/bin/python.exe'`. Демонстрационные POI и времена переходов синтетические. Происхождение нельзя скрывать при показе. Для контрольных top-5 и расписания см. [Recommendation](recommendation-baseline.md) и [Routing](routing-baseline.md). Документ проверен чтением кода и путей; полноценная интеграция с backend не выполнялась.

2. Какие реальные входы анкеты и форматы API/БД уже существуют? Как сопоставить их без дублирования модели?
3. Кто и как выбирает набор/версию POI, хранит отчёты, snapshots и обновляет их?
4. Кто предоставляет Routing API, ключи, направленную матрицу, геометрию и внешнюю навигацию? Как сообщаются ошибки и устаревшие данные?
5. Как UI показывает `unknown`, невключённые обязательные места и непроверенный бюджет, не обещая выполнимость?
6. Какой минимальный сценарий интегрируем первым и кто владеет каждым небольшим PR?
7. Какие дополнения нужны для многодневности, дневных окон, питания и автоматической модели темпа? Их модель ещё должна быть утверждена.
8. Какой LLM-провайдер/бюджет/политика данных допускаются для Route Assistant? Какие структурированные операции, подтверждение и хранение версий нужны?

Пользователь подтвердил, что интервью есть; путь к материалам и выводы на момент этой спецификации не получены. Их отсутствие в этой копии нельзя считать отсутствием проведённых интервью.

Из долгов 3–16 ноября нельзя закрыть одним подключением кода: использование подтверждённых выводов интервью/пользовательской разметки, многодневную модель, реальное пешеходное время и фактическую LLM-интеграцию. Они требуют отдельных входных материалов/решений и проверяемых результатов. Синтетическая демонстрация не является их заменой.

## Актуальное дополнение 18 ноября

R1–R5 реализованы отдельной версией 0.2, контракт 0.1 сохранён. Напарник адаптируется к опубликованному AI/DS-контракту: ожидание его стека больше не блокирует нашу библиотеку. Для подключения использовать ai_ds/README.md, routing-contract-v0.2.md и route-assistant-implementation-2026-11-18.md. Предпочтительны прямой Python-импорт или CLI через shell=False в соответствии со стеком backend. Новый HTTP-сервис не добавлялся.

Вся регрессия изолированной копии: 188/188. Контракт включает многодневность, темп, бюджет/часы, directed legs и пять операций Assistant. Production-авторизация, атомарное постоянное хранилище и frontend принадлежат Fullstack. Reference InMemoryRouteStore не сохраняет поездку после перезапуска. Неизвестные факты и expert_estimate показываются пользователю как draft/unknown, а не как проверенная поездка.
