## Как работает цепочка

1. HTML показывает форму. JavaScript проверяет заполнение и отправляет JSON на POST /api/auth/register.
2. Python заново проверяет почту, длину и совпадение паролей. Проверка браузера сама по себе не защищает сервер.
3. Почта нормализуется: удаляются крайние пробелы, регистр понижается. Уникальность обеспечивает ограничение UNIQUE в SQLite, включая одновременные запросы.
4. scrypt вычисляет хеш пароля с новой случайной солью для каждого аккаунта. Исходный пароль не записывается в БД или журналы.
5. Сервер создаёт случайный токен сеанса. В БД записывается только SHA-256 токена; браузер получает сам токен через HttpOnly cookie. SHA-256 используется для случайного токена, а не вместо scrypt для пароля.
6. Браузер открывает /trips. Сервер сверяет токен и срок; без входа перенаправляет на форму.
7. JavaScript страницы запрашивает GET /api/auth/me и отображает почту через textContent. Данные берутся из текущего сеанса, а не выбранного клиентом user_id.
8. При выходе сервер удаляет текущий сеанс и очищает cookie; старый токен после этого не работает.

Функции database/init_database отвечают за SQLite; hash_password/verify_password — за пароль; current_user — за поиск пользователя по действующему сеансу; обработчики register/login/logout — за действия пользователя. Подробные технические параметры перечислены в README. Соль не секрет: она делает результаты одинаковых паролей разными. Хеш не является шифрованием с ключом для расшифровки.

## Проверки

На Python 3.13 / macOS выполнено 13 интеграционных unittest-тестов по настоящему HTTP с отдельной временной SQLite-базой:

- Регистрация, cookie HttpOnly / SameSite=Lax и открытие защищённой страницы.
- Повторная регистрация той же почты с другим регистром и пробелами.
- Некорректная почта, короткий/слишком длинный пароль, несовпадающий повтор; ответы не возвращают входной пароль.
- Неверный пароль и неизвестный аккаунт: одинаковое сообщение, без открытия доступа.
- Замена токена при повторном входе и отзыв текущего токена при выходе.
- Отсутствующий, подменённый и просроченный сеанс.
- Разделение двух аккаунтов: каждый получает собственную почту.
- В БД хранится scrypt-хеш пароля и хеш токена, а не исходные значения.
- Запросы с чужим/отсутствующим Origin отклоняются.
- После 30 попыток в минуту на IP возвращается 429 с Retry-After.
- Перезапуск тестового сервера сохраняет пользователя и действующий сеанс; повторный вход после выхода работает.
- Файлы backend, .git и runtime не выдаются через статическую раздачу.

Команда: .venv/bin/python -m unittest discover -s tests/fullstack -v.

Первый прогон: 13/13 прошли, но Python сообщил о незакрытых соединениях SQLite в самих тестах и незакрытом объекте HTTPError. Исправлено управление ресурсами в тестовом коде: соединения закрываются в finally, HTTPError закрывается явно. Повторный прогон с -W error::ResourceWarning: 13/13, OK, без указанных предупреждений. Это исправление тестовой инфраструктуры, а не доказательство устранения пользовательской ошибки готового туристического сценария.

Дополнительно через интерфейс настоящего браузера на отдельном сервере 8771 и временной тестовой базе: регистрация вымышленной почты → переход в «Мои поездки» с нужной почтой → выход → ошибка неверного пароля → вход с правильным паролем. Тестовый сервер остановлен после проверки. Пользовательский сервер на 8765 не останавливался: ему нужен ручной перезапуск для загрузки нового Python-кода. Автоматические тесты также останавливают только собственные процессы, временная БД не совпадает с пользовательской.

Применён процесс проектной инструкции qa-integration-check: задана область проверки аккаунтов, проверены ошибки и перезапуск, исправлены предупреждения и выполнен повторный прогон. Отдельный независимый QA-субагент не запускался, сторонний MCP не использовался. Не выдавать это за доказательства их применения.

## Ограничения

Нет подтверждения владения почтой, восстановления пароля, удаления аккаунта, многопользовательского публичного развёртывания или общей базы для разных устройств. Поддержан ограниченный формат ASCII-почты. Текущий лимит по IP рассчитан на локальную проверку, а не на сеть общего доступа или несколько серверов.

Cookie без Secure на локальном HTTP; при HTTPS-запросе Secure включается. Работа HTTPS за прокси и публичное размещение не проверялись. Срок сеанса — семь суток. Выход отзывает только текущий сеанс, а не все устройства. Закрытие браузера не обязательно завершает сеанс. Локальные исключения пользователя из-за неверной конфигурации БД/порта не исправляются удалением данных.

Безопасность публичного сервиса не заявляется. Фактически проверены перечисленные сценарии; это не исчерпывающий аудит. Отображение на широком экране отдельно не проверялось, ручной браузерный прогон выполнен в доступной узкой области. Восстановление соединения и таймаут интерфейса предусмотрены сообщениями, но отключение сервера во время регистрации вручную не воспроизводилось.

Источники решений: [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) — scrypt N=2^15, r=8, p=3; [Starlette Responses](https://starlette.dev/responses/) — параметры cookie.
