## Исходное состояние и цель

Изучены AGENTS.md, `.codex/config.toml`, все шесть существующих `.codex/agents/*.toml`, docs/fullstack/AGENT_BRIEF.md, PRODUCT_DECISIONS_2026-11-17.md, журнал 00_WORKFLOW.md и analyst-requirements/SKILL.md. Текущая работа ведётся в feature/fullstack поверх 708a762 с незакоммиченными анкетой и исправлением QA-01; их нельзя сбрасывать или переписывать при настройке ролей.

В текущем config зарегистрированы analyst, architect, qa_agent и три AI/DS-исполнителя. analyst, architect и qa_agent уже общие для двух участников — утверждение «все существующие роли только напарника» неточно. Не хватает именно двух профильных исполнителей Fullstack. Нужно добавить их, сохранив общих агентов и направления AI/DS. Задача не требует нового стека, платной модели, дополнительных серверов или переписывания приложения.

## Минимальный состав ролей

| Роль | Владелец и результат | Граница с другими ролями |
|---|---|---|
| frontend_agent | Участник 2: страницы, формы, доступность и поведение интерфейса, анкета, расписание, карта, отображение переходов, чат и подтверждение правок | Получает JSON/API от backend_agent; не пишет алгоритмы ранжирования/оптимизации, не хранит пароли/ключи, не создаёт собственные источники POI |
| backend_agent | Участник 2: HTTP/API, серверная валидация, SQLite, аутентификация, изоляция пользователей, сохранение и загрузка, адаптеры Routing API и модуля AI/DS | Интегрирует согласованные публичные функции напарника; не дублирует его математическую модель, не заменяет её заглушкой и не переписывает AI/DS |
| analyst | Общая роль: требования, маленькие задачи, критерии, приоритеты и передача | Не создавать отдельного fullstack_analyst; профильные исполнители не утверждают новые требования |
| architect | Общая роль: границы, интерфейсы, API/JSON, изменения схем и совместимость | Не создавать отдельного fullstack_architect; спорные контракты передавать архитектору и команде |
| qa_agent | Общая роль: независимая проверка и повторный тест исправления | Собственные тесты разработчика необходимы, но не заменяют независимое заключение QA |

Общие роли не становятся подчинёнными frontend/backend и не заменяются их копиями. Оркестратор фактически передаёт им задания и результаты. Если задача содержит UI и сервер, он разделяет её по согласованному интерфейсу; параллельные исполнители не изменяют один файл.

## Обязательные инструкции обоих исполнителей

Перед задачей читать AGENTS.md, актуальные требования и результат отдельного аналитика/проектировщика, проверять структуру, Git-ветку и локальные изменения. Работать в feature/fullstack, не создавать новый репозиторий, не выполнять git init, reset --hard, принудительный push, автоматическое объединение веток или удаление чужого кода. Коммит/push выполняются в рамках адресного поручения, с пояснением каждой команды; не считать сохранение файла коммитом или коммит публикацией.

Пользовательница — начинающая студентка на Mac. Выполнять небольшие понятные срезы; объяснять назначение изменённых файлов, основные функции и путь данных. Давать короткую практику, способ проверить её и вопрос на понимание, не вводить десятки новых технологий. Основной чат объединяет сообщения и ведёт обучение, чтобы два исполнителя не заваливали участницу параллельными заданиями и вопросами. Рутинные согласованные исправления выполняются самостоятельно; изменение требований, архитектуры, общего контракта, новые зависимости/платные API — через команду.

Не читать runtime/, .env, реальные учётные записи и секретные настройки без необходимости и отдельного разрешённого объёма. Для тестов — временная SQLite-база, вымышленные пользователи, собственный свободный порт; не останавливать сервер участницы и не менять её базу. Не записывать пароли/токены в отчёт, URL или localStorage. Отдельно отмечать ограничения локального HTTP и не объявлять публичное развёртывание безопасным без проверки.

После реализации передать QA требования, список файлов, команду запуска/проверки, реальные результаты и непроверенные сценарии. Сообщать «написан тест», «запущен и прошёл» и «независимо перепроверен» как разные факты. Любой найденный дефект получает воспроизведение; исправление возвращается отдельному QA на ретест. Не объявлять передачу по одному лишь подготовленному промпту.

## Специальные требования frontend_agent

- Проверять поля в браузере для удобства, признавая обязательность независимой серверной проверки. Не строить защиту аккаунта только на скрытых кнопках.
- Разделять пустое состояние, загрузку, успех, отказ, конфликт версии, смену аккаунта и потерю соединения. Не писать «сохранено» без подтверждения сервера и не стирать локальные правки молча.
- Сохранять исправление QA-01: отправлять первоначальный контекст владельца формы, не заменять его автоматически после смены аккаунта; существующие тексты повторного входа и поведения проверять через согласованный контракт.
- Отображать только полученные POI, расписание, время/расстояние/источник и неопределённость. Линия между маркерами не становится реальным пешим маршрутом. Не выдумывать пересадки/повороты и не выдавать синтетику за реальную навигацию.
- Чат показывает предложение изменения до подтверждения. Неподтверждённая правка не меняет сохранённый маршрут.
- В рамках задачи проверять доступность управления с клавиатуры, подписи полей, ясные ошибки и ширины экрана, которые реально просмотрены. Не заявлять браузерную проверку на основании чтения HTML.

## Специальные требования backend_agent

- Валидировать типы, смысл и ограничения на сервере; права владельца получать из аутентифицированного сеанса, не из произвольного user_id в теле.
- Обеспечивать сохранность записей и версий, безопасное изменение схем без удаления пользователей/черновиков, явные ошибки и ограничения. Сохранение анкеты не выдавать за сохранение маршрута.
- Для интеграции получать согласованный JSON/API-контракт, сверять текущие возможности AI/DS и вызывать его публичный интерфейс. Не превращать one-day baseline в многодневный изменением подписи UI.
- Routing adapter подключает выбранный реальный провайдер и нормализует полученные расстояния/время/геометрию/ошибки. Выбор POI, их ранжирование, оптимизация порядка и математические правила времени остаются у AI/DS. Пересечение границ обсуждается с architect и владельцами.
- Секреты внешних API остаются на сервере, обращения имеют таймаут и обработку отказа; платные запросы не выполнять без разрешения. LLM-провайдер преимущественно выбирается Участником 1; backend отвечает за согласованную интеграцию, а не за самовольную замену модели.
- Тестировать реальные HTTP/SQLite-взаимодействия там, где это необходимо: изоляцию двух пользователей, перезапуск, ошибки входа/контракта, конфликт и смену владельца. Заглушки внешних сервисов явно обозначать и не считать доказательством живого вызова.

Первоначальная разработка не велась через отдельных исполнителей; отдельная цепочка началась с текущего анализа/исправления. Новые конфигурации не должны переписывать эту историю.

Генерация маршрута, карта, пешеходная Routing-интеграция, реальный каталог обязательных мест и AI-редактирование в текущей Fullstack-ветке не готовы. Группа/единица бюджета, transport_modes и многодневные окна анкеты ещё не согласованы с единичным transport и однодневным baseline напарника. Начало/конец дня по отелю отложено пользователем. Новым ролям запрещено молча утверждать эти решения или менять общий AI/DS-контракт.

Файл TOML, успешный его разбор и реальный запуск отдельного агента — три разных результата. Имя задачи в инструменте делегирования само по себе не загружает локальный TOML. После добавления ролей нужно проверить обнаружение в новом сеансе/доступной среде и, если автоматическое обнаружение не подтверждено, честно передавать явное чтение соответствующей инструкции. Пробный запуск должен действительно вернуть результат отдельного исполнителя. Для MCP нужны название стороннего сервера, реальный инструмент, параметры без секретов и полученный результат; конфигурация/текстовое описание не заменяют вызов. Новый этап настройки не доказывает MCP.

Сейчас авторизовано создание двух ролей, поэтому собственный скилл Участника 2 предлагается отдельным следующим шагом, а не скрытой частью настройки конфигов. Подходящий кандидат — повторяемая проверка изменения Fullstack-сценария: требования → права/контракт → UI/API/SQLite → воспроизведение → отчёт и передача QA. Конкретное имя, область и содержимое нужно сформулировать по реальному упражнению, затем создать и действительно применить. Уже существующие analyst-requirements и qa-integration-check можно применять по назначению, но нельзя объявлять их авторской работой Участника 2. До создания/загрузки нового SKILL.md не указывать его как уже доступный.

## Критерии завершения настройки ролей

1. Есть две адресные конфигурации frontend_agent и backend_agent, связанные с config, с совпадающими именами и существующими путями.
2. Сохранены все шесть прежних регистраций и три AI/DS-конфигурации без переписывания. Общие analyst/architect/qa не дублируются.
3. Зоны файлов, работа с шаблонами backend/pages и общими тестами явно разделены; порядок обучения, Git, данных, тестов и передачи QA присутствует в обеих инструкциях.
4. Не изменены роли напарника, технологии приложения и его данные. Настройка не ломает незакоммиченный срез анкеты.
5. Устаревшие утверждения «frontend/backend не зарегистрированы» адресно согласованы с новым состоянием в затронутых общих инструкциях; историю первоначального отсутствия ролей сохранить как историю, не превращать в текущий факт.
6. Синтаксис/ссылки проверены; доступность и хотя бы безопасный отдельный пробный запуск каждой роли проверены фактически либо ограничение среды явно зафиксировано.
7. Есть независимое QA-заключение по конфигурации и краткий журнал фактической передачи. Создание своего скилла и сторонний MCP не засчитаны автоматически.
