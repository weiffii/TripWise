## Предложенная совместимая детализация для исполнителей

Не требуется новый сервис, библиотека, таблица или платный API. Существующий отдельный Fullstack-черновик не превращается в согласованный контракт AI/DS.

```json
{
  "schema_version": "fullstack-draft-0.1",
  "travelers": 4,
  "traveler_counts": {"adults": 2, "children": 1, "seniors": 1},
  "budget_amount": "15000.00",
  "budget_currency": "RUB",
  "budget_basis": "per_person",
  "budget_scope": "trip_food_and_entertainment"
}
```

Показан только изменяемый фрагмент полного запроса. Предложенный первый список валют: RUB, USD, EUR, CNY. Бюджет хранится **в исходной выбранной валюте**; автоматического обменного курса и конверсии нет. Переключение валюты меняет единицу введённой суммы, не обещает её пересчёт. Указание «на человека» одинаково применяется ко всем введённым путешественникам; возрастные скидки не рассчитываются. В сводке отображать выбранную валюту, состав и итог компании.

`traveler_counts` содержит строго целые неотрицательные adults/children/seniors, без неизвестных ключей. Каждое число не больше текущего технического предела 100; сумма от 1 до 100 и совпадает с существующим `travelers`. Значения bool, дроби, строки и отрицательные числа сервер отклоняет. Форма считает общий `travelers` автоматически; второй редактируемый общий счётчик не нужен. Возрастные пороги, правила допуска детей и влияние возраста на алгоритм не утверждены: нельзя придумывать диапазоны и автоматически менять темп.

Старые черновики и старые HTTP-клиенты с отсутствующим `traveler_counts` поддержать без потери данных: техническое заполнение adults=travelers, children=0, seniors=0. Это **не подтверждённые сведения о фактическом возрасте** старой группы, состав можно исправить в анкете. Явно переданный неполный/null/невалидный объект не исправлять молча. GET должен вернуть нормализованную структуру для старого сохранённого JSON без побочного сохранения или изменения revision. Повторный PUT сохраняет полный новый объект. Старые суммы остаются RUB. Сохраняются owner_context, X-TripWise-Draft-Owner, последовательное автосохранение, 401/409/428 и защита от записи в другой аккаунт.

## Разделение исполнения

**Backend Agent:** только `backend/drafts.py` и тесты Fullstack, необходимые для нового контракта и совместимости. Добавить серверную валидацию состава/валют, нормализацию старых данных, тесты нового и старого ввода. Не менять accounts.py, auth, настройки агентов, AI/DS и настоящую пользовательскую БД для тестов. Передать фронтенду точные ключи и ошибки. Проверка: все валюты проходят round-trip; неверные значения/суммы отклоняются; старый JSON загружается; старая версия запроса принимается; owner/revision regressions сохраняются.

**Frontend Agent:** `frontend/` и `backend/pages/questionnaire.html`, `backend/pages/trips.html` (это HTML-шаблоны интерфейса), без правок серверного Python и тестов коллеги. Применить новый стиль на входе, поездках и анкете. Сделать переключатель темы на всех страницах, помнить выбор локально; при отсутствии выбора учитывать системное оформление. Не хранить в localStorage данные аккаунта/анкеты. Ручной ввод счётчиков доступен клавиатурой, корректные labels и видимый focus обязательны. Сохранить сообщения о загрузке/ошибке, реальные действия и честное описание ещё не подключённых функций. Фото должно быть реально доступным ресурсом; не выдавать скриншот референса с чужими элементами за собственный фон. Не добавлять удалённые шрифты/зависимости или внешние фото-сервисы без решения координатора. Проверить широкую и узкую ширину, читаемость обеих тем, сохранение выбранной валюты и состава после повторного открытия. Переключение темы не редактирует анкету.

**QA Agent:** после обеих реализаций независимо применить `qa-integration-check`, запустить Fullstack-набор с временной БД, проверить успешный и ошибочный HTTP-сценарии, старый сохранённый JSON, повторное открытие, смену владельца и конфликт revision. В браузере проверить три страницы, обе темы, узкую ширину и сценарий adults=2/children=1/seniors=1, EUR, 100 на человека → 400 EUR на компанию. Отдельно сообщить, если браузерная проверка недоступна: HTTP не доказывает визуальное качество. Обнаруженные ошибки передать владельцу файла и повторно проверить исправление.

## Фактические границы и следующий этап

В коде есть аккаунты и один сохраняемый черновик параметров Москвы. Настоящий маршрут, каталог обязательных мест и карта не реализованы в этой ветке. TASKS.md описывает раннее состояние и не подтверждает актуальное выполнение; его статусы без участницы не обновлялись. Календарные сроки не означают готовность задач.

Локальный снимок `origin/feature/ai-ds` содержит `docs/ai/contracts-v0.1.md` и `routing-contract-v0.1.md`; в документе Routing явно указан однодневный прототип. Он принимает один transport, требует routing_context, не подтверждает бюджет и часы. Новая валюта и состав группы сами по себе не интегрированы с этим модулем. Свежесть удалённой ветки не подтверждена fetch в рамках анализа.

Следующий P0 после этого среза: совместно с Участником 1 утвердить адаптер анкеты к его входным данным (один/несколько дней, transport, сумма/валюта/состав, реальные POI и дневные лимиты), затем подключить реальный каталог → рекомендации → расписание → сохранение маршрута и карту. Пока нельзя молча конвертировать иностранный бюджет, игнорировать детей/пожилых или выдавать синтетические места и прямые линии за полноценный туристический маршрут. Аналитик не менял чужие модули и общий контракт.
