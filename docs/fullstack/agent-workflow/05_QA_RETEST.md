## Проверка смысла двух исходных регрессий

До запуска прочитан актуальный test_account_switch.py, а не только его результат.

- Пустой A сначала получает owner_context из GET и удерживает его. После выхода и регистрации B тест отправляет прежние поля, revision = 0 и **исходный A-context**, используя уже общую cookie B.
- Для существующих черновиков A удерживает свой контекст и документ revision = 1. Законная начальная запись B выполняется с **отдельно загруженным B-context**. Затем старый документ A отправляется с A-context/A-revision под cookie B.
- Сравнение GET B с baseline включает весь объект, а не только одну сумму или людей.
- Оба теста дополнительно требуют ровно HTTP 409 и заголовок ACCOUNT_CHANGED. Поэтому они не проходят случайно из-за отсутствия нового заголовка и ответа 428.
- Общий helper не подставляет свежий контекст текущего пользователя в устаревший запрос A.

Это сохраняет первоначальное защитное ожидание и проверяет устранение той же причины дефекта, которая была воспроизведена до исправления.

## Read-only проверка серверной и клиентской части

backend/drafts.py возвращает owner_context и для null-черновика. PUT сначала использует обычную аутентификацию. Внутри транзакции записи, до чтения revision и изменения данных, owner_context сравнивается с id именно подтверждённого текущего пользователя. Заголовок не выбирает владельца строки: SQL продолжает использовать user['id']. Нового обхода доступа по передаваемому user_id не добавлено.

В frontend/questionnaire.js:

- ownerContext присваивается при первоначальной успешной загрузке документа и отправляется с каждым PUT;
- после 401/ACCOUNT_CHANGED он не заменяется данными текущего аккаунта и не стирается;
- ACCOUNT_CHANGED устанавливает отдельное блокирующее состояние и отменяет таймер; обычные изменения полей не возобновляют автосохранение;
- ручное «Готово» разрешает повтор только при account_changed/reauth_required с прежним контекстом;
- обычный revision_conflict этим повтором не разблокируется;
- тексты объясняют, что нужно вернуться в прежний/тот же аккаунт и повторить действие, а локальные поля остаются в текущей вкладке;
- сообщение CONTEXT_REQUIRED предупреждает, что несохранённые правки при обновлении пропадут.

Эти свойства подтверждены чтением исправленного JavaScript. Реальное отображение сообщений, остановка таймера в браузере и ручное восстановление A→A через две вкладки в этом независимом прогоне не проверялись и не выдаются за браузерный результат.

## Границы приёмки

Фактически закрыта воспроизводимая серверная ошибка смешения контекстов A→B и повторно пройдены связанные HTTP-регрессии. Гипотезы о потере секунд, медленной сети/таймауте, физически одновременных обновлениях и визуальных состояниях из отчёта 02_QA_REVIEW.md этим исправлением не исследованы заново. Время начала/конца маршрута по отелю и интеграционный формат AI/DS остаются вопросами команды.

Для следующей демонстрации желательно пройти двумя настоящими вкладками: A с открытой формой → другая вкладка входит в B → старая форма показывает отказ и B неизменён → другая вкладка возвращается в A → ручной повтор сохраняет A. Это дополнительная браузерная проверка; она не отменяет фактически подтверждённый результат HTTP-ретеста.

Политика контекста использует существующий id аккаунта. В приложении нет удаления/повторного создания аккаунтов; если оно появится, проектировщику нужно пересмотреть повторное использование id, как уже отмечено в 03_ARCHITECT_FIX.md. Публичный аудит безопасности и общая готовность MVP не заявляются.
