## Принятые требования и граница текущего среза

Полный продуктовый путь: обязательный вход → «Мои поездки» → анкета → предложенный маршрут по дням и карта → правки с предварительным подтверждением → сохранение маршрута. Пользовательница выбрала обычную анкету, один город, календарь и время готовности к первой/последней прогулке, количество людей, бюджет только питания/развлечений с переключателем «на человека / на компанию», 1–2 главных интереса, дополнительные интересы, три темпа, несколько способов передвижения и обязательные места из каталога. Первый город — Москва.

В текущем коде реализованы форма и хранение параметров. Автосохранение работает только после корректного заполнения всех обязательных полей. Незавершённые и ошибочные правки остаются несохранёнными с предупреждением. Один аккаунт имеет один активный черновик, а не произвольное число готовых поездок. Список обязательных мест недоступен с пояснением, API принимает только пустой required_poi_ids. На карточке явно написано, что маршрут не построен.

Это честно описанные ограничения этапа. Отсутствие генерации здесь нельзя оформлять как внезапно обнаруженный дефект существующей функции. Но каталог обязательных мест означает, что F01 закрыта лишь частично; F11 требует сохранения самого маршрута и подтверждённых правок, которое черновик не заменяет. Не закрыты F03–F10 и полный туристический путь. Выбор темпа и транспорта в форме не доказывает влияние на расчёт. Технические пределы формы (до 100 людей, до 1 млрд ₽) не подтверждены пользовательским исследованием и не должны подаваться как продуктовые выводы.

TASKS.md описывает исходный план и неподтверждённые статусы, не соответствующие детализации текущих Fullstack-отчётов. Его не следует автоматически переписывать или отмечать всё выполненным. Предложение: после независимой QA-проверки согласовать точечное обновление статусов со ссылками на коммит/отчёт. Дедлайн 2 декабря и контрольные точки 22/26 ноября сохраняются; готовность прошлого календарного этапа не выводится из даты.

## Критерии приёмки текущего среза

| Код | Проверяемое условие |
|---|---|
| A01 | Без действующего входа HTML анкеты не выдаётся; GET/PUT черновика не открывают данные |
| A02 | Москва/Россия и московское время показаны явно; API отвергает несогласованную географию/смещение |
| A03 | Окончание позже начала; отрицательный/бесконечный бюджет, дробное/булево число людей и неверные поля не принимаются |
| A04 | Выбираются 1–2 уникальных главных интереса; дополнительные не повторяют главные; транспорт не пуст и без дублей |
| A05 | Сумма, единица бюджета, люди, даты, темп и транспорт сохраняются без молчаливой подмены и восстанавливаются |
| A06 | После сообщения об успешном сохранении GET и повторное открытие дают последнюю подтверждённую версию, включая после перезапуска сервера |
| A07 | Незавершённая/ошибочная правка не портит последнюю корректную запись; интерфейс не заявляет успех при отказе или неизвестном результате |
| A08 | Сервер выбирает владельца по сеансу, не по user_id из тела; пользователь B не читает и не заменяет черновик A |
| A09 | Старые вкладки после выхода, истечения сеанса или смены аккаунта не записывают параметры прежнего владельца в аккаунт другого пользователя |
| A10 | Одновременные обновления одной revision не теряют новую версию: один запрос сохраняется, устаревший получает 409; состояние после конфликта понятно |
| A11 | Правка во время медленного сохранения и нажатие «Готово» не теряют последнюю корректную правку; переход дожидается подтверждения |
| A12 | Ошибки сети/таймаут/401 не приводят к ложному сообщению «сохранено» или автоматической потере введённого; есть понятный путь продолжения |
| A13 | На карточке сохранён именно черновик; генерация, каталог и реальная поддержка смешанного транспорта не заявлены готовыми |

Критерии A09–A12 описывают надёжность уже существующего сохранения и изоляцию аккаунтов, а не новые туристические возможности.

## Риски для первоочередного воспроизведения QA

**Смена аккаунта при открытой анкете — гипотеза по коду, не подтверждённый дефект.** frontend/questionnaire.js загружает preferences и revision, но не фиксирует личность владельца загруженного документа и при PUT использует текущую cookie. Обработчик backend/drafts.py корректно берёт текущего пользователя, но сравнивает revision только с его черновиком. Если A держит открытые поля, а другая вкладка входит под B, совпадение номеров может позволить сохранить старые поля A в черновик B. Особенно важно воспроизвести сценарий из сообщения UI после 401: «Откройте вход в другой вкладке, затем повторите сохранение». Точки чтения: frontend/questionnaire.js loadDraft/saveLatest; backend/drafts.py get_draft/save_draft. Ожидается безопасная остановка или повторная проверка принадлежности; автоматическое смешивание данных недопустимо.

**Конфликты и сетевые неопределённости.** Backend использует транзакцию и revision, клиент — последовательные сохранения. В существующих тестах есть последовательное устаревшее обновление, но по чтению кода не подтверждён реальный одновременный запрос и полный браузерный конфликт. После 409 клиент блокирует дальнейшие сохранения до обновления. Нужно оценить, понятно ли пользователю, что локальная правка может быть потеряна при обновлении, и не является ли сообщение слишком уверенным при таймауте после фактической записи.

**Точность времени.** API принимает даты со временем, тогда как fillForm берёт slice(0, 16), то есть минуты. Проверить прямой корректный API-ввод с секундами и последующее редактирование другого поля через UI: не теряется ли точность без предупреждения. Политика секунд не согласована; при расхождении сначала зафиксировать вопрос контракта, не вводить новый произвольный стандарт.

**Граница частичного заполнения.** Страница прямо говорит, что сохраняется заполненная анкета. Требование автосохранения полной поездки не тождественно сохранению каждого пустого промежуточного поля. Проверить честность сообщения и предупреждение выхода; не придумывать требование хранить любой невалидный JSON.

## Что передать проектировщику перед интеграцией AI/DS

Fullstack хранит собственную схему fullstack-draft-0.1. Её нельзя молча выдать за UserPreferences 0.1 напарника. Нужно совместно определить преобразование количества людей и бюджета, нескольких transport_modes вместо одного transport, доступных окон первого/последнего дня, многодневности и обязательных POI. Начало/конец ежедневной прогулки по адресу отеля пользовательница прямо отложила до разговора с Участником 1. Решение не принимается аналитиком. Актуальность ветки AI/DS и новые контракты на этом аналитическом этапе не перепроверялись.

После QA сначала устранить подтверждённые дефекты ограниченного среза, затем поручить architect контрактную сверку. При исправлениях отдельный разработчик получает конкретное воспроизведение, а QA — изменённую версию для ретеста. Новые функции не добавлять под видом исправления.
