## Что изменено

- backend/drafts.py: GET возвращает строковый owner_context вместе с draft, в том числе при null. PUT требует X-TripWise-Draft-Owner. Отсутствие заголовка даёт 428 и код CONTEXT_REQUIRED. В существующей транзакции записи до чтения revision контекст сравнивается с id пользователя подтверждённого сеанса. Несовпадение даёт 409 и код ACCOUNT_CHANGED без записи. Владелец строки по-прежнему берётся только из user['id'], не из заголовка.
- frontend/questionnaire.js: форма удерживает контекст первоначальной загрузки, не подменяет его после смены входа. Каждое сохранение передаёт исходный контекст. При смене аккаунта, отсутствии контекста или 401 автосохранение останавливается; поля остаются. «Готово» разрешает ручной повтор только для смены аккаунта/повторного входа с прежним контекстом. Перевход в тот же аккаунт позволяет сохранить; обычный revision-конфликт не разблокируется.
- tests/fullstack/test_drafts.py: положительные запросы удерживают контекст от первоначального GET; для другого клиента отдельно загружается его контекст. Не добавлен глобальный helper, автоматически подставляющий свежий контекст во все PUT.
- tests/fullstack/test_account_switch.py: два исходных regression-сценария удерживают именно старый A-контекст. Законные предварительные записи B используют отдельно загруженный B-контекст. Ожидания отказа и неизменности B сохранены и усилены точным 409 / ACCOUNT_CHANGED. Добавлены проверки отсутствия контекста, неверного контекста, перевхода в тот же аккаунт и сохранения прежней защиты revision.
- README.md: описаны уточнённый собственный HTTP-протокол, восстановление работы и фактический тестовый прогон.

Этот отчёт — единственный новый документ разработчика. Отчёты аналитика, QA и проектировщика не переписаны. Коммит/push не выполнялись.

## Почему исправление закрывает воспроизведение

Revision прежнего A может совпадать с revision B, но удерживаемый контекст A не совпадает с пользователем cookie B. Сравнение выполняется сервером в операции записи, включая первый пустой черновик. Заголовок не выбирает строку и не даёт новых полномочий. Он не секрет, не токен сеанса и не заменяет аутентификацию. Запрос, начавшийся под A до переключения cookie, может изменить только A; запрос под B с контекстом A отклоняется.

Новых таблиц/миграций или библиотек не требуется. Формат preferences и контракт интеллектуального модуля не меняются. Старые клиенты без нового заголовка намеренно получают отказ и должны обновить страницу.

## Фактическая проверка разработчика

Первый запуск штатного набора с loopback bypass остановился до выполнения тестов: среда не разрешила bind локального порта, `Ran 0 tests`, `PermissionError`, три ошибки setUpClass. Это ограничение запуска, а не результат проверки кода.

После разрешения открытия собственных временных локальных портов выполнена команда:

```sh
NO_PROXY=127.0.0.1,localhost no_proxy=127.0.0.1,localhost .venv/bin/python -W error::ResourceWarning -m unittest discover -s tests/fullstack -v
```

Результат: **31 тест, 20.197 секунды, OK**. Из них 13 аккаунтов, 12 черновиков, 6 контекста владельца. Набор работает по настоящему HTTP на временных базах и свободных портах; после завершения собственные процессы остановлены штатным cleanup. Пользовательская база и процесс на 8765 не использовались. Выполнен `git diff --check`, замечаний нет.

Два прежних падения теперь проходят с реальным старым A-контекстом: пустой черновик B остаётся null; существующий черновик B с совпавшей revision остаётся точно прежним. Дополнительно проверены 428 без контекста, 409 неверному контексту, 401 после выхода, успешное сохранение после перевхода в тот же A, обычный revision-конфликт без ошибочной маркировки ACCOUNT_CHANGED.
