## Реализовано

- Логотип TripWise во всех трёх HTML ведёт на `/`, с соответствующим aria-label. Предупреждение о несохранённых данных остаётся.
- На странице поездок кнопка «Создать новую поездку» находится вне пустого состояния и списка. Новая форма открывается по `/trip/new?new=1`; отсутствие id также означает новую пустую анкету. Создание со страницы главной использует этот же сценарий.
- Все разделы анкеты получили цельные иллюстрированные шапки. Компания оформлена карточками с количеством; интересы — восемью карточками с индивидуальными декоративными SVG; транспорт — тремя карточками с иллюстрациями; темп сохраняет прежние иллюстрации; обязательные места — выделенные checkbox-карточки с выбранными chips. Hero анкеты уменьшен, чтобы внимание оставалось на заполнении. Имена/ID существующих полей сохранены.
- Все восемь основных интересов остаются доступными, минимум один. Дополнительные по-прежнему не пересекаются с основными. Убраны подписи «1–2». Это изменение Fullstack, поддержка всех восьми алгоритмом напарника не заявляется.

## CRUD-контракт

- Новая форма получает GET `/api/trips` только ради исходного owner_context, никогда не копирует последнюю поездку. Edit с положительным безопасным целым id получает GET `/api/trips/{id}` и заполняет только выбранную запись. Неверный id не превращается в New.
- Сохранение только по кнопке: новый снимок POST `/api/trips` с preferences и creation_key, редактирование PUT конкретного id с revision/preferences. Заголовок owner-context фиксируется при загрузке формы.
- При неопределённом результате POST сохраняются и UUID, и исходный снимок, и его editVersion. Повтор кнопкой отправляет тот же запрос. Если после подтверждения есть новые локальные правки, форма остаётся открыта уже с ID созданной записи; следующий отдельный клик использует PUT. Так не создаётся дубликат и не теряются новые поля.
- Определённый отказ 400/422 сбрасывает неподходящий снимок без создания записи, чтобы исправленные поля могли быть отправлены. При сетевой ошибке/5xx снимок удерживается.
- Список поездок строится из всех записей GET `/api/trips`. У каждой своя иллюстрация направления, даты, бюджет, компания, ссылки Edit и кнопка Delete. Названия выводятся textContent.
- Delete запрашивает подтверждение с названием и датами, затем отправляет DELETE конкретного id с revision и исходным owner_context. До успешного ответа карточка не удаляется, при ошибке остаётся. Отмена confirm не отправляет запрос. При удалении последней записи показывается пустое состояние, кнопка New остаётся.

## Проверки для QA

Две новые поездки одного аккаунта, независимое редактирование каждой, Delete cancel и success/failure, смена аккаунта и revision-конфликт. New при заполненном списке не загружает прежние поля и не выполняет POST до Save. Все восемь интересов выбираются и восстанавливаются. Проверьте явный Save с правкой во время запроса, неизвестным результатом POST и повтором исходного снимка; 422 → исправление → следующий клик не повторяет отклонённый snapshot. Проверьте иллюстрированные карточки в обеих темах при375/1440 и клавиатуру.

Практика для студентки: создать две анкеты, изменить даты только первой и убедиться, что вторая не изменилась. Вопрос: зачем серверу одновременно ID поездки, owner_context и revision?
