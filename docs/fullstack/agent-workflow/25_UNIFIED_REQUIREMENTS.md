# Объединение интерфейса и построения маршрутов: требования

Дата: 22 ноября 2026. Исполнитель: отдельный Analyst Agent. Прочитаны AGENTS.md, analyst-requirements, PROJECT_OVERVIEW, FEATURES, ROADMAP, TASKS и docs/ai/data-sources.md. Это критерии новой задачи, а не подтверждение её выполнения.

## Утверждено пользователем

- Работу объединяем в отдельной ветке от integration/fullstack-ai-ds; исходные ветки не перезаписываем.
- Публичная главная, регистрация/вход, темы и современное оформление анкеты сохраняются.
- Сценарий: анкета → «Создать маршрут» → результат с расписанием и картой → «Редактировать» / «Сохранить поездку».
- Создание и просмотр результата не добавляют поездку в постоянное хранилище. Только явное сохранение создаёт новую карточку либо обновляет выбранную существующую поездку.
- Каждая ранее сохранённая поездка остаётся; создание новой не заменяет соседнюю. Редактирование/удаление относятся только к выбранной записи; удаление требует подтверждения.
- В направлениях первыми доступны Россия → Москва и Китай → Шанхай. Остальные страны/города обозначены «В разработке» и не выбираются для генерации. Сервер тоже проверяет доступность.
- Можно выбрать от одного до всех восьми основных интересов; сохраняются состав группы, бюджет/его способ расчёта, несколько режимов транспорта и несколько обязательных мест.

## Обнаруженные границы существующего планировщика

В исходном backend/shanghai.py обе модели ограничены 1–5 днями; принимают CNY/RUB/USD/EUR, бюджет до 10 млн, до 30 участников каждой возрастной категории. Поддержаны walk/transit/taxi и mixed с transport_modes. Публичные категории интересов совпадают с восемью категориями Fullstack. Это чтение кода, не результат прогона.

Существующий Fullstack допускает более широкие суммы/составы/валюты и использует другой формат дат и названия полей. Нужен явный адаптер, а не усечение данных. Если введённое значение пока не поддержано генератором, показать понятную ошибку до построения и сохранить заполненные поля. Не подменять выбранный город Москвой, car такси без объяснения, неизвестные POI ближайшими догадками, групповой бюджет бюджетом на человека.

В планировщике есть фиксированный учебный FX-снимок, а не подтверждённые текущие курсы. Нельзя называть его актуальным курсом, добавлять конвертацию в анкету без объяснения или выдавать оценки затрат за проверенные цены. Сведения о происхождении и синтетических/оценочных слоях не скрываются.

## Критерии приёмки

1. На доступных Москве и Шанхае анкета запускает существующий движок через согласованный адаптер; показанный результат соответствует отправленным параметрам.
2. До Save количество постоянных сохранённых поездок не меняется: ни в saved_trips, ни в planned_trips. Непостоянный предпросмотр отделён от сохранённой поездки.
3. Edit открывает данные текущего предпросмотра/выбранной поездки, не чужую или последнюю произвольную анкету. После повторной генерации также требуется Save.
4. Save сохраняет именно показанный результат; повтор после потерянного ответа не создаёт дубликат; новая локальная правка не сохраняется фоновым запросом.
5. «Мои поездки» показывает сохранённые анкеты и/или маршруты с ясным различием сущностей. Идентификатор анкеты не выдаётся за route_id. Переходы, Edit/Delete, revision и принадлежность аккаунту остаются корректными.
6. Загрузка каталога использует настоящие ID движка для нужного города; исходные локальные ID UI не передаются как будто они принадлежат другому каталогу.
7. Недоступные направления невозможно выбрать в UI и передать напрямую для построения; RU/CN и Москва/Шанхай стоят первыми.
8. Ошибка сети, неподдержанный параметр, отказ движка или истёкший предпросмотр оставляют понятное сообщение и не выдают ложное сохранение. Перезагрузка/перезапуск временного хранилища не объявляются гарантированно сохраняющими незаписанный результат.
9. Ни параметры, ни маршрут, ни чужая запись не выдаются без проверки серверного сеанса. Сохраняются Origin, контекст исходного владельца и проверки версий там, где предусмотрены контрактом архитектора.
10. До завершающего коммита разрешены все семь Git-конфликтов, отсутствуют маркеры конфликтов, выполнены подходящие API/JS/алгоритмические проверки. Пройденные проверки и ограничения описаны раздельно.

## Разделение работы

Architect определяет конкретный контракт временного результата и явного сохранения. Backend реализует этот контракт и адаптеры, не меняя формулы AI/DS. Frontend объединяет оформление, анкету, экран результата и список. QA независимо проверяет оба города, отсутствие записи до Save, изменение/повторное открытие и ошибки. Координатор управляет Git и безопасностью рабочей базы. Analyst разрешает README и документирует только полученные факты.

Общие TASKS.md, сроки и математические модели этим заданием не изменяются. Фактические выводы интеграции будут добавлены в README после проверки исполнителями.
