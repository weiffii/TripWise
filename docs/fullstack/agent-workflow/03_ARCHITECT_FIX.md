## Проблема и граница исправления

Текущий сервер правильно выбирает пользователя по cookie, но revision является локальным номером его черновика. Форма A после смены общей cookie на B предъявляет revision A, совпадающую с revision B; сервер считает запрос изменением B. Ошибка возникает и при первом сохранении, когда обе revision равны нулю.

Исправляется только смешение контекстов аккаунтов. Генерация маршрута, каталог POI, точность секунд, новые туристические возможности и общая архитектура не входят в задачу. Требование — при записи проверять пару «владелец загруженного документа, revision», а фактического владельца строки по-прежнему брать только из аутентифицированного сервером пользователя.

## Рассмотренные варианты

| Вариант | Оценка |
|---|---|
| Только GET /me непосредственно перед PUT | Не закрывает гонку: cookie может смениться между двумя запросами |
| Контекст текущего сеанса | Закрывает A→B, но потребует дополнительного восстановления при перевходе в тот же A, поскольку токен сеанса меняется |
| Случайный постоянный контекст аккаунта в новой таблице | Подходит, но добавляет таблицу/миграцию/жизненный цикл без необходимости для этого дефекта |
| Строгое предусловие владельца загрузки плюс существующая revision | Минимальное решение без миграции, зависимостей или новой криптографии; сохраняет работу после перевхода в тот же аккаунт |

Рекомендация — последний вариант. Непрозрачность не является защитой в этом сценарии: id аккаунта уже возвращается GET /api/auth/me. Контекст служит предусловием намерения формы, а не паролем, bearer-токеном или полномочием выбрать произвольного владельца. Если клиент намеренно подменит его, он всё равно может изменить только собственный аккаунт, подтверждённый cookie. Не генерировать контекст из хеша пароля и не раскрывать токен/хеш сеанса.

## Минимальное уточнение собственного draft API

GET /api/trip-draft после аутентификации возвращает прежний draft и обязательное дополнительное поле owner_context:

```json
{"owner_context":"123","draft":null}
```

owner_context — строковое представление id подтверждённого текущего пользователя. Оно возвращается и для пустого черновика. Уже существующие потребители draft, например список поездок, могут игнорировать новое поле.

PUT /api/trip-draft сохраняет прежнее тело `{revision, preferences}`, но требует заголовок `X-TripWise-Draft-Owner` с owner_context, полученным при загрузке именно этого документа. Тело не получает user_id. Сервер не использует заголовок в качестве выбираемого владельца строки.

Проверки обработчика:

1. Прежние проверка Origin, текущего сеанса и полей сохраняются. Неавторизованный запрос по-прежнему получает 401.
2. Нет заголовка — 428 с понятным сообщением «Обновите страницу анкеты перед сохранением» и `X-TripWise-Draft-Error: CONTEXT_REQUIRED`. Никакой записи в БД.
3. В существующей транзакции записи `BEGIN IMMEDIATE`, до чтения revision и до любых изменений, сравнить заголовок со `str(user['id'])`, где user получен серверной аутентификацией этого запроса.
4. Не совпал — 409 с `X-TripWise-Draft-Error: ACCOUNT_CHANGED` и сообщением о смене аккаунта и остановленном сохранении. Никакой записи в БД, включая создание пустого черновика.
5. Совпал — выполнить существующую проверку revision и запись только по user['id']. Старый конфликт revision остаётся 409; его прежние ожидания не ослабляются.

Контекст и запись проверяются одним обработчиком без промежуточного клиентского /me. Cookie конкретного HTTP-запроса и полученный по ней user не меняются, когда другая вкладка позже входит в другой аккаунт. Поэтому сравнение с user внутри транзакции исключает запись A в B. Запрос, уже начавшийся под A, может затронуть только строку A, а не внезапно выбрать B. Общую задачу немедленного отзыва уже исполняющегося запроса этим исправлением не расширять.

Числовой id в контексте не секрет; полный токен сессии остаётся HttpOnly. В будущей функции удаления/повторного создания аккаунтов следует отдельно пересмотреть возможность повторного использования id; сейчас удаления аккаунтов через приложение нет.

Это небольшое совместное уточнение собственного Fullstack HTTP-протокола для выполнения уже принятой изоляции пользователей. Оно не меняет схему preferences fullstack-draft-0.1, формат UserPreferences напарника, математические модели, таблицы или архитектуру. Старый frontend без заголовка намеренно не должен сохранять: после обновления сервера страницу нужно обновить. Миграция пользовательской БД не требуется.

## Клиент и восстановление

- loadDraft получает owner_context и сохраняет его в памяти рядом с revision; отсутствие корректной строки означает ошибку загрузки, поля не разблокируются. Запрещён fallback «возьми текущий /me на каждом сохранении».
- Каждый PUT передаёт неизменённый контекст загруженной формы. Не обновлять его автоматически после входа другого пользователя, при 401 или перед повторной попыткой. Иначе дефект вернётся.
- При ACCOUNT_CHANGED отменить debounce-таймер и остановить автоматическое сохранение старого документа. Показать: «Аккаунт изменился. Сохранение остановлено. Войдите в прежний аккаунт в другой вкладке и нажмите „Готово“ для повторной попытки». Локальные поля не стирать и не помечать сохранёнными.
- Нажатие «Готово» после такого сообщения может один раз повторить PUT с прежним контекстом и прежней revision. Если пользователь по-прежнему B — снова отказ. После перевхода в тот же A — сохранение разрешено при совпавшей revision. Не заменять контекст на B, чтобы убрать ошибку.
- Обычный конфликт revision не превращать в автоматическую перезапись и не снимать его блокировку под видом смены аккаунта.
- Сообщение 401 уточнить: войти именно в тот же аккаунт, затем повторить; текущие поля и контекст остаются в памяти. Истёкший сеанс без входа ничего не сохраняет. Новый сеанс того же аккаунта совместим с прежним контекстом.
- При CONTEXT_REQUIRED остановить сохранение, предложить обновление страницы; не заявлять, что несохранённые поля переживут обновление.

### Как обновить тестовые запросы, не скрыв дефект

Позитивные тесты должны явно получить owner_context через GET перед корректным сохранением и передать соответствующий заголовок. При отдельном клиенте B нужно отдельно получить B-контекст для его законных записей. Нельзя автоматически подставлять свежий контекст по текущей cookie во все PUT: так старый запрос A перестанет быть старым и регрессия будет замаскирована.

В двух QA-regression-сценариях захватить A-контекст при первоначальном GET и удерживать вместе с revision/preferences. После переключения cookie на B его законные предварительные записи выполняются с отдельно загруженным B-контекстом. Затем отправить старую пару A-контекст/A-revision под cookie B. Ожидания сохраняются: отказ и точное равенство GET B прежнему baseline, включая null. Дополнительно проверить, что отказ вызван ACCOUNT_CHANGED, а не отсутствующим заголовком/невалидным телом. Не принимать прохождение двух тестов лишь из-за отсутствия нового заголовка.

Добавить отдельные проверки: отсутствие контекста даёт 428 без изменения БД; обычные create/update работают; повторный вход в тот же A с прежним A-контекстом позволяет сохранить, если revision не менялась; подмена/просрочка сеанса по-прежнему 401; прежний revision-конфликт остаётся защищённым. Проверку аутентификации и прежние ожидания не ослаблять.

Прогон по существующему окружению: `.venv/bin/python -W error::ResourceWarning -m unittest discover -s tests/fullstack -v`. Если в конкретном сеансе прокси мешает loopback, как в отчёте QA, исключить только 127.0.0.1/localhost через NO_PROXY/no_proxy; не выводить настройки прокси или секреты.

Сохранение в том же аккаунте, повторный вход и прежние корректные сценарии проходят. Интерфейс не перезагружает форму и не меняет её владельца автоматически при ACCOUNT_CHANGED.
