# Несколько сохранённых анкет: сервер и миграция

Дата: 21 ноября 2026. Отдельный Backend Agent реализовал подтверждённое пользователем хранение нескольких анкет по явной кнопке сохранения, редактирование и удаление. Основание — контракт Architect Agent; это пока анкеты, не рассчитанные AI/DS-маршруты.

## Файлы и решения

- `backend/drafts.py`: `saved_trips` становится единственным рабочим хранилищем. Поля: integer id, user_id, preferences_json, revision, created_at, updated_at, creation_key; уникальная пара user_id/creation_key.
- `init_drafts()` выполняет CREATE и миграцию в одной BEGIN IMMEDIATE транзакции. Маркер schema_migrations `multi-trips-v1` предотвращает повторный импорт. Старые trip_drafts переносятся с creation_key `legacy-v1`; JSON, revision и updated_at копируются без преобразования, created_at при отсутствии старого значения равен updated_at. Старый стол остается архивом и не удаляется/не обновляется API.
- Старые GET/PUT `/api/trip-draft` обращаются строго к canonical записи `legacy-v1`, не к последней поездке. Поэтому старая открытая форма не изменит новую поездку при появлении второй карточки. GET нормализует старый состав только в ответе без записи.
- `backend/trips.py`: новая CRUD-поверхность; все изменяющие запросы проверяют Origin, исходный owner-context и текущий сеанс. Владелец определяется сервером. Чужие и отсутствующие ID дают одинаковый 404; PUT/DELETE требуют актуальную revision.
- `backend/main.py`: новый router, no-store для `/api/trips` и безопасные сообщения 422 без echo входных данных.
- В той же согласованной задаче primary_interests теперь от 1 до 8 уникальных категорий; пересечение с secondary по-прежнему запрещено.

## Контракт

```text
GET /api/trips                       {owner_context,trips:[trip,...]}
GET /api/trips/{id}                  {owner_context,trip}
POST /api/trips                      {preferences,creation_key:UUID} -> 201 {trip}
PUT /api/trips/{id}                  {revision,preferences} -> 200 {trip}
DELETE /api/trips/{id}               {revision} -> 204
trip = {id,preferences,revision,created_at,updated_at}
```

Все записи требуют `X-TripWise-Draft-Owner` из исходного GET. Нет заголовка — 428, смена аккаунта — 409 с `ACCOUNT_CHANGED`, конфликт revision — 409. Creation_key создаётся клиентом один раз для попытки создания новой анкеты. Повтор с тем же ключом и тем же каноническим payload возвращает 200 существующую запись, не создаёт дубль и не увеличивает revision. Другой payload — 409, не перезаписывает запись. Резервное значение legacy-v1 недоступно в POST, поскольку требуется UUID. После редактирования старый повтор создания с отличающимся payload также не перезапишет данные. После удаления UUID не хранится как tombstone: новый POST с тем же ключом может создать новую запись; это не означает повторного импорта из архива. API не выполняет неявного сохранения по GET.

## Выполненные проверки разработчика

```sh
NO_PROXY=127.0.0.1,localhost no_proxy=127.0.0.1,localhost .venv/bin/python -W error::ResourceWarning -m unittest discover -s tests/fullstack -p test_trips.py -v
```

8/8 реальных HTTP-тестов прошли за 6.427 s. Проверены: две независимые записи; редактирование только одной; удаление только одной; сохранность другой после перезапуска; idempotent POST и конфликт иного payload; запрет чужих ID; отсутствие доступа анонимно; owner/Origin/revision; no-store и безопасная 422; однократный импорт сырых старых JSON без потери байтов; тождество legacy alias и canonical записи; невоскрешение удалённой мигрированной записи после повторного запуска. `py_compile` Python и `git diff --check` прошли.

Отдельные 4/4 `test_many_interests.py` ранее прошли за 2.342 s (выбор 3/8, отказы пустому/повторному/неизвестному/пересекающемуся). Общая независимая регрессия передана QA, не приписывается разработчику.

## Сохранность и передача

Изменялись только назначенные серверные файлы, новые tests/fullstack/test_trips.py и test_many_interests.py, этот отчёт. Runtime пользователя не читался и не изменялся; запуск миграции на пользовательском сервере выполняет координатор после backup и независимой QA. Тесты используют временную SQLite и свои процессы. Новых зависимостей, внешних API и изменений алгоритмов напарника нет.

Для старых тестов raw legacy: до проверки миграции нужно остановить тестовый сервер, добавить архивную строку и убрать миграционный маркер в временной БД, затем запустить. Вставка в архив после завершённой миграции намеренно не меняет рабочую запись. Это следует новому контракту, а не повод поддерживать два расходящихся хранилища.

Студентке: id отличает поездки одного пользователя, user_id защищает их принадлежность, revision защищает от старой вкладки, creation_key защищает от дублирования при повторе сохранения. Практика — сохранить две анкеты, изменить первую, удалить вторую. Вопрос: почему одного user_id уже недостаточно, чтобы выбрать конкретную сохранённую поездку?
