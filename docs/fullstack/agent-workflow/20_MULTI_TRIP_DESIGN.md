# Несколько сохранённых анкет: техническое решение

Дата: 21 ноября 2026. Пользовательница подтвердила, что каждая сохранённая поездка остаётся отдельной карточкой; нужны создание, редактирование и удаление. Это разрешает расширение прежней модели «одна анкета на аккаунт». Ниже проект решения, а не доказательство его реализации или прохождения проверок.

## Проблема и текущее состояние

До этой задачи `trip_drafts.user_id` был первичным ключом: второе сохранение заменяло первую анкету. GET/PUT `/api/trip-draft` не имели идентификатора поездки. Frontend сохранял только явной кнопкой; owner-context защищал старую форму при смене аккаунта, revision — от перезаписи устаревшей версии. Эти свойства нужно сохранить.

Рассмотрены варианты: предупреждать о замене (не соответствует новому ответу пользовательницы); вести две независимо изменяемые таблицы (риск расхождения данных); перейти к единой таблице нескольких анкет с совместимым старым API. Выбран последний вариант без новых зависимостей и изменения AI/DS.

## Хранение и миграция

Каноническая таблица `saved_trips`: `id INTEGER PRIMARY KEY`, `user_id REFERENCES users(id)`, `preferences_json`, `revision`, `created_at`, `updated_at`, `creation_key TEXT`; уникальность `(user_id, creation_key)`.

В одной транзакции инициализации создать новую таблицу и таблицу маркеров миграции. Если маркер `multi-trips-v1` отсутствует, перенести каждую существующую строку `trip_drafts` в `saved_trips` с `creation_key='legacy-v1'`, сохранив preferences, revision и updated_at; для неизвестного created_at использовать прежний updated_at. Затем записать маркер. Откат транзакции должен откатывать и импорт, и маркер.

Старую таблицу не удалять: это архив миграции, который новый код не изменяет и API после миграции не читает. Не импортировать архив при каждом запуске: удалённая пользователем анкета не должна появиться снова. Рабочая истина только `saved_trips`.

## Контракт API

Объект `trip`: `id` (целое положительное), `preferences` (текущий TripPreferences), `revision`, `created_at`, `updated_at`. Сохранённая анкета не называется рассчитанным маршрутом.

| Запрос | Вход | Успех |
|---|---|---|
| GET `/api/trips` | Сеанс | `{owner_context, trips:[trip...]}` |
| GET `/api/trips/{id}` | Сеанс | `{owner_context, trip}` |
| POST `/api/trips` | `{preferences, creation_key:UUID}` | 201 `{trip}`; повтор того же ключа и тех же нормализованных данных — 200 с прежней записью |
| PUT `/api/trips/{id}` | `{revision, preferences}` | 200 `{trip}` с revision+1 |
| DELETE `/api/trips/{id}` | JSON `{revision}` | 204 без тела |

Все изменяющие запросы требуют существующие Origin-проверку, сеанс и `X-TripWise-Draft-Owner` из исходной загрузки формы/списка. Заголовок — предусловие, а не выбор владельца. Владелец всегда определяется сеансом. SQL ищет запись одновременно по id и user_id. Отсутствующая или чужая запись — 404. Нет owner-context — 428/CONTEXT_REQUIRED; аккаунт изменился — 409/ACCOUNT_CHANGED; устарела revision — 409. Ошибки сохраняют прежние данные. Новый префикс API должен получить `Cache-Control: no-store` и безопасные сообщения валидации без чувствительных входных значений.

POST с тем же creation_key, но другими нормализованными данными возвращает 409 и не создаёт запись. UUID отделяет новые запросы от служебного ключа `legacy-v1`. Клиент генерирует ключ один раз на новую форму. После неопределённого сетевого результата повторяет первоначальный снимок с тем же ключом; нельзя незаметно повторять другой снимок с тем же ключом. PUT/DELETE выполняют проверку revision и запись/удаление в одной транзакции.

## Совместимость прежнего API

GET/PUT `/api/trip-draft` становятся адаптером к единственной канонической строке текущего пользователя с `creation_key='legacy-v1'`. GET возвращает прежнюю форму `{owner_context,draft}` без нового обязательного поля в draft. При отсутствии такой строки GET возвращает null; PUT с revision=0 создаёт её. Это не «последняя поездка»: иначе старая открытая форма могла бы отредактировать новую поездку с такой же revision. Новые UI-страницы старый API не используют.

Записи нового API сразу отражаются в старом API только если редактируется именно мигрированная строка. Независимых записываемых копий нет. Старый архив не служит резервным источником API после удаления канонической строки.

## Frontend и проверки

На всех страницах логотип ведёт на `/`. В «Моих поездках» постоянная кнопка «Создать новую поездку» ведёт к пустой `/trip/new`; карточка редактируется через `/trip/new?id=<id>`. Список загружается с нового API. Новая форма получает owner-context через GET списка, существующая — через GET выбранной записи. Загрузка/ввод не создают строки. Только кнопка «Сохранить» вызывает POST или PUT. Удаление требует явного подтверждения и отправляет revision карточки; ошибка не убирает карточку как будто удаление прошло.

Primary interests: минимум один, технический максимум восемь известных категорий; уникальность и отсутствие пересечения с secondary сохраняются. Модель и ограничение AI/DS не меняются автоматически.

QA: две анкеты одного пользователя сохраняются независимо; правка первой не меняет вторую; отмена удаления ничего не отправляет; успешное удаление затрагивает только выбранный id; чужие id недоступны для чтения/редактирования/удаления; owner-context и revision защищают все записи; повтор POST после потери ответа не даёт дубль; миграция переносит старую анкету один раз; после удаления и перезапуска она не восстанавливается. Миграционные фикстуры должны быть подготовлены в старой таблице **до** запуска миграции: вставка в архив после завершённой миграции не обязана менять рабочую таблицу. Проверки сохранности JSON старой таблицы при GET остаются полезными, но ответ API сравнивается с канонической строкой.

Риски/ограничения: это CRUD анкет, пока без рассчитанного расписания, карты и переходов. Прямая старая запись внешними инструментами в архив после миграции не поддерживается. Сроки и общий TASKS.md этим документом не меняются. Решение передано координатору, backend_agent и frontend_agent; результат исполнения проверяется отдельно QA.
