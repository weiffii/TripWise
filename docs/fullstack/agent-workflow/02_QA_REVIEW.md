## Фактически выполненные команды

Первоначально запущена штатная команда:

```sh
.venv/bin/python -W error::ResourceWarning -m unittest discover -s tests/fullstack -v
```

В этом QA-сеансе тестовая среда содержит HTTP/HTTPS-прокси и не исключает loopback: `proxy_bypass('127.0.0.1')` вернул False. Поэтому первый запуск завершился в setUpClass двух наборов с RemoteDisconnected, до выполнения тестов: `Ran 0 tests`, `FAILED (errors=2)`. Это ошибка маршрутизации локального тестового трафика в среде проверки, а не доказательство дефекта приложения.

Повтор без прокси только для локальных адресов:

```sh
NO_PROXY=127.0.0.1,localhost no_proxy=127.0.0.1,localhost .venv/bin/python -W error::ResourceWarning -m unittest discover -s tests/fullstack -v
```

Результат существующего набора до добавления новых regression-тестов: **25 тестов, 12.568 секунды, OK**, без ResourceWarning. Это 13 тестов аккаунтов и 12 тестов черновиков. Фактически перепроверены валидация, временные сеансы, права по текущей cookie, сохранение/восстановление, перезапуск, последовательный конфликт revision и сохранность прежней корректной записи после ошибочного обновления.

После этого создан отдельный regression-файл и выполнено:

```sh
NO_PROXY=127.0.0.1,localhost no_proxy=127.0.0.1,localhost .venv/bin/python -W error::ResourceWarning -m unittest discover -s tests/fullstack -p test_account_switch.py -v
```

Результат: **2 теста, 2.221 секунды, FAILED (failures=2)**. Ожидания тестов не подогнаны к ошибочному поведению: они требуют отказа и неизменности черновика B. В обоих случаях получено `HTTP 200; черновик B изменился: True`.

Тесты сами создают и удаляют временные базы, запускают Uvicorn на свободном локальном порту и останавливают только свои процессы. Версии Python и библиотек используются из существующего .venv. Секреты, пароли и токены в отчёт не выводятся.

## QA-01 Перенос старой анкеты в другой аккаунт

Приоритет: **P1**, нарушение границы между локально загруженными данными разных аккаунтов и возможная перезапись данных нового аккаунта. Это не обход входа по произвольному user_id: сервер использует текущего вошедшего пользователя. Ошибка в том, что владелец старой формы не сверяется с владельцем текущего сеанса.

### Вариант 1 Пустые черновики

1. Войти как вымышленный A, открыть анкету. GET /api/trip-draft возвращает draft = null; клиент держит revision = 0.
2. Сохранить локальные поля A в памяти, не отправляя их.
3. Выполнить выход и вход/регистрацию как B с тем же cookie jar, моделируя другую вкладку того же браузера. У B нет черновика, его revision тоже 0.
4. Из старой вкладки отправить PUT с сохранёнными полями A и revision = 0. Запрос содержит актуальную cookie B — как браузер и отправил бы её автоматически.

Ожидается: отказ без создания записи B из старого документа A и понятное сообщение о смене аккаунта.

Фактически: HTTP 200, черновик B создан с полями A. Регрессионный тест `test_empty_stale_form_cannot_create_draft_for_new_account` падает.

### Вариант 2 Одинаковые версии существующих черновиков

1. A сохраняет свою анкету: revision = 1, количество людей = 7. Клиент загружает и удерживает документ A.
2. В том же cookie jar выполнить выход A и регистрацию B.
3. B сохраняет свою анкету: revision = 1, количество людей = 1, бюджет = 3000.
4. Старый клиент A отправляет свой документ с revision = 1, используя текущую cookie B.

Ожидается: отказ, поля и revision B остаются прежними.

Фактически: HTTP 200, B получает revision = 2 и данные старой анкеты A. Регрессионный тест `test_same_revision_stale_form_cannot_overwrite_new_account_draft` падает.

### Подтверждение и причина

Симуляция выполнена через реальные HTTP-обработчики, реальную авторизацию и SQLite. Поля/revision старой вкладки удерживаются в памяти теста, cookie jar общий и реально переключается при выходе/регистрации. Настоящая браузерная автоматизация двух вкладок в этом QA-прогоне не выполнялась; границы проверки этим явно ограничены.

Связанные места кода:

- frontend/questionnaire.js: loadDraft, строки 110–122: клиент запоминает документ и revision, но не контекст его владельца.
- frontend/questionnaire.js: saveLatest, строки 129–155: отправляется revision/preferences с текущей cookie. После 401 предлагается вход в другой вкладке без проверки, тот ли это пользователь.
- backend/drafts.py: get_draft, строки 89–93: ответ не даёт привязки загруженного контекста к владельцу для последующего сохранения.
- backend/drafts.py: save_draft, строки 96–115: revision сравнивается только с записью владельца текущей cookie; одинаковые значения разных пользователей не различаются.

Номера строк относятся к состоянию на момент этой проверки и могут измениться после исправления.

## Задание проектировщику и разработчику

1. Проектировщику определить минимальную проверяемую привязку загруженного документа к аккаунту/контексту сохранения, включая первый пустой черновик. Защита должна действовать на сервере при записи, а не только через предупреждение клиента или отдельный предварительный GET /me, после которого cookie ещё может смениться.
2. Не разрешать выбор произвольного владельца через user_id и не убирать существующую проверку текущего сеанса. Изменения собственного Fullstack-контракта описать явно и согласовать в рамках задачи исправления; контракт AI/DS не менять.
3. При смене аккаунта остановить автосохранение старого документа и показать понятное объяснение. Не переносить поля A в B и не затирать последние изменения B. Предусмотреть восстановление входа в тот же аккаунт после 401.
4. Разработчику исправлять только согласованные Fullstack-файлы. Не переписывать архитектуру, не добавлять новые туристические функции или зависимости, не читать/удалять пользовательскую базу.
5. После реализации передать QA точный перечень изменённых файлов, выбранный контракт и команды проверки. Регрессионные проверки безопасности должны сохранять смысл: отказ старому контексту и неизменность B. Не заменять их ожиданием текущего HTTP 200.

## Условия независимого ретеста

- Оба сценария QA-01 безопасно отклоняются, GET B совпадает с его исходным состоянием.
- Новый/повторный корректный ввод того же аккаунта сохраняется, обычный revision-конфликт остаётся защищённым.
- Перевход в тот же аккаунт и восстановление работы не приводят к скрытой потере параметров.
- Старые 25 тестов проходят или их изменения обоснованы реальным уточнением контракта, а не снятием защитных проверок.
- По возможности отдельно воспроизвести сценарий двумя настоящими вкладками; отсутствие такой проверки отметить.
