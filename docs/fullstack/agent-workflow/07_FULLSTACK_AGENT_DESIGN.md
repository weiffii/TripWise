## Минимальное изменение

Создать только `.codex/agents/frontend_agent.toml` и `.codex/agents/backend_agent.toml`. Каждый использует существующий формат standalone TOML: `name`, `description`, многострочный `developer_instructions`. Имя совпадает с именем файла и ключом регистрации. Не задавать model, reasoning effort, тариф, permissions или sandbox mode: использовать настройки текущего окружения.

Добавить в конец существующего `.codex/config.toml`:

```toml
[agents.frontend_agent]
description = "Интерфейс TripWise: формы, страницы, карта и взаимодействие с пользователем."
config_file = "agents/frontend_agent.toml"

[agents.backend_agent]
description = "Сервер TripWise: API, SQLite, аккаунты, сохранение и интеграция AI/DS."
config_file = "agents/backend_agent.toml"
```

Все шесть прежних регистраций сохранить без изменений. Пять прежних TOML сохранить побайтово; в analyst.toml разрешены только две адресные замены, перечисленные ниже. `[features]`, лимит `max_concurrent_threads_per_session = 3` и любые остальные существующие значения не менять. analyst, architect и qa_agent уже общие, их копии не нужны. Новые восемь ролей не означают восемь одновременных процессов.

Формат и относительные config_file сверены координатором по [standalone subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents) и [config reference](https://learn.chatgpt.com/docs/config-file/config-reference). Локальный CLI, проверенный координатором: 0.167.0-alpha.4.1. Этот проект не заявляет собственного повторного CLI-испытания.

## Содержание инструкций

- Выполнять только конкретные разрешённые файлы задания; не редактировать одни файлы параллельно с другим исполнителем. Обычная задача UI/API не разрешает править .codex/ или общие инструкции.
- Объяснять студентке на Mac небольшими шагами: назначение файлов/функций, путь данных, проверка, одна практика и вопрос. Общение с участницей объединяет основной чат, не два параллельных потока вопросов.
- Не менять требования, архитектуру, общий контракт, зависимости/сервисы и платные API без согласования. Модель разработки и LLM внутри TripWise — разные компоненты.
- Не использовать git init, reset --hard, force push, автоматический merge и удаление чужой работы. Коммит/push — по заданию с объяснением команды. Файл, коммит и публикация — разные этапы.

- Применять существующие скиллы по назначению и с фактическим чтением. Свой новый fullstack-скилл пока не создан, не объявлять его доступным. Не приравнивать созданный TOML к запущенному агенту, подготовленный промпт — к передаче, тест разработчика — к независимому QA, браузерный инструмент — к стороннему MCP.
- По завершении дать список файлов, реальные команды/результаты, ограничения и пакет для отдельного qa_agent. Не подгонять тесты; подтверждённая ошибка после исправления возвращается на независимый ретест.

Особенности `frontend_agent`:

- Ответственность: существующие HTML/CSS/JavaScript, формы, состояние загрузки/ошибок, доступность, адаптивность, расписание, карта, расстояния и чат с предварительным подтверждением. Сохранить сине-голубую палитру и текущий стек; новую сборку не вводить.
- `backend/pages/*.html` — тоже его UI-область, несмотря на расположение. Python backend не редактировать без отдельного адресного задания.
- Клиентская валидация нужна для удобства, не заменяет серверную. Сохранять контекст владельца анкеты и защиту от старых вкладок; не менять его молча при 401/смене аккаунта. Не объявлять «сохранено» до ответа сервера.

- Проверять реальное поведение браузера при доступном инструменте и указывать непроверенную раскладку/сценарии. Изменения API передавать backend/architect, не придумывать отдельный несогласованный контракт.

Особенности `backend_agent`:

- Ответственность: Python/FastAPI, HTTP-контракты, серверная валидация, SQLite, аккаунты/сеансы, изоляция пользователей, запись/загрузка, адаптеры Routing API и публичных AI/DS-функций.
- UI-шаблоны backend/pages не редактировать одновременно с frontend. Общие tests/fullstack, README/requirements/.gitignore — только один назначенный заданием владелец.
- Пользователя брать из серверного сеанса. Сохранять Origin, контекст загруженной анкеты, revision, транзакции и проверки QA-01. Не выбирать владельца по клиентскому user_id и не хранить исходный пароль.
- SQL параметризовать, ошибки возвращать без секретов; изменения схемы — безопасные, без удаления пользовательских данных. Тесты не используют настоящую базу. Локальное HTTP не объявлять готовым публичным размещением.
- Не копировать алгоритмы/математические модели напарника и не изменять ai_ds/, его тесты/данные/общие контракты без согласования. Неподдержанные групповой бюджет, transport_modes и многодневность передавать на совместное проектирование.

## Передача QA и реальные пробы

После реализации отдельный QA проверяет критерии 1–7 из 06, синтаксис, ссылочную целостность, сохранность пяти прежних TOML и только двух разрешённых замен в analyst.toml, неизменность шести старых регистраций и минимальность общих правок. В критерии 2 из 06 требование сохранности старых конфигураций применяется с этим явно разрешённым исключением для двух строк общего analyst. Изменение только конфигураций не требует повторного полного HTTP-набора приложения, если продуктовый код не затронут.

Координатор отдельно запускает каждого нового исполнителя: frontend_agent получает чтение своего TOML и просьбу объяснить существующую форму/свои границы без записи; backend_agent — чтение своего TOML и объяснение текущего draft API, защиты владельца и правил тестовой базы без записи. Каждый возвращает прочитанные пути, ответственность и границы. Эти две реальные пробы подтверждают исполнение поручений по явно прочитанным инструкциям. Автоматическое обнаружение новых ролей текущим уже начатым сеансом этим не подтверждается: его либо отдельно проверяют новым сеансом/доступным реестром, либо честно отмечают как непроверенное.

На момент этого документа реализация, пробы и независимая проверка ещё не выполнены. Координатор должен фактически передать задание исполнителю, затем QA, и записать результаты по факту.
