# Четвёртое занятие Анкета Москвы и сохранение параметров

Дата: 17 ноября 2026 года. Ветка: feature/fullstack, исходный коммит 708a762. Пользовательница выбрала Москву. Изменения этапа пока локальные, коммит и push не выполнялись.

## Что готово

Кнопка «Создать поездку» открывает защищённую анкету. В ней страна Россия и город Москва, дата/время первой и последней прогулки, число людей, бюджет питания и развлечений за всю поездку, переключатель единицы бюджета, восемь категорий интересов, три темпа и несколько способов транспорта.

Нужно выбрать 1–2 главных интереса, дополнительные не должны повторять главные. На странице показана сводка параметров. Время — московское. После корректного заполнения всех обязательных полей запускается автосохранение в SQLite. Незавершённые и ошибочные значения не сохраняются; последняя корректная версия остаётся в базе. При выходе с несохранёнными изменениями предусмотрено предупреждение браузера.

После «Готово — к моим поездкам» показывается карточка «Черновик анкеты · Маршрут не построен». По «Продолжить анкету» восстанавливаются параметры. Пока хранится одна активная анкета на пользователя; готовые маршруты будут отдельной сущностью.

Каталог обязательных мест пока не подключён: поиск отключён с объяснением. Не добавлялись выдуманные POI или самостоятельно собранные данные вместо модуля напарника. Гостиница, начало/конец каждого дня по адресу, алгоритм многодневности, реальная маршрутизация и смешанный транспорт не утверждены и не реализованы. Транспорт, группа и даты на этом шаге только сохраняются как входные пожелания.

## Файлы и связь частей

Новые файлы: backend/drafts.py, backend/pages/questionnaire.html, frontend/questionnaire.js, tests/fullstack/test_drafts.py и этот отчёт.

Изменены backend/main.py (подключение API и защищённой страницы, создание таблицы при старте), backend/pages/trips.html и frontend/trips.js (карточка черновика), frontend/styles.css (оформление анкеты), tests/fullstack/test_accounts.py (общие средства изолированного HTTP-тестирования), README.md и документ продуктовых решений. Данные и код AI/DS не менялись, новые зависимости не устанавливались.

HTML даёт поля, JavaScript собирает параметры в JSON и отправляет их на PUT /api/trip-draft. Python проверяет данные заново, определяет владельца по сеансу и сохраняет JSON в таблице trip_drafts. GET /api/trip-draft загружает только текущую анкету этого пользователя.

Это позволяет объяснить на защите различие: браузер показывает и собирает, backend проверяет и ограничивает доступ, SQLite хранит. Сохранённые пожелания ещё не являются рассчитанным маршрутом.

## Формат обмена внутри Fullstack

Пример тела сохранения, не контракт интеллектуального модуля:

```json
{
  "revision": 0,
  "preferences": {
    "schema_version": "fullstack-draft-0.1",
    "country_code": "RU",
    "city": "Москва",
    "timezone": "Europe/Moscow",
    "first_walk_at": "2026-11-20T15:00:00+03:00",
    "last_walk_end_at": "2026-11-22T18:00:00+03:00",
    "travelers": 3,
    "budget_amount": "15000",
    "budget_currency": "RUB",
    "budget_basis": "per_person",
    "budget_scope": "trip_food_and_entertainment",
    "primary_interests": ["history", "museums"],
    "secondary_interests": ["nature"],
    "pace": "balanced",
    "transport_modes": ["walking", "public_transit"],
    "required_poi_ids": []
  }
}
```

revision = 0 означает первый черновик. Каждое успешное сохранение увеличивает номер. Если другая вкладка уже обновила анкету, запрос со старым номером отклоняется с 409; предыдущие новые данные не затираются. JavaScript отправляет сохранения последовательно и замечает изменения, сделанные во время ожидания ответа.

API не принимает user_id от браузера. Страна/город/валюта/часовой пояс для этого среза фиксированы, неизвестные поля отклоняются. Цена валидируется как Decimal с не более чем двумя знаками после запятой; отрицательные и бесконечные суммы не допускаются. Ноль допустим. Количество людей — целое от 1 до 100, бюджет не выше 1 млрд рублей: это технические пределы текущей формы, а не выводы пользовательского исследования. Даты должны содержать время и смещение Москвы, окончание позже начала. Проверка «поездка в будущем» пока не реализована.

Полный UserPreferences из AI/DS 0.1 имеет другие поля. Перед интеграцией нужны совместное решение по группе и бюджету, массиву transport_modes вместо одного transport, доступным интервалам первого/последнего дня и многодневности. Не преобразовывать их молча с потерей смысла.

## Фактические проверки

Команда: .venv/bin/python -W error::ResourceWarning -m unittest discover -s tests/fullstack -v.

Результат: 25/25 тестов прошли (13 прежних аккаунтов, 12 новых черновиков), без ResourceWarning. Запуск на Python 3.13/macOS; реальные HTTP-запросы, временные SQLite-базы и отдельные серверы. База пользовательницы и её сервер на 8765 не затронуты.

Проверены загрузка пустого черновика, точное восстановление значений, бюджет/группа/несколько видов транспорта, обновление версии, конфликт устаревшей записи без потери данных, недоступность чужой анкеты, отказ без входа, ошибочные даты и смещения, числовые границы и boolean вместо числа, категории/дубли/пересечения, запрет выдуманных POI и user_id, отказ чужому Origin, сохранность после перезапуска и недоступность шаблона через статический путь. Некорректное обновление не портит последнюю сохранённую версию. Прежние тесты входа повторены из-за изменения общей серверной инициализации.

Через настоящий браузер в узкой области пройдено:

1. Регистрация вымышленного аккаунта, «Создать поездку», открытие анкеты.
2. Заполнение дат 20–22 ноября 2026, трёх людей, бюджета 15 000, двух главных интересов, одного дополнительного и двух видов транспорта.
3. Подтверждено автосохранение. Сводка при бюджете на человека: 45 000 ₽ на компанию; после переключения на компанию: 15 000 ₽.
4. Окончание раньше начала блокирует завершение; после исправления сохраняется корректная версия.
5. Завершение, карточка черновика, повторное открытие: даты, люди, бюджет, единица бюджета, главные/дополнительные интересы и транспорт восстановлены.

При проверке сообщения об ошибках обнаружено, что общий текст «заполните даты, бюджет и главные интересы» не объясняет обратный порядок уже заполненных дат. Исправлено: показывается сообщение конкретного невалидного поля. Повторный браузерный прогон подтвердил текст «Окончание последней прогулки должно быть позже начала первой», затем исправление дат и успешное сохранение. Скриншот итоговой карточки сохранён отдельно для показа участнице. Исправление относится к конкретной проверке интерфейса; более широкие пользовательские тесты ещё не проводились.

Непроверенное вручную: широкая раскладка, конфликт двух одновременно редактирующих вкладок, медленная сеть/таймаут при сохранении и срабатывание предупреждения выхода. Конфликт версий проверен на уровне реального HTTP. Выдача страницы не доказывает поддержку алгоритмом этих параметров. Тестовый сервер остановлен после проверки.

Для структуры анализа и проверки применены существующие инструкции analyst-requirements и qa-integration-check чтением и работой основного агента. Отдельный независимый субагент, сторонний MCP, пользовательские интервью на этом этапе не выполнялись.

Официальные источники для серверной валидации: [Pydantic — validators](https://pydantic.dev/docs/validation/latest/concepts/validators/), [типы дат и Decimal](https://pydantic.dev/docs/validation/latest/api/pydantic/standard_library_types/).

## Практика участницы

Перезапустить свой сервер прежней командой из README, войти в аккаунт, открыть «Создать поездку». Заполнить анкету, дождаться сообщения о сохранении, вернуться в «Мои поездки» и открыть её снова. Проверить, что значения восстановились. Готовый туристический маршрут на этом этапе не появится.

Вопрос: если параметры восстанавливаются после перезапуска браузера и сервера, где они хранятся — только в JavaScript страницы или в SQLite на стороне сервера?

Следующее действие после самостоятельной проверки — коммит, затем сверка свежего AI/DS-кода и согласование точного контракта с напарником до подключения генерации.
