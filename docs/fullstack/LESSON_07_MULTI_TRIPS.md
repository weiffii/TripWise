# Занятие 7. Несколько поездок и независимые карточки

Дата: 21 ноября 2026. Пользователь уточнил: каждая сохранённая поездка остаётся, нужны редактирование и удаление. Это заменяет прежнюю модель одной активной анкеты, описанную в занятии 6. Сохраняются **анкеты параметров**, не рассчитанные AI-маршруты.

## Что изменилось

В «Моих поездках» всегда есть «Создать новую поездку». Она открывает пустую форму и не изменяет прежние записи. Каждое явное сохранение новой формы создаёт отдельную карточку. «Редактировать» открывает выбранную анкету; «Удалить» запрашивает подтверждение и должно удалять только выбранную запись. Логотип на трёх страницах ведёт на главную.

Основных интересов можно выбрать от одного до всех восьми; прежний максимум два снят в UI и серверной модели. Дополнительные не пересекаются с основными. Разделы направления/времени, компании/бюджета, интересов, темпа/транспорта и мест получили локальные декоративные иллюстрации и оформление карточками. Новых UI-зависимостей нет.

## ID и revision простыми словами

ID — постоянный номер отдельной анкеты. Например, Париж может иметь id 11, Токио — id 12. Редактирование /api/trips/11 изменяет Париж, а не последний открытый город. Номер не является разрешением доступа: сервер дополнительно проверяет владельца по сеансу.

Revision — номер версии этой записи. Если Париж открыт в двух вкладках с revision 1 и одна сохранила revision 2, другая не может молча перезаписать свежие данные старой revision 1. Сервер вернёт конфликт 409. Это защищает выбранную карточку, не блокируя независимый Токио.

POST /api/trips создаёт новую запись с UUID попытки создания; PUT /api/trips/{id} редактирует выбранную; DELETE с revision удаляет выбранную после подтверждения UI. Все изменения требуют Origin, сеанс и исходный owner-context. Чужие id недоступны. Новая форма ничего не записывает до кнопки.

Если ответ создания потерялся, клиент не знает, успел ли сервер сохранить. Повтор по отдельному нажатию посылает прежний body и UUID: сервер возвращает прежнюю запись без дубля. Новые локальные правки не досылаются автоматически. После определённого 422 можно исправить значения и отправить новый снимок — QA отдельно проверил различие этих случаев.

## Старые данные и запуск

Рабочая таблица теперь saved_trips. Однократная транзакционная миграция multi-trips-v1 переносит старую анкету из trip_drafts с прежними параметрами, владельцем, revision и временем. Маркер миграции предотвращает дубли и восстановление удалённой карточки после перезапуска. trip_drafts остаётся архивом, не вторым изменяемым источником данных. Старый API /api/trip-draft связан только с legacy-v1, не с последней новой поездкой.

Перед обновлением основного сервера координатор создал SQLite-копию через sqlite.backup: runtime/tripwise-before-multi-<time_ns>.sqlite3 с правами 0600, без вывода содержимого. runtime исключена из Git. Затем обновлённый сервер 8765 успешно прошёл startup с миграцией; /api/health вернул ok. Тестовые серверы остановлены. Новые изменения пока не закоммичены и не отправлены на GitHub.

## Фактические проверки

Независимый QA применил qa-integration-check: **58/58 HTTP-тестов прошли**, 34.213 с, без ResourceWarning, на временных БД и собственных портах. Подтверждены независимость двух анкет, правка/удаление одной без влияния на другую, владельцы, версии, создание без дублей, миграция/перезапуск, все восемь интересов и прежние регрессии.

QA исполнил настоящий JS через Node VM с контролируемыми DOM/fetch — PASS. Проверены новый POST, редактирующий PUT, отсутствие автосохранения, снимок и правки во время запроса, потерянный ответ/UUID, исправление 422, все 8 интересов, Delete cancel/error/success с правильными id/revision/owner. Это клиентская логика, не настоящий браузерный диалог.

Координатор в настоящем браузере на временном сервере 8774 зарегистрировал вымышленного пользователя, создал Париж со всеми 8 интересами и бюджетом 600, затем Токио 800. New показал пустую форму. Edit изменил Париж на 650, а Токио остался 800. Обе карточки сохранились; снимок /tmp/tripwise-multiple-trips.png временный и не гарантируется после очистки /tmp.

**Подтверждение удаления в настоящем браузере не завершено:** getJsDialog/close блокировались CDP timeout. Это ограничение проверки, не установленный дефект удаления. API и JS-логика прошли; отмену и подтверждённое удаление учебной карточки следует проверить вручную. Нельзя заявлять, что UI-delete уже проверен успешно.

## Практика и следующий шаг

Создайте две учебные анкеты. Измените бюджет первой и убедитесь, что вторая не поменялась. Нажмите удаление ненужной учебной карточки, сначала отмените и проверьте сохранность; затем подтвердите и проверьте исчезновение только выбранной карточки. Это оставшаяся ручная проверка native-диалога.

Вопрос: чем ID анкеты отличается от revision и почему знание ID не должно давать доступ другому аккаунту?

Генерация, расписание, карта, Routing API, AI-редактирование и сохранение построенного маршрута пока не подключены. AI/DS напарника не получил поддержку 8 основных интересов автоматически; нужен согласованный адаптер без молчаливого усечения. Следующий этап — [пакет интеграции](NEXT_INTEGRATION_HANDOFF.md). TASKS.md и сроки не менялись, готовность MVP этим занятием не заявляется.
