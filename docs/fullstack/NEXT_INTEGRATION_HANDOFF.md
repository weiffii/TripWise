## Реальные точки вызова снимка

```python
from ai_ds.data import load_pois, process_pois
from ai_ds.recommendation import recommend, RecommendationError
from ai_ds.routing import build_route, RoutingError

records = load_pois(path)                    # JSON из локального файла
pois, quality = process_pois(records)         # принятые записи + отчёт качества
recommendation = recommend(preferences, pois, evaluated_at=aware_datetime)
route = build_route(preferences, pois, recommendation,
                    travel_times, routing_context)
```

Это сигнатуры из чтения кода; фрагмент не запускался в данной задаче. `evaluated_at` необязателен и полезен для воспроизводимых тестов. Перед рекомендациями проверить `quality['summary']['rejected_count']`, происхождение и пригодность набора. `RecommendationError.response()` формирует структурированный `VALIDATION_ERROR`; ошибки Routing различаются по коду, их нельзя подменять пустым успешным маршрутом. В `routing.py` сигнатура с **пятью** параметрами, хотя ранний общий контракт ещё показывает будущую версию с четырьмя.

Модель рекомендаций снимка — `lexicographic-v0.1`; модель однодневного Routing — `day-enumeration-v0.1`. Новых математических коэффициентов Fullstack не добавляет. HTTP-сервер должен оборачивать согласованные публичные функции, а не копировать алгоритмы.

## Какие JSON должны встретиться в адаптере

Сокращённый пример целевого профиля AI/DS; это **синтетический пример структуры**, не автоматически согласованная адаптация новой анкеты:

```json
{
  "schema_version": "0.1",
  "destination": {"country_code": "RU", "city": "Москва"},
  "date_start": "2026-11-19",
  "date_end": "2026-11-19",
  "timezone": "Europe/Moscow",
  "primary_interests": ["history"],
  "secondary_interests": [],
  "pace": "balanced",
  "transport": "walking",
  "budget": {"amount": 15000, "currency": "RUB", "scope": "trip_food_and_entertainment"},
  "required_poi_ids": [],
  "top_k": 5
}
```

Общий документ описывает JSON-запрос с `schema_version`, `preferences` и `pois`; фактический CLI `ai_ds.demo` читает профиль и POI из **двух отдельных файлов** (`--preferences` и `--pois`), а библиотечная функция принимает их отдельными аргументами. POI — полный объект контракта, включая координаты/null, категории, рейтинг/null, длительность/null, стоимость/null, availability и provenance. Для реальной записи требуется `provenance.is_synthetic=false` и `retrieved_at`; одного настоящего названия места недостаточно. Неизвестная цена и неизвестные часы остаются неизвестными.

Ответ рекомендаций: `schema_version`, `model_version`, `items` с `poi_id/rank/score/reasons`, `excluded`, `required_poi_ids`, `warnings`, `constraint_checks`. Названия и координаты для карточек разрешаются через тот же снимок полного POI-набора.

Вход Routing дополнительно содержит:

- `routing_context`: `day_start`, `day_end`, `endpoint_policy='first_last_poi'`, `declared_pace`, `max_active_seconds`, `rest_after_visit_seconds`. Числовые лимиты не выводятся из выбранного темпа автоматически.
- `travel_times`: один `mode`, `basis`, `source_id`, массив **направленных** `pairs`. У каждой пары `from_poi_id`, `to_poi_id`, `status` (`known/unknown/unreachable`), `duration_seconds`, `distance_meters`. Отсутствующая пара, неизвестное время и нулевой переход — разные состояния.

Ответ Routing содержит `days` с `date`, `visits`, `breaks`, `legs`; глобальные `status`, `warnings`, `constraint_checks`, `unplaced_required_poi_ids`. Не считать список мест доказательством выполнимости: текущая модель оставляет общий статус `unknown`, бюджет `not_checked`, часы `unknown` даже при найденном расписании.

## Отличия от новой анкеты

| Анкета Fullstack | Снимок AI/DS | Что решить |
|---|---|---|
| `fullstack-draft-0.1` | `0.1` | Явный адаптер и его версия, а не подмена идентификатора |
| Дата/время первой и последней прогулок, возможны разные дни | Routing принимает один день; нужны дневные окна | Многодневная поддержка владельцем Routing или явно согласованный ограниченный первый сценарий |
| `transport_modes` — несколько | `transport` и матрица одного режима | Как выбирается режим и как показывается неподдержанный выбор |
| `travelers`, `traveler_counts` | Эти поля отсутствуют | Какие ограничения реально учитываются и какие пока только сохраняются |
| Бюджет Decimal-строкой; на человека/компанию | Число в `budget.amount`, без `budget_basis` | Семантика суммы, точность JSON-адаптера и обработка общего бюджета |
| RUB/USD/EUR/CNY по новому срезу | Проверяется трёхбуквенный код; конверсия и бюджетные ограничения не реализованы | Сравнимость с ценами POI и честное предупреждение о непроверенном бюджете |
| Обязательные места пока отключены, сервер принимает только пустой список | ID обязаны существовать в том же наборе | Настоящий каталог, стабильные ID, проверка города и доступности |
| Темп — три значения | Нужны явные активные лимиты и отдых | Кто утверждает правила и значения, без произвольных defaults |
| Нет `top_k` в форме | Обязателен положительный `top_k`; Routing максимум восемь уникальных кандидатов | Политика числа кандидатов, учёт обязательных мест сверх top-K |

## Пять вопросов для встречи с Участником 1

1. **Какой коммит и реальный набор Москвы можно интегрировать?** Нужны точный путь/формат набора, provenance, отчёт качества, пример успешного публичного вызова, права/атрибуция источника. Синтетический fixture подходит для технического теста, но не пользовательской выдачи.
2. **Какой первый сквозной сценарий реально поддержан?** Многодневная поездка нужна продукту; если сейчас только один день и walking, нужно совместно выбрать ограниченный промежуточный сценарий и явно сообщать ограничения, сохранив остальные ответы анкеты.
3. **Что означает бюджет и состав группы для модели?** Согласовать per-person/group, детей/пожилых, валюту и неизвестные цены. Не обещать возрастные ограничения/скидки и пересчёт, которых в алгоритме нет.
4. **Какие дневные окна и лимиты передавать?** Кто утверждает max_active/rest для темпа, endpoint_policy и границы дня; ранее решение об отеле отложено. Не принимать first_last_poi молча за окончательное продуктовое решение.
5. **Какой источник настоящих пеших переходов и как передаём ошибки?** Нужны выбранный провайдер, ответственный за доступ/квоту, формат направленных пар, geometry/navigation_url и время обновления. Добавление сервиса/зависимости согласуется отдельно; геометрическая оценка и тестовая матрица не заменяют пешую навигацию.

## Что Fullstack может готовить отдельно

- Завершить текущую анкету и независимую проверку сохранения новых полей.
- Подготовить описание HTTP-адаптера и view-model карточек без изменения общего контракта.
- Подготовить интерфейс поиска/выбора обязательных мест и состояния «каталог недоступен / пусто / ошибка / нет результатов»; реальный выбор активировать после проверенного набора.
- Подготовить отображение расписания, предупреждений, неизвестных значений и ошибок на явно подписанных тестовых данных в тестах/дизайн-превью, не в реальной пользовательской выдаче.
- Спроектировать сохранение снимка результата с версиями данных/модели и владельцем аккаунта; новую схему/API представить до реализации. Нынешний черновик не выдавать за сохранённый маршрут.

## Что зависит от совместной интеграции

Реальная выдача POI требует проверенного каталога и владельца его обновления. Генерация требует доступных модулей согласованной версии и явного адаптера всех неподдержанных ответов анкеты. Расписание требует дневных правил и данных переходов. Карта реального маршрута требует координат, выбранной карты/атрибуции и, для пеших линий/времени, согласованного Routing API. Нельзя сливать ветку, переписывать чужой код или устанавливать внешние зависимости по одному этому документу.
