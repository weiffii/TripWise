# Проверка качества рекомендательной системы TripWise

## 1. Назначение

Этот скилл предназначен для систематической проверки качества рекомендательной системы TripWise.

Цель — убедиться, что алгоритм действительно учитывает предпочтения туриста, корректно обрабатывает ограничения и формирует объяснимые рекомендации.

Проверять необходимо не только отсутствие программных ошибок, но и качество полученного результата.

## 2. Когда использовать

Применять скилл:

- после первой реализации алгоритма рекомендаций;
- после изменения формул или коэффициентов;
- при добавлении новых факторов ранжирования;
- после изменения структуры входных данных;
- при сравнении нескольких методов рекомендаций;
- перед интеграцией с Routing Agent;
- при обнаружении неожиданных рекомендаций.

## 3. Подготовка

Перед началом проверки:

1. Изучить AGENTS.md.
2. Найти утверждённые требования к рекомендациям.
3. Изучить действующую математическую модель.
4. Проверить структуру входных и выходных данных.
5. Определить используемый набор достопримечательностей.
6. Найти существующие тесты и метрики.
7. Проверить, какие характеристики данных реально доступны.

Не придумывать отсутствующие требования или утверждённые коэффициенты.

Если модель ещё не согласована, сначала указать, какие решения требуют утверждения.

## 4. Проверка персонализации

В TripWise используются восемь категорий:

- музеи;
- история;
- природа;
- кафе;
- развлечения;
- шопинг;
- смотровые площадки;
- необычные места.

Пользователь выбирает одну или две основные категории интересов. Остальные выбранные категории могут быть дополнительными.

Проверить:

1. Влияют ли основные интересы на итоговое ранжирование.
2. Имеют ли основные интересы больший приоритет, чем дополнительные.
3. Изменяются ли рекомендации при изменении интересов пользователя.
4. Учитываются ли объекты, относящиеся к нескольким категориям.
5. Не исчезают ли подходящие объекты из-за ошибок обработки категорий.
6. Как работает система при недостаточном количестве подходящих мест.

## 5. Проверка популярности и рейтингов

TripWise должен преимущественно рекомендовать популярные и качественные достопримечательности с учётом персональных интересов.

Проверить:

- влияние популярности на итоговую оценку;
- влияние рейтинга;
- сопоставимость показателей;
- обработку отсутствующих рейтингов;
- отсутствие необоснованного преимущества объектов с неполными данными;
- влияние интересов пользователя на итоговый порядок.

Не считать популярность и рейтинг одинаковыми показателями.

Не назначать неизвестным значениям произвольные оценки.

## 6. Проверка математической модели

Изучить используемую формулу ранжирования.

Для каждого показателя определить:

- смысл;
- источник данных;
- диапазон значений;
- способ нормализации;
- влияние на итоговую оценку;
- ограничения применения.

Проверить:

1. Корректность вычислений.
2. Отсутствие ошибок нормализации.
3. Обоснованность коэффициентов.
4. Устойчивость к отсутствующим значениям.
5. Отсутствие некорректного доминирования одного фактора.
6. Соответствие модели утверждённым требованиям.

Не изменять модель и её коэффициенты без согласования.

Если обнаружены проблемы, подготовить предложения по исправлению.

## 7. Тестовые профили туристов

Создать воспроизводимый набор тестовых сценариев.

Обязательно предусмотреть:

### Профиль 1. История и музеи

Основные интересы — история и музеи.

Проверить приоритет соответствующих достопримечательностей.

### Профиль 2. Природа и необычные места

Основные интересы — природа и необычные места.

Проверить изменение рекомендаций относительно первого профиля.

### Профиль 3. Развлечения и шопинг

Основные интересы — развлечения и шопинг.

Проверить соответствие выдачи выбранным категориям.

### Профиль 4. Ограниченный бюджет

Использовать профиль с ограниченным бюджетом.

Проверить, как алгоритм учитывает стоимость и неизвестные цены.

### Профиль 5. Недостаток данных

Использовать объекты с пропущенными характеристиками.

Проверить устойчивость алгоритма и корректную обработку неизвестных сведений.

Тестовые профили могут быть синтетическими, но должны быть явно обозначены как тестовые.

## 8. Метрики качества

Использовать метрики, соответствующие доступным данным и целям проверки.

Возможные направления оценки:

- соответствие рекомендаций интересам;
- качество порядка рекомендованных объектов;
- разнообразие рекомендаций;
- доля объектов с достаточными данными;
- устойчивость выдачи;
- наличие повторяющихся объектов;
- выполнение ограничений.

Если доступны подтверждённые пользовательские оценки релевантности, рассмотреть Precision@K, Recall@K или NDCG@K.

Не рассчитывать эти метрики без необходимой разметки.

Не выдавать результаты проверки на синтетических профилях за подтверждённое качество рекомендаций у реальных пользователей.

## 9. Сравнение алгоритмов

При сравнении нескольких вариантов:

1. Использовать одинаковые входные данные.
2. Фиксировать параметры эксперимента.
3. Применять одинаковые критерии оценки.
4. Сравнивать полученные результаты.
5. Анализировать преимущества и недостатки.
6. Учитывать сложность реализации и скорость работы.
7. Предлагать обоснованный выбор.

Не объявлять один алгоритм лучшим только на основании одного удачного примера.

## 10. Проверка взаимодействия с Routing Agent

Перед передачей рекомендаций маршрутизатору проверить:

- наличие необходимых идентификаторов;
- соответствие действующему интерфейсу;
- наличие координат или корректную маркировку их отсутствия;
- отсутствие некорректных дубликатов;
- корректность итоговых оценок;
- наличие данных об ограничениях;
- воспроизводимость результатов.

Recommendation Agent отвечает за ранжирование мест.

Окончательный выбор последовательности посещений, распределение по дням и проверку выполнимости выполняет Routing Agent.

## 11. Автоматизация тестирования

При необходимости создавать автоматические тесты на Python.

Проверять:

- корректные входные данные;
- пустые наборы;
- отсутствующие характеристики;
- некорректные значения;
- различные профили туристов;
- граничные случаи;
- повторяемость результатов при одинаковых условиях.

Использовать существующую инфраструктуру тестирования проекта.

Не изменять утверждённую математическую модель при написании тестов.

## 12. Отчёт о проверке

После выполнения подготовить отчёт:

1. Проверяемая версия алгоритма.
2. Используемый набор данных.
3. Тестовые профили.
4. Проверенные требования.
5. Использованные метрики.
6. Полученные результаты.
7. Обнаруженные ошибки.
8. Ограничения проверки.
9. Предложения по улучшению.
10. Готовность к передаче Routing Agent.

Если проверка не была выполнена, прямо указать причину.

## 13. Ограничения

- Не выдумывать результаты тестов.
- Не изменять утверждённую модель без согласования.
- Не использовать неподтверждённые данные как реальные.
- Не подменять пользовательское тестирование синтетическими сценариями.
- Не добавлять новые ML-модели без практического обоснования.
- Не менять код маршрутизатора.
- Не изменять frontend и backend других участников.
- Не утверждать, что рекомендации качественные, только потому что код выполняется.

## 14. Критерии завершения

Проверка считается выполненной, если:

1. Проверены применимые функциональные требования.
2. Использованы воспроизводимые тестовые сценарии.
3. Выполнены необходимые автоматические тесты.
4. Проанализировано влияние основных факторов ранжирования.
5. Обнаруженные ошибки зафиксированы.
6. Подготовлен отчёт с результатами и ограничениями.
7. Понятно, готов ли алгоритм к интеграции.

Все отчёты и объяснения писать на русском языке.
