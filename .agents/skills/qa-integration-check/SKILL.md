# Комплексное тестирование и проверка интеграции TripWise

## 1. Назначение

Этот скилл предназначен для проверки работоспособности TripWise как единой системы.

Цель — обнаруживать ошибки взаимодействия компонентов, проверять основные пользовательские сценарии и оценивать готовность проекта к использованию и демонстрации.

Основной исполнитель — QA Agent.

Проверять необходимо не только отдельные функции, но и полный путь данных от ввода параметров пользователем до отображения готового маршрута.

## 2. Когда использовать

Применять скилл:

- после интеграции двух или более компонентов;
- после изменения API или структуры данных;
- после объединения изменений из разных веток;
- после исправления интеграционных ошибок;
- перед созданием релиза;
- перед демонстрацией проекта;
- при обнаружении некорректного поведения приложения.

## 3. Подготовка

Перед проверкой:

1. Изучи AGENTS.md.
2. Изучи действующую архитектуру TripWise.
3. Проверь структуру репозитория.
4. Найди инструкции по запуску.
5. Определи используемые технологии.
6. Изучи утверждённые API-контракты.
7. Найди существующие тесты.
8. Определи доступные внешние сервисы.
9. Проверь состояние тестовой среды.

Не выдумывай команды запуска, пути файлов или структуру проекта.

Не изменяй конфигурацию среды без необходимости.

## 4. Определение области проверки

Перед запуском тестов установи:

- какие компоненты изменились;
- какие интерфейсы затронуты;
- какие пользовательские сценарии зависят от изменений;
- какие существующие тесты необходимо повторить;
- какие новые проверки нужны.

Если изменение локальное, сначала проверь затронутый компонент и его зависимости.

Перед релизом выполняй расширенную проверку основных сценариев платформы.

## 5. Проверка запуска приложения

Проверь:

- установку необходимых зависимостей;
- корректность конфигурации;
- запуск frontend;
- запуск backend;
- доступность необходимых сервисов;
- подключение базы данных, если она используется;
- отсутствие критических ошибок запуска;
- доступность приложения после запуска.

Используй существующие инструкции проекта.

Не раскрывай значения переменных окружения и API-ключей в отчёте.

Если приложение не запускается, зафиксируй ошибку и условия её возникновения.

## 6. Проверка API-контрактов

Для интегрируемых компонентов проверь:

1. Соответствие форматов запросов.
2. Соответствие форматов ответов.
3. Наличие обязательных полей.
4. Корректность типов.
5. Обработку необязательных полей.
6. Проверку входных данных.
7. Обработку ошибок.
8. Совместимость версий интерфейсов.

Не изменяй утверждённые контракты самостоятельно.

Если интерфейсы несовместимы, определи конкретное расхождение и передай вопрос ответственным агентам.

## 7. Проверка передачи туристических данных

Проверь путь данных:

Data Agent → Recommendation Agent.

Убедись, что:

- данные соответствуют утверждённой схеме;
- идентификаторы сохраняются;
- категории корректно передаются;
- координаты имеют правильный формат;
- отсутствующие характеристики корректно обрабатываются;
- ошибки данных не приводят к неконтролируемому сбою.

При необходимости используй data-poi-quality-check.

Не исправляй исходные туристические данные на основании предположений.

## 8. Проверка рекомендаций и маршрутизации

Проверь взаимодействие:

Recommendation Agent → Routing Agent.

Убедись, что:

- рекомендации передаются в ожидаемом формате;
- идентификаторы объектов не теряются;
- оценки корректно обрабатываются;
- обязательные места сохраняются;
- отсутствующие характеристики не вызывают сбой;
- маршрутизатор получает необходимые параметры;
- ошибки корректно возвращаются вызывающему компоненту.

Для углублённой проверки используй существующие скиллы:

- recommendation-evaluation;
- route-validation.

Не изменяй математические модели самостоятельно.

## 9. Проверка взаимодействия с backend

Проверь:

- передачу параметров пользователя;
- вызов рекомендательной системы;
- вызов маршрутизатора;
- получение структурированных результатов;
- обработку ошибок;
- сохранение маршрута;
- повторную загрузку сохранённого маршрута;
- корректность передачи результатов frontend.

Не считай успешный HTTP-ответ доказательством корректности данных.

## 10. Проверка frontend

Проверь основные пользовательские сценарии:

1. Открытие приложения.
2. Ввод города и дат.
3. Выбор интересов.
4. Указание бюджета.
5. Выбор темпа путешествия.
6. Выбор транспорта.
7. Добавление обязательных мест.
8. Генерация маршрута.
9. Просмотр расписания.
10. Просмотр карты.
11. Сохранение маршрута.
12. Повторное открытие маршрута.

Проверь корректность отображения полученных данных и сообщений об ошибках.

Если автоматизированного браузерного тестирования нет, укажи необходимые ручные проверки.

Не утверждай, что интерфейс протестирован, если он фактически не открывался.

## 11. Проверка Route Assistant

Проверь полный сценарий AI-редактирования:

1. Пользователь открывает готовый маршрут.
2. Отправляет текстовый запрос.
3. LLM интерпретирует запрос.
4. Система определяет необходимые изменения.
5. Вызываются разрешённые инструменты.
6. Пересчитывается затронутая часть маршрута.
7. Проверяются ограничения.
8. Пользователю показываются предлагаемые изменения.
9. Пользователь подтверждает или отклоняет их.
10. Система корректно сохраняет подтверждённый результат.

Дополнительно проверь:

- недоступность LLM;
- некорректный ответ модели;
- невозможный запрос;
- конфликт с обязательными местами;
- сохранение исходного маршрута при отказе;
- отсутствие несанкционированных изменений.

Не выполняй платные вызовы API без разрешения.

Для воспроизводимых автоматических проверок используй заглушки внешних сервисов, явно обозначая их как тестовые.

## 12. Проверка ошибок и граничных случаев

Обязательно рассмотри:

- пустые входные данные;
- некорректные даты;
- неизвестный город;
- отсутствие подходящих достопримечательностей;
- недостаточный бюджет;
- конфликтующие обязательные места;
- недоступность внешнего API;
- отсутствие интернет-соединения;
- превышение допустимого времени ожидания;
- некорректные данные от внешнего сервиса;
- повторные запросы пользователя.

Проверяй, что система обрабатывает такие ситуации предсказуемо и не теряет пользовательские данные.

## 13. Автоматизация тестирования

Используй существующие инструменты проекта.

При необходимости создавай:

- модульные тесты;
- интеграционные тесты;
- API-тесты;
- сквозные тесты;
- регрессионные тесты.

Автоматизируй воспроизводимые проверки.

Для внешних сервисов используй контролируемые тестовые ответы, когда реальные вызовы не нужны.

Не заменяй тесты на реальные данные исключительно синтетическими сценариями, если задача требует проверки фактической интеграции.

Не изменяй ожидаемые результаты тестов только ради успешного прохождения.

## 14. Диагностика ошибок

Для каждой обнаруженной проблемы зафиксируй:

1. Название ошибки.
2. Затронутый компонент.
3. Условия возникновения.
4. Шаги воспроизведения.
5. Ожидаемый результат.
6. Фактический результат.
7. Логи или другие доступные подтверждения.
8. Предполагаемую причину.
9. Уровень серьёзности.
10. Ответственного агента.
11. Предлагаемый способ исправления.

Не выдавай предполагаемую причину за подтверждённую.

Если ошибка находится на стыке компонентов, сообщи об этом Architect Agent.

## 15. Исправление и повторная проверка

Небольшие локальные ошибки можно исправлять в границах согласованной задачи.

Если исправление затрагивает чужой компонент, архитектуру, математическую модель или API-контракт, сначала получи согласование.

После исправления:

1. Повтори тест, выявивший ошибку.
2. Проверь связанные компоненты.
3. Выполни необходимые регрессионные тесты.
4. Зафиксируй результаты.
5. Обнови статус проблемы.

Не утверждай, что ошибка исправлена, если повторная проверка не выполнена.

## 16. Проверка готовности к демонстрации

Перед защитой TripWise 2 декабря 2026 года проверь:

- воспроизводимый запуск приложения;
- доступность необходимых сервисов;
- ввод параметров путешествия;
- генерацию рекомендаций;
- построение маршрута;
- отображение расписания и карты;
- работу основных функций сохранения;
- доступность заявленных возможностей Route Assistant;
- обработку критических ошибок;
- отсутствие известных блокирующих проблем.

Разделяй полностью работающие функции, частично реализованные возможности и демонстрационные сценарии.

Не обозначай функцию готовой, если она проверена только на заглушках.

## 17. Отчёт о проверке

После завершения подготовь отчёт:

1. Дата и область проверки.
2. Проверенная версия проекта.
3. Используемая среда.
4. Выполненные тесты.
5. Успешные проверки.
6. Неуспешные проверки.
7. Обнаруженные ошибки.
8. Исправленные проблемы.
9. Непроверенные сценарии.
10. Ограничения тестовой среды.
11. Риски для интеграции и демонстрации.
12. Рекомендации по дальнейшей работе.

В итоговом статусе используй:

- готово;
- готово с ограничениями;
- не готово;
- недостаточно данных для оценки.

Всегда обосновывай выбранный статус.

## 18. Ограничения

- Не изменяй архитектуру без согласования.
- Не изменяй математические модели.
- Не меняй API-контракты самостоятельно.
- Не переписывай чужие компоненты без разрешения.
- Не скрывай обнаруженные ошибки.
- Не выдумывай результаты тестов.
- Не утверждай, что интеграция проверена, если тесты не проводились.
- Не подключай платные сервисы без разрешения.
- Не раскрывай секреты.
- Не удаляй пользовательские данные.
- Не выдавай тестовые заглушки за реальные интеграции.

## 19. Критерии завершения

Проверка считается завершённой, если:

1. Определена область тестирования.
2. Проверены применимые пользовательские сценарии.
3. Проверены затронутые интеграционные интерфейсы.
4. Выполнены доступные автоматические тесты.
5. Зафиксированы ошибки и ограничения.
6. После исправлений выполнены повторные проверки.
7. Подготовлен отчёт.
8. Обоснована готовность проекта или компонента.

Все отчёты, объяснения и документацию пиши на русском языке.
