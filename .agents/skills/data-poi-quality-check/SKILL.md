# Проверка качества данных TripWise

## 1. Назначение

Этот скилл предназначен для проверки качества данных о туристических объектах (POI).

Цель — выявлять ошибки, пропуски, дубликаты и противоречия, которые могут повлиять на рекомендации и построение маршрутов.

Скилл должен не только находить проблемы, но и объяснять, как они влияют на работу TripWise.

## 2. Когда использовать

Применять скилл:

- после получения данных из внешнего API;
- после нормализации и объединения данных;
- при обновлении базы достопримечательностей;
- при подготовке резервного набора;
- перед использованием нового набора в рекомендательной системе;
- при обнаружении ошибок в рекомендациях или маршрутах, которые могут быть связаны с данными.

## 3. Подготовка к проверке

Перед началом работы:

1. Изучить AGENTS.md.
2. Найти действующую схему данных POI.
3. Определить источник проверяемого набора.
4. Проверить формат и количество записей.
5. Определить обязательные и необязательные поля.
6. Проверить наличие существующих тестов и валидаторов.

Если утверждённой схемы нет, сообщить об этом. Не назначать самостоятельно новые обязательные поля.

## 4. Проверка структуры

Проверить:

- соответствие записей действующей схеме;
- наличие обязательных полей;
- корректность типов данных;
- корректность идентификаторов;
- отсутствие повреждённых записей;
- согласованность форматов значений.

Для каждой обнаруженной ошибки сохранять идентификатор объекта и описание проблемы.

## 5. Проверка географических данных

Проверить:

- широта находится в диапазоне от -90 до 90;
- долгота находится в диапазоне от -180 до 180;
- координаты представлены корректным числовым значением;
- широта и долгота не перепутаны, если это можно установить;
- координаты соответствуют указанному городу и стране, если доступен надёжный источник проверки.

Не считать координаты (0, 0) автоматически ошибочными: сначала проверить контекст.

Не исправлять координаты на основании предположений.

Если объект невозможно надёжно разместить на карте, отметить его как непригодный для маршрутизации до исправления данных.

## 6. Проверка категорий

В TripWise используются восемь категорий:

1. Музеи
2. История
3. Природа
4. Кафе
5. Развлечения
6. Шопинг
7. Смотровые площадки
8. Необычные места

Один объект может относиться к нескольким категориям.

Проверить:

- соответствие категорий утверждённому перечню;
- отсутствие некорректных значений;
- корректность преобразования категорий внешнего источника;
- наличие неоднозначных классификаций.

Не назначать категорию по одному только названию объекта, если данных недостаточно.

## 7. Поиск дубликатов

Искать возможные дубликаты по:

- идентификаторам внутри одного источника;
- внешним идентификаторам;
- нормализованным названиям;
- географической близости;
- адресам, если они доступны;
- другим признакам, предусмотренным действующей схемой.

Разделять:

- подтверждённые дубликаты;
- предполагаемые дубликаты;
- разные объекты с похожими характеристиками.

Не удалять и не объединять спорные записи автоматически.

Порог географической близости должен быть обоснован и согласован, если влияет на объединение объектов.

## 8. Проверка характеристик

Проверять доступные поля:

### Рейтинг

- корректность типа и диапазона для конкретного источника;
- наличие сведений о шкале рейтинга;
- отсутствие некорректного сравнения разных шкал.

### Популярность

- наличие источника показателя;
- понятность метода расчёта;
- сопоставимость показателей.

Не выдавать неизвестную популярность за нулевую.

### Стоимость

- корректность числовых значений;
- валюту;
- наличие информации о приблизительности цены;
- дату актуальности, если доступна.

### Часы работы

- корректность формата;
- наличие информации о днях недели;
- обработку неизвестного расписания;
- наличие противоречивых сведений.

Не считать отсутствие часов работы признаком круглосуточной доступности.

### Длительность посещения

- корректность типа и единиц измерения;
- разумность значения;
- происхождение оценки.

Если длительность является предположением, она должна быть явно обозначена.

## 9. Проверка источников и актуальности

Для каждого объекта по возможности проверять:

- источник информации;
- время получения;
- дату последнего обновления;
- ограничения использования;
- наличие противоречий между источниками.

Отсутствие даты обновления не означает, что данные заведомо устарели, но должно отражаться в отчёте.

Не утверждать, что информация актуальна, если это не проверялось.

## 10. Классификация проблем

Разделять проблемы на три уровня.

### Критическая ошибка

Проблема, из-за которой объект нельзя корректно использовать в соответствующем алгоритме.

Примеры:
- отсутствует обязательный идентификатор;
- координаты некорректны;
- запись не соответствует обязательной структуре.

### Предупреждение

Проблема, которая не всегда запрещает использование объекта, но требует внимания.

Примеры:
- возможный дубликат;
- неизвестные часы работы;
- противоречие между источниками;
- отсутствует дополнительная характеристика.

### Информационное замечание

Сведения об ограничениях или особенностях данных, не являющиеся непосредственной ошибкой.

Примеры:
- цена ориентировочная;
- показатель популярности недоступен;
- часть информации требует обновления.

Критичность зависит от того, для какой функции используется объект.

## 11. Проверка пригодности для компонентов

Отдельно определять пригодность данных для:

### Рекомендательной системы

Проверить наличие характеристик, необходимых для действующей модели ранжирования.

Если показатель отсутствует, не подставлять произвольное значение.

### Маршрутизатора

Проверить наличие корректных координат и других данных, необходимых для расчёта маршрута.

Если часы работы неизвестны, отметить ограничение проверки выполнимости.

### Отображения на сайте

Проверить наличие данных, обязательных для карточки достопримечательности по действующему API-контракту.

Не считать пригодность для одного компонента автоматическим подтверждением пригодности для остальных.

## 12. Автоматизация проверки

Если необходимые инструменты отсутствуют, создать функции автоматической проверки на Python.

При этом:

1. Использовать существующую архитектуру проекта.
2. Не добавлять новые библиотеки без необходимости.
3. Разделять проверки структуры, координат, категорий и дополнительных характеристик.
4. Создавать тесты для корректных и ошибочных записей.
5. Обеспечивать повторяемость проверки на одинаковом наборе данных.
6. Не изменять исходный набор при диагностике.

## 13. Формат отчёта

После проверки подготовить отчёт, включающий:

1. Название и источник набора данных.
2. Дату проведения проверки.
3. Количество проверенных объектов.
4. Количество записей без обнаруженных проблем.
5. Количество записей с критическими ошибками.
6. Количество записей с предупреждениями.
7. Перечень проблем с идентификаторами объектов.
8. Результаты проверки пригодности для рекомендаций и маршрутизации.
9. Предложения по исправлению.
10. Ограничения выполненной проверки.

Если одна запись содержит несколько проблем, учитывать это отдельно при подсчётах, чтобы показатели не вводили в заблуждение.

Отчёт сохранять в согласованном расположении внутри проекта.

## 14. Ограничения

- Не выдумывать отсутствующую информацию.
- Не подменять неизвестные сведения нулевыми значениями без предусмотренного правила.
- Не удалять исходные записи.
- Не объединять спорные дубликаты без согласования.
- Не изменять утверждённую схему данных.
- Не изменять алгоритмы рекомендаций и маршрутизации.
- Не выполнять платные API-запросы без согласования.
- Не считать внешний источник достоверным без проверки.
- Не заявлять об успешных тестах, если они не запускались.

## 15. Критерии завершения

Задача считается выполненной, если:

1. Проведены все применимые проверки.
2. Найденные проблемы классифицированы.
3. Определена пригодность данных для соответствующих компонентов.
4. Сформирован отчёт.
5. Автоматические проверки протестированы, если создавался новый код.
6. Указаны непроверенные характеристики и ограничения.
7. Результат можно воспроизвести.

Все отчёты, пояснения и документацию писать на русском языке.
