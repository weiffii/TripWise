# Получение и подготовка туристических данных TripWise

## 1. Назначение

Этот скилл предназначен для получения, обработки и подготовки данных о туристических объектах (POI).

Цель — сформировать единый набор данных о достопримечательностях, который смогут использовать рекомендательная система и алгоритм построения маршрутов TripWise.

Основные источники — реальные API и открытые наборы данных. Дополнительно должен поддерживаться проверенный резервный набор для демонстрации проекта.

## 2. Когда использовать

Применять скилл при:

- подключении нового источника туристических данных;
- загрузке достопримечательностей для выбранного города;
- обновлении существующего набора;
- объединении информации из разных источников;
- подготовке резервного набора;
- передаче данных другим AI/DS-компонентам.

## 3. Подготовка к работе

Перед выполнением задачи:

1. Изучить AGENTS.md.
2. Проверить существующую структуру проекта.
3. Найти действующую схему туристических объектов.
4. Проверить уже подключённые источники и библиотеки.
5. Уточнить город, необходимый объём данных и цель загрузки.
6. Проверить ограничения использования выбранного API.

Если задача требует новой зависимости, изменения схемы данных или выбора внешнего сервиса, сначала согласовать решение.

## 4. Выбор источников

При выборе источника учитывать:

- доступность API;
- наличие необходимых туристических объектов;
- качество и полноту данных;
- наличие географических координат;
- ограничения запросов;
- условия лицензирования;
- возможность обновления информации;
- стоимость использования.

Не считать все сведения из API автоматически достоверными.

Не использовать несуществующие API или неподтверждённые возможности сервисов.

## 5. Получение данных

1. Использовать существующие интеграции, если они подходят.
2. Реализовать получение данных из согласованного источника.
3. Обрабатывать ошибки подключения и запросов.
4. Учитывать ограничения количества запросов.
5. Сохранять сведения об источнике и времени получения.
6. Не включать API-ключи и другие секреты в исходный код.
7. Не изменять исходные данные без сохранения возможности восстановить их.

Если источник временно недоступен, сообщить об ошибке и предложить использование резервного набора.

## 6. Нормализация данных

Приводить полученные сведения к действующей схеме POI проекта.

Использовать согласованные категории TripWise:

- музеи;
- история;
- природа;
- кафе;
- развлечения;
- шопинг;
- смотровые площадки;
- необычные места.

Один объект может относиться к нескольким категориям.

При обработке учитывать:

- идентификаторы объектов;
- названия;
- страну и город;
- координаты;
- категории;
- рейтинг и популярность, если доступны;
- стоимость и часы работы, если доступны;
- ориентировочное время посещения;
- источник информации.

Не назначать отсутствующим характеристикам произвольные значения.

Если преобразование категории неоднозначно, отмечать объект для дополнительной проверки.

## 7. Объединение данных

При работе с несколькими источниками:

1. Сохранять сведения о происхождении данных.
2. Выявлять возможные совпадения объектов.
3. Не объединять спорные записи автоматически.
4. Учитывать различия в форматах рейтингов и других характеристик.
5. Не считать показатели из разных источников напрямую сопоставимыми без нормализации.
6. Отмечать противоречивые сведения.

Не удалять исходные записи без согласования.

## 8. Резервный набор данных

Поддерживать возможность использования заранее подготовленного набора достопримечательностей.

Резервный набор должен:

- использовать утверждённую структуру POI;
- содержать сведения об источниках;
- позволять воспроизводить тестовые сценарии;
- быть доступным при отсутствии подключения к API;
- отличаться от актуальных данных, полученных в реальном времени.

Если для тестов используются синтетические объекты, явно обозначать их как тестовые.

## 9. Подготовка к передаче данных

После обработки:

1. Проверить соответствие структуры действующей схеме.
2. Передать данные для проверки качества с использованием скилла data-poi-quality-check.
3. Отделить пригодные записи от записей, требующих дополнительной проверки.
4. Обеспечить возможность использования результата Recommendation Agent и Routing Agent.
5. Не менять интерфейсы взаимодействия без согласования.

## 10. Разработка кода

При необходимости самостоятельно создавать функции и модули для:

- получения данных из API;
- обработки ответов;
- нормализации записей;
- преобразования категорий;
- объединения источников;
- сохранения подготовленных данных.

Соблюдать существующую архитектуру проекта.

Использовать уже установленные библиотеки, если они подходят.

Писать автоматические тесты для важных преобразований и обработки ошибок.

## 11. Результат работы

После выполнения задачи сообщить:

1. Какие источники использованы.
2. Какие данные получены.
3. Сколько объектов обработано.
4. Какие преобразования выполнены.
5. Какие файлы созданы или изменены.
6. Какие тесты запускались и с каким результатом.
7. Какие проблемы обнаружены.
8. Что необходимо проверить перед использованием данных.

## 12. Критерии завершения

Задача считается выполненной, когда:

- данные получены из согласованного источника;
- результат соответствует утверждённой схеме;
- происхождение информации сохранено;
- ошибки обработки учтены;
- применимые тесты выполнены;
- данные переданы на проверку качества;
- ограничения и нерешённые проблемы зафиксированы.

Не утверждать, что данные достоверны и полностью проверены, если соответствующая проверка не проводилась.

Все объяснения и документацию писать на русском языке.
