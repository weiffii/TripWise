# Проверка туристических маршрутов TripWise

## 1. Назначение

Этот скилл предназначен для проверки туристических маршрутов, сформированных алгоритмами TripWise.

Цель — убедиться, что маршрут соответствует предпочтениям пользователя, учитывает ограничения и может быть выполнен при доступных данных.

Проверять необходимо не только программную корректность, но и логическую, временную и географическую согласованность маршрута.

Основной исполнитель — Routing Agent.

## 2. Когда использовать

Применять скилл:

- после первой реализации маршрутизатора;
- после изменения алгоритмов оптимизации;
- после формирования маршрута по дням;
- после изменения параметров пользователя;
- после редактирования маршрута через Route Assistant;
- перед интеграцией маршрутизатора с backend;
- при обнаружении ошибок в расписании;
- перед демонстрацией проекта.

## 3. Подготовка к проверке

Перед началом работы:

1. Изучить AGENTS.md.
2. Найти действующую математическую модель маршрутизации.
3. Изучить утверждённые требования TripWise.
4. Проверить структуру входных и выходных данных.
5. Получить параметры пользователя.
6. Определить используемый вид транспорта.
7. Проверить доступность данных о местах и перемещениях.
8. Найти существующие автоматические тесты.

Если необходимые сведения отсутствуют, не подменять их выдуманными значениями.

## 4. Проверка структуры маршрута

Убедиться, что:

- маршрут относится к выбранному городу или территории;
- даты соответствуют запросу пользователя;
- посещения корректно распределены по дням;
- каждая точка имеет идентификатор;
- порядок посещений однозначно определён;
- время начала и окончания посещений согласовано;
- длительность посещений неотрицательна;
- отсутствуют непредусмотренные повторения объектов;
- структура соответствует действующему API-контракту.

При обнаружении ошибки указать конкретный день и объект.

## 5. Проверка временных ограничений

Для каждого дня проверить:

1. Время начала и окончания маршрута.
2. Длительность посещения каждой точки.
3. Время перемещений между точками.
4. Наличие пересечений посещений.
5. Наличие достаточного времени для переходов.
6. Соответствие известным часам работы объектов.
7. Наличие запланированных перерывов.
8. Соблюдение ограничений по продолжительности дня.

Не считать неизвестные часы работы подтверждением того, что объект открыт.

Если временные данные приблизительные, явно указывать это.

## 6. Проверка географической согласованности

Проверить:

- наличие корректных координат;
- логичность последовательности посещений;
- отсутствие необоснованных перемещений;
- корректность используемых расстояний;
- соответствие времени перемещения выбранному транспорту;
- наличие источника маршрутных данных.

Не использовать расстояние по прямой как подтверждённое расстояние по дороге.

Если маршрутизирующий API недоступен, сообщить об ограничении проверки.

Не выдумывать улицы, повороты, остановки или пересадки.

## 7. Проверка транспорта

TripWise поддерживает три режима:

- пешком;
- автомобиль;
- общественный транспорт.

### Пеший маршрут

Проверить:

- наличие данных о переходах между соседними точками;
- расстояние каждого перехода;
- ориентировочное время;
- учёт переходов в расписании;
- корректность связи точек маршрута.

Полноценный пеший режим является приоритетом MVP.

### Автомобиль

Проверить:

- соответствие маршрута автомобильной дорожной сети;
- доступность расчётов времени;
- корректность данных маршрутизатора;
- наличие предупреждений при неполных данных.

Не считать ограничения парковки и дорожного движения проверенными, если соответствующих данных нет.

### Общественный транспорт

Проверить:

- наличие реальных данных о перемещениях;
- корректность заявленных возможностей;
- отсутствие вымышленных расписаний и пересадок;
- явную маркировку ограничений базового режима.

Не выдавать ориентировочные оценки за проверенный маршрут общественного транспорта.

## 8. Проверка обязательных мест

Если пользователь выбрал обязательные достопримечательности:

1. Проверить их наличие в маршруте.
2. Проверить отсутствие случайного удаления.
3. Проверить возможность посещения в указанные даты.
4. Определить причины невыполнимости, если они есть.
5. Предложить варианты решения конфликта.

Не исключать обязательные точки без предупреждения и согласования.

Если выполнить все ограничения невозможно, явно указать конфликт.

## 9. Проверка темпа путешествия

В TripWise используются три темпа:

- спокойный;
- сбалансированный;
- насыщенный.

Проверить соответствие маршрута действующей модели темпа.

Учитывать:

- количество посещений;
- длительность перемещений;
- общую занятость дня;
- продолжительность отдыха;
- соотношение посещений и перемещений;
- ограничения пользователя.

Не использовать произвольное фиксированное количество достопримечательностей как единственный критерий темпа.

Не назначать новые коэффициенты без согласования.

## 10. Проверка питания и бюджета

Проверить:

- учёт выбранного бюджета на питание и развлечения;
- наличие необходимых перерывов на питание согласно действующим требованиям;
- корректность расчёта известных затрат;
- наличие отметок об ориентировочных ценах;
- отсутствие выдуманных стоимостей.

Если точная цена неизвестна, не считать бюджет гарантированно соблюдённым.

При превышении бюджета указывать причину и возможные варианты исправления.

## 11. Проверка после AI-редактирования

После изменения маршрута через Route Assistant:

1. Сохранить исходную версию маршрута для сравнения.
2. Определить запрошенные пользователем изменения.
3. Проверить, что изменения действительно выполнены.
4. Проверить сохранение остальных ограничений.
5. Проверить обязательные места.
6. Повторно проверить время и перемещения.
7. Проверить отсутствие новых конфликтов.
8. Сформировать понятное описание изменений.
9. Подготовить обновлённый маршрут для подтверждения пользователем.

Не сохранять окончательные изменения без подтверждения пользователя.

Не считать результат LLM автоматически корректным.

Если запрос невозможно выполнить, объяснить причину и предложить допустимую альтернативу.

## 12. Тестовые сценарии

Создать воспроизводимые проверки для следующих случаев:

1. Однодневный пеший маршрут.
2. Многодневный маршрут.
3. Спокойный темп.
4. Насыщенный темп.
5. Обязательные достопримечательности.
6. Недостаточное время.
7. Закрытый объект.
8. Превышение бюджета.
9. Отсутствие данных о перемещениях.
10. Некорректные координаты.
11. Недостаточное количество подходящих мест.
12. Изменение маршрута через Route Assistant.
13. Конфликт между запросом AI-редактирования и обязательными местами.
14. Недоступность внешнего API.

Тестовые данные должны быть явно обозначены как тестовые.

## 13. Автоматизация

При необходимости создавать автоматические проверки на Python.

Предпочитать независимые функции проверки отдельных ограничений.

Использовать существующие инструменты тестирования проекта.

Проверять нормальные, ошибочные и граничные случаи.

Не изменять утверждённую модель оптимизации во время проверки без согласования.

После обнаружения ошибки подготовить воспроизводимый тест.

Исправление кода выполнять в пределах согласованной задачи.

После исправления повторно запускать проверку.

## 14. Формат результата

После проверки подготовить отчёт:

1. Идентификатор или описание маршрута.
2. Исходные параметры пользователя.
3. Проверенные ограничения.
4. Результаты временной проверки.
5. Результаты географической проверки.
6. Результаты проверки транспорта.
7. Выполнение обязательных посещений.
8. Соответствие темпу.
9. Результаты проверки бюджета.
10. Обнаруженные ошибки и предупреждения.
11. Ограничения доступных данных.
12. Предложения по исправлению.
13. Итоговый статус готовности маршрута.

Разделять:

- подтверждённо корректные условия;
- обнаруженные нарушения;
- условия, которые не удалось проверить.

Не считать отсутствие найденных ошибок доказательством полной выполнимости маршрута.

## 15. Ограничения

- Не выдумывать географические данные.
- Не придумывать время перемещений.
- Не считать неизвестные часы работы подтверждёнными.
- Не удалять обязательные места без согласования.
- Не изменять утверждённые математические модели.
- Не подключать платные API без разрешения.
- Не изменять frontend и backend других участников.
- Не доверять непроверенным ответам LLM.
- Не выдавать синтетические тесты за пользовательское тестирование.
- Не утверждать, что проверки выполнены, если они не запускались.

## 16. Критерии завершения

Проверка считается выполненной, если:

1. Проверены все применимые ограничения.
2. Обнаруженные нарушения зафиксированы.
3. Указаны непроверенные условия.
4. Созданы или выполнены необходимые тесты.
5. После исправления ошибок проведена повторная проверка.
6. Подготовлен отчёт.
7. Итоговый статус маршрута обоснован результатами проверки.

Все объяснения и документацию писать на русском языке.
